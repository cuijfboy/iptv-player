## 0. 结论

刷新被「进程死亡」打断后，重触发**不再被 30 min 退避挡住**：命中「排队中 **且** 有未收尾运行标记」
时用 `ExistingWorkPolicy.REPLACE` 立即重排；正在运行 / 普通退避 / 队列空 / 已结束一律保持既有语义
（逐字不变）。

## 1. 根因

- 进程死亡后 WorkManager 把 `refresh-manual` 重排成 `ENQUEUED` + 上次尝试的 **30 min 退避**
  （真机 `dumpsys jobscheduler`：`Minimum latency +29m27s`、`Backoff initial=+30m`）。
- `RefreshScheduler.enqueueNow` 一直用 `ExistingWorkPolicy.KEEP` ⇒ **重触发是 no-op**（队列里那条
  谁也挤不动），而界面把等待显示成「已排队，等待网络…」——**等待原因被写错**。

## 2. 关键难点

WorkManager **无法区分**「进程死亡重排」与「worker 自己 `retry()`」（两者都是 `ENQUEUED` +
`runAttemptCount ≥ 1` + 退避）⇒ 必须用**自有持久标记**。

## 3. 改法（4 处）

1. **台账**：`RefreshRunLedger` + `SharedPrefsRefreshRunLedger`（文件 `refresh-run`，键
   `run-unconcluded`，开工 / 收尾都 `commit`）+ `recordingRefreshRun`：`try/finally` 包住 worker
   运行，**成功 / retry / give-up / 取消都清标记，只有进程死亡留痕**。
2. **纯决策**：`RefreshReclaim.plan(existing, runUnconcluded)` —— `QUEUED` 且有标记 ⇒ **REPLACE**；
   `RUNNING` ⇒ KEEP（不杀正在跑的）；普通退避 / 队列空 / 已结束 ⇒ KEEP。
3. **入队口**：`WorkEnqueuer.enqueueOnce(spec, policy)` 增参 + `existing(name)`
   （`getWorkInfosForUniqueWorkFlow().first()`，不阻塞）；`enqueueNow` 改 `suspend`（唯一生产调用方
   `WizardUpdatePort.start()` 本就是 suspend）。
4. **可读的等待原因**：`WizardUpdateWait{AWAITING_CONSTRAINTS, RETRY_AFTER_INTERRUPTION}`（纯增量）
   + 新串「上次更新被中断，正在重试…」；`WORK_SCHEDULE` 增 `queuedState` /
   `interruptedRunOnRecord` / `policy`。

## 6. 回退

去掉 `RefreshReclaim` 的 `REPLACE` 分支即逐字回到旧行为（`KEEP`）。

## 7. 已知限制（供 QA 判读）

1. 向导 `maybeStartUpdate` 仍只在 `NotStarted` 时自动重触发——**故意没放宽**（放宽会变成「每次状态
   变化都重排」的死循环）。若真机发现自动重触发偶发不发生，那是**入队时机**问题，建议另立卡
   （例如「启动时若台账有未收尾运行就重排一次」）。
2. 台账是**全局单布尔**，不按 unique 名分桶（周期运行被杀也会留标记；影响面小，如实记录）。
