## 0. 结论（先看这段）

**刷新真的落库了。** 根因是刷新管线**只写 `stream`、用的是 `ChannelMapper` 按「本次装载序号」发的内存 channel id，而这些 id 在 Room 里根本不存在**，于是 `stream.channel_id -> channel.id` 外键把**整批**写回滚掉（`DB_FAIL{streams:466, written:0}`）。修法沿用既有的**唯一写入接缝 `CatalogSink`**：刷新先经接缝 upsert 频道、拿到**落库后的 channel id**，再把 stream 指向这些 id，写入顺序与旧语义（浅校验/深探/评分/甄选/去重/失败不改表）都不变。

| 项 | 结果 |
|---|---|
| 根因（一句话） | 刷新只写 `stream`、用 `ChannelMapper` 的内存 channel id；Room 里没有对应 channel 行，外键拒绝整批 ⇒ `written:0` |
| 修复 | `CatalogSink` 增加 `upsertChannels()`（**增量**、键 `(name_key, group_key)`、**不删**频道），刷新在写 stream 前先解析/落库 channel id |
| 离线复现 | `RefreshPersistRoomTest`：直接经 `RoomStreamRepository` 写一条孤儿 stream ⇒ 被拒 + `DB_FAIL`（复现 `written:0`） |
| 离线证明 | 同文件：刷新后 channels+streams 都在 Room、外键成立、可被 `StreamRepository.candidates` 选中；重复刷新幂等；全失败不改表 |
| 真机证据 | 电视上一次 MANUAL 刷新（18 源，42 min 跑完 `SRC_REFRESH_DONE`）后 Room 实测 **channels 189→1031、streams 0→1822、启用流 320 = selectedPrimary 223 + backup 97**，`PRAGMA foreign_key_check` **0 违规**、孤儿 stream **0**；随后 `PLAY_FIRST_FRAME{costMs:735, 1920×1080 AVC/AAC}` —— **刷新后可起播**（修复前是 `written:0`） |
| 质量门 | `./gradlew --offline check` 绿；三道静态守卫（sensitive-info / tv-focus / notification-channel）全绿 |
| 与文档差异 | `docs/02` §4.3 端口未变、§5.1 表未动；接缝新增一个方法（`:core:data` 内部实现），不外露 |

**一处口径变化（报 god/arch 裁）**：刷新现在会**新增**它看到的频道行（只增不删、保留用户列）。这正好补上 dev-a-20 记的已知缺口「刷新管线没有写频道行的出口 ⇒ 只存在于订阅 URL 的频道不会进列表」；代价是刷新会把源里**不可用**的频道也带进列表（它们没有「不可用」标记，只能靠流的甄选体现）。判据「刷新后 channels+streams 都在 Room 且外键成立」按此实现。

## 1. 复现与定性

### 1.1 现象（来自 `docs/05/57` §7-1）
手动刷新跑 11.7 min，`SRC_REFRESH_DONE{phase:DONE, channels:207, selectedPrimary:131, …}`，但会话里**没有** `selection persisted` 的 `DB_UPSERT`，只有两条
`DB_FAIL{message:"stream upsert failed", streams:466, written:0, err:"FOREIGN KEY constraint failed (code 787 SQLITE_CONSTRAINT_FOREIGNKEY)"}`。浏览页仍是快照的 189 台——刷新**空转**。

### 1.2 根因（代码链）
1. `RefreshSourcesUseCase` 的候选集来自 `ChannelMapper.toDomain(capped)`：`ChannelMapper` 按**本次装载序号**发 id（`channelId = index+1`），注释里写明「ids are not identity across refreshes」。
2. 管线只调 `streamRepository.upsertAll(...)`，**从不写 `channel`**；写进去的 `stream.channel_id` 就是上面那批内存 id。
3. Room 的 `stream` 表有 `ForeignKey(stream.channel_id -> channel.id, ON DELETE CASCADE)`。库里只有快照的 189 行（库 id 1..189），刷新那批 id 一旦越界或不重合，**第一行就 FK 失败**；`StreamDao.upsertAll` 的 `written` 在插入之后才自增，所以是 `written:0`，`RoomStreamRepository.upsertAll` 捕获异常并记 `DB_FAIL`——**表现是「刷新成功、库没变」**。

**一句话根因**：刷新用**内存 channel id** 写 `stream`，而这些 channel 行从未落库，`stream.channel_id → channel.id` 外键拒绝整批。

### 1.3 为什么离线单测没抓到
`RefreshSourcesUseCaseTest`/`RefreshBackHalfTest` 走的是**内存** `ChannelStore` + `InMemoryStreamRepository`——`StateFlow` 没有外键可违反，所以测试全绿而生产失败。这正是 `docs/05/23` 收口时点出的「两条写入端」问题的同一类：**接缝只统一了导入，刷新没走接缝**。

## 2. 修法（沿用 `CatalogSink` 接缝）

### 2.1 接缝加一个方法（不破坏「整体替换」契约）
`core/data/.../store/CatalogSink.kt` 新增：

```kotlin
suspend fun upsertChannels(catalog: MappedCatalog, nowMs: Long): Map<Long, Long>
```

- 语义：把 `catalog` 里的频道**变成存在**（键 = §5.1 `(name_key, group_key)`，已存在则**保留该行与其用户列**），返回 **`内存 channel id -> 落库 channel id`**；**只增不删、不写 stream**。
- 与 `write()` 的分工写进 KDoc：`write()` = **整体替换**（导入/播种拥有频道表）；`upsertChannels()` = **刷新**用（只保证「我要挂流的频道存在」，绝不删除用户正在看的表）。
- 两个实现都补齐：
  - `RoomCatalogWriter.upsertChannels`：分批（`BATCH_SIZE=500`）`channelDao.upsertAll` 取回 id；存储失败**降级**为记 `DB_FAIL` + 返回空 map（docs/02 §11），`CancellationException` 照旧上抛；
  - `ChannelStore.upsertChannels`：内存版按同一键增量插入、给新行发新 id（测试专用，行为与 Room 对齐）。

### 2.2 管线里改「写入顺序」
`RefreshSourcesUseCase` 注入 `CatalogSink`，在**原有** `Persist(candidates)` 之前插入一步解析：

```kotlin
val resolved = resolveStreamChannelIds(ChannelMapper.toDomain(capped))  // 先落频道、拿库 id
val persisted = persistMergingHealth(resolved)                          // 再写 stream（沿用旧逻辑）
… runBackHalf(channelIndex = resolved.channels.associateBy { it.id }, candidates = persisted, …)
```

`resolveStreamChannelIds`：`catalogSink.upsertChannels(...)` → 把 `channels`/`streams` 的落库 id 重写；**频道被接缝判定未落库的 stream 直接丢弃**（无 channel 行时外键必失败，挂错频道更糟）。接缝返回空 map（存储失败）时返回空目录 ⇒ 这一轮**不写任何 stream**（不制造第二波 `DB_FAIL`），并已在接缝侧记了 `DB_FAIL`。

### 2.3 保持的既有语义
浅校验 / 深探 / 评分 / 甄选 / 去重 / `isFresh` 断点续跑 / 预算 / 取消 / 单频道 `ON_DEMAND_SINGLE_CHANNEL` 路径 **一行未动**；`persistMergingHealth` 的「合并既有健康度」原样保留，只是现在按库 id 取既有候选。失败路径（0 候选 / 全源失败）依旧**不改表**。

## 5. 未做 / 判断点

### 5.1 附带发现（**本卡未修**）：浅校验的健康戳仍按「内存 stream id」落库
同一类根因的第二处：**channel id 本卡已修，stream 自己的 id 没有修**。管线里 `persisted`（=`ChannelMapper` 的 stream，id 是本次装载序号）在写库后**没有回读库 id**，于是：

- `shallowValidate` 的 `streamRepository.recordOutcome(stream.id, …)` 拿内存 id 去 `streamDao.getById` ⇒ **要么查不到（空操作），要么撞上别的行（把健康戳/`play_history` 写到不相干的流上）**；
- `runBackHalf` 里 `streamRepository.health(stream.id)` 同理 ⇒ 评分看到的尝试数恒为 0。

**真机证据（本轮刷新）**：`streams_checked=1822`（全部）而深探通过只有 331 ⇒ 浅校验的 1822 次 `recordOutcome` 显然不是打在「自己那一行」上的；`play_history=1633` 行也随之产生。**读回路径仍然成立**：`isFresh` 靠 `persistMergingHealth` 合并库里既有健康度 + 最终 Persist 用 `(channel_id, url_hash)` 回写 `last_ok_at`，所以「第二次刷新跳过新鲜流」没有被破坏。

**影响**：不影响「刷新→落库→起播」（本卡目标），但健康数据会错位、`play_history` 归属错误、评分的 `stability` 维度偏保守。**修法方向**：在写 stream 之后把 `(channel_id, url_hash) -> 库 stream id` 解析回来（与 `upsertChannels` 对称，读多写零），再进入浅校验/评分；需要给接缝或 `StreamRepository` 加一个只读的 id 解析口（`StreamRepository` 是 §4.3 冻结端口 ⇒ 走 §4.0 F6 让 arch 裁）。

1. **刷新会新增频道**（见 §0 口径变化）：若 god 认为「刷新只该更新已有频道的流、新频道一律不进列表」，改法只需在 `resolveStreamChannelIds` 里把「接缝新插入的行」剔除（接缝仍按同一键返回 id），不需要动别的代码——但那样就**保持** dev-a-20 记的缺口。
2. **内置源在本网段对 GitHub raw 全超时**：与 App 无关（电视可 ping、`docs/05/57` §2.2 同类归因），但会让「刷新有没有用」的真机取证依赖外部网络。建议归档一条**自持源**（局域网/本地 HTTP）作为后续真机取证的固定入口。
3. **`docs/05/57` §4 的断言还原不完整**（代理分量键），已在本文件 §4.1 记明，建议 QA 侧补一句收尾清单。
4. 未做：定时刷新（`refresh-daily`）真机复跑、长稳；本轮只覆盖 MANUAL。
5. 本轮为隔离变量**清空过 `stream` 表**、并**手工写入过 1 条订阅行与 5 个收藏**用于取证书定位（真实链路：订阅行由「源管理」UI 读、收藏由「只看收藏」筛选），收尾 `pm clear` 一并清除。
6. 设备收尾：包留机 + `pm clear` + 回桌面 + 常亮关。
