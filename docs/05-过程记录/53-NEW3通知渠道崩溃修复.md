## 2. 根因（代码链，逐跳可复核）

现象与系统证据由 QA 提供（48 号 §2、证据 `evidence/P2Gv3/crash-notification-channel.txt`）：`NotificationService: No Channel found for pkg=ilab.iptv.player, channelId=refresh, id=12023` → `FATAL EXCEPTION: main … RemoteServiceException: Bad notification for startForeground` → `Force finishing activity …WizardActivity`（本轮 3 次复现）。

代码链：

1. 任何刷新入口（向导第 1 步主按钮 / 手动 / 06:00 定时）都只做一件事：`RefreshScheduler.enqueueNow/scheduleDaily` → `WorkManagerEnqueuer` 把 **`RefreshWorker`** 放进队列。**没有任何入口绕过这个 worker**。
2. `RefreshWorker.doWork` 起跑第一件事是 `postForeground(...)` → `setForeground(RefreshNotifications.foregroundInfo(...))`，而该 `ForegroundInfo` 用的是 **`RefreshNotifications.CHANNEL_ID = "refresh"`**（通知 id `0x2EF7` = 12023）。
3. `RefreshNotifications.ensureChannel()`（渠道的唯一创建者）**全仓没有调用点**：`rg -n "ensure[A-Za-z]*Channel"` 只命中它自己的定义，以及播放侧 `PlaybackNotifications.ensureChannel`（那条有调用点，见 §4.1）。渠道 `refresh` 因此从未存在于系统里。
4. 平台在 `startForeground` 处判定通知不可用并抛 `RemoteServiceException` —— 抛点在 WorkManager 的 `SystemForegroundService` 主线程路径上，**不在 `RefreshWorker` 的调用栈里**，所以当时 `postForeground` 的 `try/catch`（里面只有 `android.util.Log.w`）永远拿不到它。这正是「加个 catch」解决不了的原因。
5. 影响面：① 向导主路径按下即闪回桌面；② 每次 06:00 与任何手动刷新都崩；③ 崩后 WorkManager 30 min 线性退避重排、到期再崩；④ 全天 `SRC_REFRESH_DONE = 0`（刷新管线真机从未跑完）。

## 3. 修法：改了什么、为什么改在这里

### 3.1 代码改动（2 个 main 文件）

| 文件 | 改动 |
|---|---|
| `app/src/main/kotlin/ilab/iptv/player/refresh/RefreshNotifications.kt` | `ensureChannel(context)` 由 `Unit` 改 **`Boolean`**（「渠道现在是否可用」）；渠道的创建收敛到一个新增的 `ChannelSink` 接缝（`channelExists()` / `createChannel(id,name,description)`），生产实现 `AndroidChannelSink` 就是那两次 `NotificationManager` 调用，`@RequiresApi(O)` 标注（外层 `SDK_INT < O` 提前返回，lint 需要这个标注才认流程） |
| `app/src/main/kotlin/ilab/iptv/player/refresh/RefreshWorker.kt` | `doWork` 用 `startForegroundState(logger, trigger)` 取代原来的「先 post、再记一条 SERVICE_REFRESH_START」；`postForeground` 返回是否被平台接受；进度帧只在渠道可用时才 `setForeground` |

`doWork` 现在的顺序（关键就是这个顺序）：

```
WORK_RUN(start) → ensureChannel（建渠道，拿不到就降级）→ setForeground(第一帧) → 流水线跑（每阶段更新通知 + setProgress）→ WORK_RUN(结论)
```

### 3.2 为什么是「刷新任务起跑前（worker 的 run 路径）」而不是应用启动

1. **单一收口**：所有入口都落到 `RefreshWorker.doWork`（§2 第 1 条），所以一处调用覆盖全部；`IptvApplication.onCreate` 也可靠，但它覆盖的是「进程启动」这件事，而这个缺陷的本质是「要发通知这件事」。
2. **时序即证明**：`createNotificationChannel` 是同步 binder 调用，紧接其后的第一次 `setForeground` 必然能看到渠道，不存在竞争窗口。
3. **不依赖启动顺序**：将来新增入口（另一个 worker、诊断面板直发）仍要经过 worker 的前台路径；而启动钩子只保证「启动过」，不保证「这次要发的通知有渠道」——用户在系统设置里删掉渠道后再跑一次刷新，启动钩子也救不了（其实两者都会在 onCreate 重跑，但 worker 路径天然更贴调用点）。
4. **与播放侧同形**：`PlaybackService.onCreate` 里就有 `PlaybackNotifications.ensureChannel(this)`，位置正好在 `ServiceCompat.startForeground` 之前 —— 播放侧没出这个 bug 的原因就在这里（§4.1），沿用同一种写法让两份通知代码可对照。

### 3.3 失败可观测 + 降级（不崩进程）

| 失败 | 处置 | 事件 |
|---|---|---|
| 渠道拿不到（`ensureChannel` 返回 false：API 26+ 但 `NotificationManager` 为空 / 平台不落地 / 创建抛异常） | **不发通知**，整轮照跑（刷新是目的，前台状态是手段） | `SERVICE_REFRESH_START{result=failed, reason=channel_unavailable}` |
| `setForeground` 抛可捕获异常（如后台起前台被拒） | 继续跑；后续阶段帧仍会重试更新通知 | `SERVICE_REFRESH_START{result=failed, reason=set_foreground}` |
| 一切正常 | 正常跑 | `SERVICE_REFRESH_START{result=ok}`（**每次运行恰好一条**，与原实现一致） |

**未新增事件码**：`SERVICE_REFRESH_START` 早已注册（`core/common/EventCodes.kt`），本轮只是补上它的 `result`/`reason` 字段，与 `docs/03 §3.3` 及 28 号文档里 `SERVICE_PLAYBACK_START` 的既有写法一致。
