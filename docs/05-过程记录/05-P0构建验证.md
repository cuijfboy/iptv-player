### 4.3 纯 Kotlin 守护的反证实验（本任务第 5 项）

1. 临时新增 `core/domain/src/main/kotlin/ilab/iptv/player/core/domain/PurityGuardProbe.kt`，内容含 `import android.os.Bundle`。
2. `./gradlew :core:domain:verifyPureKotlin` → **失败**，输出：

   ```
   > Purity guard failed: :core:domain is a pure-Kotlin module but imports Android:
       src/main/kotlin/ilab/iptv/player/core/domain/PurityGuardProbe.kt  ->  android.os.Bundle
   ```

3. `./gradlew check` → **失败**（2 个失败：`verifyPureKotlin` 与 `:core:domain:compileKotlin`，后者因为纯 Kotlin 模块没有 Android 类路径，`android.os.Bundle` 本来就解析不到 —— 守卫生效时编译也会同时失败）。
4. **删除探针文件**，`./gradlew check` → **成功**（`verifyPureKotlin: OK` ×3，`BUILD SUCCESSFUL in 7s`）。工作区已确认无残留（`find core/domain -name '*.kt'` = 0）。

## 5. 失败与修复（本轮真实修掉的构建缺陷）

| # | 失败 | 根因 | 修复 | 状态 |
|---|---|---|---|---|
| 1 | `build-logic/build.gradle.kts`：4 × `Unresolved reference: findLibrary`，导致 `tools/bootstrap-gradle.sh` 连 wrapper 都生成不出来 | Gradle 8.13 为版本目录生成的是**只含类型化别名**的访问器，`libs.findLibrary(...)` 在 included build 的根构建脚本和预编译约定插件里都不可用 | 6 个文件改为显式取目录对象：`extensions.getByType<VersionCatalogsExtension>().named("libs")`，再 `catalog.findLibrary(...)` | 已修（实测通过） |
| 2 | `:app` 里 `@HiltAndroidApp` / `@AndroidEntryPoint` 无法解析（编译期） | Hilt 的 Gradle 插件**不会**自动添加 `hilt-android`（实现）与 `hilt-compiler`（KSP）依赖，只套 `alias(libs.plugins.ksp/hilt)` 不够 | `:app` 改套约定插件 `id("iptv.hilt")`（它同时给实现依赖 + KSP 处理器） | 已修（实测通过） |
| 3 | `./gradlew lint` 失败：`AndroidManifest.xml:15 Error: Expecting android:banner ... [MissingTvBanner]` | 带 `LEANBACK_LAUNCHER` 的电视应用必须有首页 banner，`abortOnError = true` 下这是 error | 新增占位 banner `app/src/main/res/drawable/app_banner.xml`，并在 `<application>` 上挂 `android:banner`（正式 320×180 美术资源留到 P1 设计系统） | 已修（lint 0 error） |
| 4 | `verifyPureKotlin` 的报错文案写成 `:core:domain:verifyPureKotlin is a pure-Kotlin module` | 任务动作里 `path` 取到的是**任务路径**而不是模块路径 | 在工程作用域先取 `guardedModulePath` 再传进任务 | 已修（现在输出 `:core:domain is a pure-Kotlin module`） |
| 5 | 上一轮的 3 条环境阻塞（无 Gradle / 无网络 / 无缓存） | 沙箱禁网 | 本轮沙箱放开后自动消除；`tools/bootstrap-gradle.sh` 一次跑通 | 已闭环 |

### 8.2 反证实验 · CR-01 依赖守护（每条都改完即撤回）

守护任务 `verifyModuleDependencies` 的报告原文（一次跑出三类违规，说明它不是只查一条）：

```
> Dependency guard failed (docs/02 §3.2):
    - rule 5 (api exposure): :core:data exposes :core:database through `api` — declare it with implementation() …
    - rule 2: :feature:channels declares :core:database directly (see docs/02 §3.2)
    - rule 5 (no cycles): :core:common -> :core:log -> :core:common
```

| 实验 | 注入 | 期望 | 实测 |
|---|---|---|---|

### 9.4 顺手排查的坑（含判断依据）

1. **JDK 17 够不够 → 够，但改用 21**。依据：反编译 AGP 8.11.1 jar 里的 `com/android/build/gradle/internal/plugins/AndroidPluginBaseServices.class`，跑的是 `JavaVersion.current().isCompatibleWith(JavaVersion.VERSION_17)`，不满足才报 `AGP_USED_JAVA_VERSION_TOO_LOW` —— 所以 17 是它写死的**下限**，17 能跑。换 21 的理由是**与已验证环境一致**：本机五条命令的绿灯全在 JBR **21.0.10** 上跑出来，中间没有任何一步是在 17 上验证过的。
2. **AGP 8.11.1 要求的最低 Gradle = 8.13**。依据：同一个 jar 的 `VersionCheckPlugin.class` 里常量 `"8.13"`（不满足会报 `Minimum supported Gradle version is 8.13`）；而 wrapper 正是 `gradle-8.13-bin.zip` —— 正好达标，wrapper 一行都不用改。
3. **`-Dorg.gradle.java.home="$JAVA_HOME"` 覆盖仍有效**。依据：`./gradlew -Dorg.gradle.java.home=/nonexistent/jdk-xyz help` → `Value '/nonexistent/jdk-xyz' given for org.gradle.java.home Gradle property is invalid (Java home supplied is invalid)`，即命令行值**压过** `gradle.properties`（否则那个不存在的路径不会生效）。所以 `gradle.properties` 里写死的 macOS JBR 路径在 Linux 上由这条覆盖兜住 —— **前提是每个 Gradle 调用都带这个参数**，漏一个就会去找 `/Applications/Android Studio.app/...` 而失败（本轮三个调用全部保留）。
4. **该装哪几个 SDK 组件**。依据是 AGP 自己的解析结果：本机首次构建（22:04）时 AGP **自动补装**了 `platforms/android-36` 与 `build-tools/35.0.0`（此前 SDK 里只有 36.1.0 / 37.0.0），说明 `compileSdk = 36` + AGP 8.11.1 默认 build-tools = **35.0.0**，正是 CI 里显式安装的那两个包（外加 `platform-tools`）。
5. **daemon 与缓存**。保留 `--no-daemon`（一次性 runner 上留 daemon 只多占内存）；新增 `actions/setup-java` 的 `cache: gradle`，它缓存 `~/.gradle`，同时省掉每次约 130 MB 的 gradle-8.13 发行包下载。`--stacktrace` 为首次真跑提供可定位堆栈。

### 11.5 边界、规则与未做项

1. **编码容错**：严格 UTF-8 失败 → 严格 GB18030（结果标 `NET_CHARSET_FALLBACK`）→ GB18030 替换解码（另标 `lossy`）。BOM（UTF-8/UTF-16/UTF-32）优先且被剥离。事件码取自 `EventCodes` 常量，未自造。
2. **去重的两层语义**：`UNIQUE(channel_id,url_hash)` 与 `UNIQUE(name_key,group_key)` 是两个不同的键，`PlaylistNormalizer` 两层都实现——同一 URL 服务多频道在频道级允许、在 `SRC_DEDUPE` 的流级被削（`docs/02` §6.1 "按 url_hash 去重；按源交错"）；按源交错会改变保留哪一条（单测固定了两种结果）。
3. **`group_key` 的推导**（docs/02 §5.1 未规定，本包做出的选择）：取**分组标题的归一化键**，缺失时回落 `ChannelGroup.OTHER.key`（`"other"`）。理由：若用 5 个枚举值当 `group_key`，"同名台跨分组共存"会被重新合并。**已报 god 复核**。
4. **`#EXTVLCOPT`**：派单写"忽略但要容错"；实现按容错处理任意键，并把 `http-user-agent` / `http-referrer` 采进 `RawEntry`（该结构本就有这两个字段）。属加法，若 god 要求严格忽略，删两行即可。
5. **GB 级长行**：单测用 5 MB URL + 2 MB 属性值的内存样本验证一次线性扫描（属性解析无正则、无回溯），不提交大夹具。
6. **构建期真缺陷**：`HashMap.putIfAbsent` 在 Android 需 API 24（本模块 minSdk 21）→ `lintDebug` **error**，已改为显式 `containsKey` 判断；这条是 `check` 抓到的，不是肉眼看出来的。
7. **未做（不属本包）**：网络抓取与 `SourceProvider`（P2-4）、`XTREAM`/`JSON` 解析、EPG（XMLTV）、UI、落库、`git commit`/`push`。docs/01–04 结论未改。

### 13.2 语义与边界（对齐 docs/03 §3.3 的 2026-09-22 口径）

3. **条数对齐**（独立脚本核过，非肉眼）：`EventCodes.kt` 有 **46** 个 `const val`、`ALL` 有 **46** 个条目、无重复、无「声明了但没进 `ALL`」的常量；`docs/03 §3.3` 表格把 `/` 配对展开也是 **46**（脚本逐行展开得出）。
4. **旧码残留检查**：`rg -n "SRC_FETCH_FAIL" --glob '!docs/**' --glob '!**/build/**'` 只命中 `EventCodes.kt`（常量声明、KDoc、`ALL`）与 `PlaylistParsers.kt` 的 KDoc 说明——**业务代码里没有任何地方仍用 `SRC_FETCH_FAIL` 兜解析失败**；`core/source` 其它文件（normalize / text / parser 其它类）不含任何事件码字面量或 `SRC_*` 引用。

### 12.5 音频两条路径 + 错误模型（真机证据）

**两条路径（§7.6 要求“两种路径都记录观测”）**：AC3 / EAC3 公开测试向量（S2 用过的同一批，经本机 `python3 -m http.server 8791` 分发），由**生产引擎**播放：

| 轮次 | 样本 | 到 READY | 首帧(合成) | 实测 acodec | 引擎观测 `audioPath` |
|---|---|---|---|---|---|
| `preferPassthrough=true` | AC3 2.1 / AC3 5.1 / EAC3 5.1 | 312 / 175 / 166 ms | 539 / 413 / 408 ms | `audio/ac3` / `audio/ac3` / `audio/eac3` | **PASSTHROUGH_HAL ×3** |
| `preferPassthrough=false` | 同上 | 246 / 233 / 240 ms | 546 / 426 / 422 ms | 同上 | **PASSTHROUGH_HAL ×3** |

`dumpsys media.audio_flinger`（两轮各抓一份）中，本进程 pid 名下出现 **`HAL format: 0x9000000 (AUDIO_FORMAT_AC3)`** 与 **`0xa000000 (AUDIO_FORMAT_E_AC3)`** 的 direct 输出线程（channel mask 7 / 0x3F，48 kHz，standby=0）。
结论与 S2 §3.4 一致：**本机 AC3/EAC3 无论开关透传都以压缩码流进 HAL**；AAC/MP2（§12.3 的 5 条频道）走 PCM 路径。引擎的两个开关位都在接口上（`PlaybackRequest.preferPassthrough`），观测项写进 `PLAY_FIRST_FRAME` 的 `audioPath` 字段。
纯音频流**不会触发** `onRenderedFirstFrame`（S2 已踩过），本实现按“READY + 正在播 + 位置前进”合成同口径的 `FirstFrame`，因此 AC3/EAC3 也有 `costMs`（上表 408–546 ms），口径写在 `Media3Engine` 的 KDoc。

**错误模型（`AppResult` + `FailureClass`）真机三连**（`engine-err3.json`）：连接被拒 `http://127.0.0.1:9/…` → `NET_UNREACHABLE`（94 ms）；**HTTP 404** → `HTTP_CLIENT` + **`httpStatus=404`**（626 ms）；不可达地址 `10.255.255.1:8080` → `NET_UNREACHABLE`（51 ms）。三条都走 `AppResult.Err`、状态机落到 `ERROR`、并发出 `PLAY_PREPARE_FAIL`（含 `failure`/`httpStatus`/`attempt` 字段），未抛异常穿过边界。
> 404 的 `httpStatus` 是本轮**真机抓到的缺陷**：media3 的 `InvalidResponseCodeException` 把状态放在 **public 字段** `responseCode` 上，最初只反射 getter 的写法在设备上返回了 `null`（首轮日志 `httpStatus=null`）；补上字段读取后复测为 `404`，并加了单测（`HttpStatusReader` 88.2% 的那两行就是这条分支）。

### 12.6 未做项、边界与需 god/arch 裁决的口径

1. **未做（明确不在本包）**：播放界面/信息条/5 s 淡出（P1-4）、换台键位与 `PLAY_SWITCH_CHANNEL` 埋点归属（P1-5）、`FailoverPolicy` + `PlaybackWatchdog`（P1-6）、`MediaSession`/音频焦点/`setWakeMode`/前台服务（P1-7）、日志落盘（P1-8）、libVLC（§7.8 已定：不打包）。**播放 10 min / 2 h 长稳未测**：本轮只有单轮 PSS 增量（5 条 +8–10 MB、30 次换台 +17.5 MB，含解码器/缓冲/新页面首帧缓存），**不足以判定“无内存泄漏”**，那是 P1 出口判据，需要长稳跑。
2. **`AppError.http` 与 docs/02 §4.6 不一致（报 god/arch）**：§4.6 把 **HTTP 429 / 5xx** 归 `HTTP_SERVER`（退避→重试→切源），但 `:core:common` 的 `AppError.http` 按 `status in 400..499` 判，**429（和 408）会被归成 `HTTP_CLIENT`**（永久降权 + 直接切源）。P1-3 的归类表按 §4.6 实现（`PlaybackErrorMapper.httpError`，含单测），**没有改动 `AppError.http`**——它属冻结基础设施且经 QA 复核。请裁决：改 `AppError.http` 的边界，还是把 §4.6 的 429 行改写成 4xx。
3. **`PLAY_ENGINE_INIT/RELEASE` 的触发者口径（docs/03 §3.3 与 docs/02 §7.7 打架）**：§3.3 写“触发点 = 引擎生命周期”，§7.7 写“触发者 = 控制器”。实现取**控制器侧**（引擎只发 `PlaybackEvent.Capabilities`，由 `PlaybackEventLogger` 落 `PLAY_ENGINE_INIT`；`release()` 后由控制器落 `PLAY_ENGINE_RELEASE`），与 §7.3“引擎只发事件、不写日志”自洽。
4. **`EngineSelector.select` 的返回类型（接口建议）**：冻结签名返回**非空**工厂，但 §7.1 要求“找不到 → `AppError.capability`，不静默降级”。实现加了 `selectOrNull`（`select` 找不到就抛，不降级）。建议 arch 把接口改成可空返回或 `AppResult`，否则每个调用点都要额外方法。
5. **宽高比的落点（§7.4 与实际依赖）**：§7.4 写“由引擎适配到 `AspectRatioFrameLayout`”，但该 View 在 **media3-ui（属 `:feature:player`）**，`:core:player` 不该依赖 UI。做法：引擎持有冻结参数 `AspectRatioMode` 并给出纯映射 `AspectRatioPlan`（`ScaleMode` + 固定比例）；P1-4 把它映射到 `AspectRatioFrameLayout.RESIZE_MODE_*`（FIT=0 / FILL=3 / ZOOM=4，`FIXED_4_3` 用 `setAspectRatio(4f/3f)`）。请 arch 确认这条切分。
6. **引擎调度器必须是 Looper 支撑的（新接口约束）**：ExoPlayer 只能在自己的 application looper 上驱动，因此 `PlayerEngineFactory.create(dispatcher)` 要求 `Handler(thread.looper).asCoroutineDispatcher()` 这类单线程、带 Looper 的调度器（构造期即 `checkNotNull(Looper.myLooper())` 快速失败）。`:core:common` 现在只有 `DispatcherProvider` 契约、**尚无实现**，P1-4/P1-7 落地时必须满足这条，否则第一帧会以“wrong thread”失败。
7. **`preferPassthrough` 是实例级开关**：§7.6 第 2 步“关透传重试同一流”需要换音频 sink，而 sink 在实例构造时固定，所以该开关变化时引擎会**重建一次实例**（S5：建实例 ~4 ms，代价在内存）。默认路径不重建，S5 的单实例复用仍是常态。
8. **共享电视的并发干扰（过程记录，非产品问题）**：本轮跑真机时，同楼层的 `worker-dev-a-7` 等 agent 在**同一个包名**上反复 `adb install -r`，多次把夹具 APK 换掉（表现为 `am start` 报 “Activity does not exist” 或运行无输出）。证据文件里的时间戳与 `No activity found` 记录在案；每条真机数据都是“装好自己的包后立刻跑、立刻拉回 JSON”得到的。建议 god 对共享设备排他（一次只允许一个 agent 安装/驱动）。
9. **为落地冻结签名而新增的 §4.2 类型**：`DeviceProfile`（`EngineSelector.select` 需要）与 `Playback.kt` 全组。`:core:model` 因此新增 `api(project(":core:common"))`（矩阵 `model → common` ✅ 允许，`verifyModuleDependencies` 通过）。请 arch 注意 §4.2 剩余类型（`StreamOutcome`/`ScoreInput`/`SelectionInput`/… 与 §4.3 端口）尚未落地，属 P1-2/P2 范围。
10. **媒体层弃用告警**：`AudioCapabilities.getCapabilities` / `isPassthroughPlaybackSupported(Format)` / `DefaultAudioSink.Builder.setAudioCapabilities` 在 media3 1.6.1 标记 deprecated，但仍是 S2 实测过的那条路径（§7.6 要求复用 Spike 结论），本轮按原样保留、未换 API。lint 已通过（deprecation 不是 error）。
