## 3. schema v2：两列 user-owned 覆盖位（唯一的结构性改动）

P3-4 的两项「用户侧编辑」需要新的持久化位。`docs/02 §5.1` 冻结的 `channel` 表没有它们，所以按 §13 的口径**加一次真迁移**（v1 → v2），而不是复用既有列：

| 列 | 语义 | 归属 |
|---|---|---|
| `channel.display_name TEXT NULL` | 用户的显示名；NULL = 用源名 | **user-owned**（刷新保留） |
| `channel.user_group_title TEXT NULL` | 用户改到的分组标题；NULL = 用源分组 | **user-owned**（刷新保留） |

- 迁移 `Migrations.MIGRATION_1_2` = 两条 `ALTER TABLE channel ADD COLUMN ...`，**无默认值、无回填**：老行两列皆 NULL，行为与升级前逐字相同。
- `ChannelDao.upsertAll` 的列切分把这两列加进 **user-owned** 组（与 `favorite/hidden/sort_order/channel_no/epg_channel_id/epg_match` 同侧），所以刷新不会把改名/移动改回去——这就是 P2-2「用户侧字段优先」在 P3-4 的延续。
- 导出 schema `2.json` 已入库；`MigrationBaselineTest` 改成「v2 是当前版本、`ALL` 恰为 `(1→2)`」并校验两份 schema 都在测试资产里；`Migration_1_2Test` 用 v1 建库、插一行、迁移后校验 `name/favorite/channel_no` 原样且两列皆 NULL。

**`name_key` / `group_key` 为什么不改**：`UNIQUE(name_key, group_key)` 是刷新 upsert 的身份键，也是 EPG 匹配链的比较键。改名若写 `name_key`、移动分组若写 `group_key`，下一次刷新会「找不到这一行 → 重新插入」，列表里就会出现两台同名频道。所以两项编辑都只写**覆盖列**，身份列保持源侧值。

## 4. 批量操作：多选、四种动作、删除口径、撤销

**多选**：页头「管理」进入管理模式；管理模式内 `OK/Enter` = 标记/取消标记（不再播放），页头实时显示「已选 N 台」，行首出现 `☑/☐`。

| 动作 | 写法 | 撤销（一层） |
|---|---|---|
| 批量隐藏 | 逐个 `setHidden(true)` | 恢复到各自的旧 `hidden` |
| 取消隐藏 | 逐个 `setHidden(false)` | 同上 |
| 移动到分组 | 逐个 `setUserGroup(title)`（写覆盖列） | 恢复到各自的旧 `user_group_title` |
| 删除 | `deleteChannels(ids)`（硬删） | `restoreChannels(删除前快照)` |

**删除 = 硬删，论证如下。**

1. **软删在本期没有落点**：§5.1 的 `channel` 没有「已删除」列，唯一的用户侧布尔位是 `hidden`——把它当删除用，就等于「删除」和「隐藏」变成同一个状态，用户分不出「我暂时不想看」和「我删掉了」。
2. **硬删与数据模型自洽**：`stream.channel_id → channel.id ON DELETE CASCADE` 已由 §5.1 定义，删一行即带走它的流，不留孤儿。
3. **已知后果（如实写出，不藏）**：`channel` 的**存在**是源侧的——导入/刷新会把播放列表里仍有的频道按 `(name_key, group_key)` 重新插回来。所以硬删的语义是「**在下次导入/刷新之前移除**」，不是「永久封杀」。要「永久封杀」需要 §5.1 加一张 tombstone 表（见 §9 裁决点 ①）。
4. 撤销用**删除前抓的完整快照**（`repository.get()` 拿到的 `ChannelWithStreams`，含流），`restoreChannels` 按原 id 优先回插、身份键次之、最后新建，因此撤销后流与用户列都在。

**撤销是「一层」**：`pendingUndo` 存的是上一次批量（或重命名）的逆操作闭包，菜单项显示为「撤销：删除 3 台」。它活在 ViewModel 里、不进库——进程被杀允许丢失最后一次撤销，与频道表滚动位置同一取舍。撤销一次后菜单项消失（要做多层需要栈 + 持久化，非本卡要求）。

## 5. 重命名：`name_key` 与自动合并怎么处理

- 改名写 `channel.display_name`，**不写** `name`、**不写** `name_key`。
- 因此：**去重身份不变**（仍是源 `name_key × group_key`），**刷新自动合并照旧**（`upsertAll` 更新同一行，不会因改名多出一台），**EPG 自动匹配也不受影响**（匹配链用 `name_key`/`tvg_id`，不是显示名）。
- 界面：列表/信息条显示 `Channel.shownName`（= `display_name ?: name`）；行内加「名」标记，元数据行在有改名时改显示**源名**，所以「这个名字跟播放列表不一样」是可解释的。
- 清空输入 = 删掉覆盖位（写 `null`），行回到源名。
- **排序仍按源 `name_key`**（`ChannelSorter` 第 5 键），即改名不会让频道跳位——这是刻意的：按显示名排序会让一处改名搅动整段顺序，且会让 P2-2 的顺序断言失效。作为口径写出（§9 裁决点 ③）。

## 6. 手动绑定 EPG

**优先级（本卡的验收句「支持手动绑定不被覆盖」）** 分两处落实，两处原本就有意图、本轮补齐可验证性：

- `EpgMatcher` 第 ⑤ 条（**匹配算法零改动**）：`epg_match == MANUAL` 且 id 非空的频道直接进 `preserved`，不参与任何自动层级。
- `LoadEpgUseCase`：写回只写 `report.hits`（`preserved` 不在其中），匹配对象是**运行开始时读到的频道快照**。⇒ 刷新不会覆盖手动绑定。
- 新增单测钉死：一台 `tvg_id` 本可命中 `CCTV1.cn` 的频道，被手动绑到 `user.picked.id` 后跑整条管线，`epg_channel_id` 仍是 `user.picked.id`、`epg_match` 仍是 `MANUAL`，且日志里**没有** `EPG_MATCH_HIT`。

**候选列表从哪来**：§5.1 只存 `programme.epg_channel_id`，没有 guide 频道名，而未命中的缺口连 programme 行都没有。所以 `LoadEpgUseCase` 在每次成功解析后把该次 `<channel>` 全集写进 `EpgChannelCatalog`（`core/data` 文件缓存 `filesDir/epg-channels.tsv`，一次运行覆盖一次；它是**派生缓存**，权威副本仍是 XMLTV 文件，故不加第八张表）。

**界面（picker）**：`ChannelManagerDialogs.showEpgPicker` = 搜索框 + 列表（`EpgPickerFilter`：对 guide 显示名或 id 做大小写无关子串匹配），选中即写 `MANUAL`；已有绑定时菜单项变「解除 EPG 绑定」→ 写 `(null, NONE)`（**故意用 NONE 而不是「MANUAL + 空 id」**：`EpgMatcher` 只保留「有 id 的 MANUAL」，所以解绑后自动链可以在下次刷新重新接手）。

**三个缺口的演示结论（真网络，`-Piptv.epgSample=1`，2026-09-22）**：

## 9. 未做项与给 god 的裁决点

**未做项**

1. **真机全流程未验**（派单要求不用电视）：多选手感、长按/MENU 双入口、EPG picker 的搜索框在遥控输入法下的可用性、BACK 退出模式的实际焦点落点，均留待 QA 真机。
2. 撤销只有一层（非栈）；绑定/解绑 EPG 未记撤销（绑定是「设置项」而非破坏性操作，只有重命名记了）。
3. 排序仍按源名（§5 已写口径）；分组移动后 `reorder`（上移/下移）仍按**源 `group_key`** 取段，对已移动的频道是近似行为（该频道已不在源分组渲染，影响面小，未改）。
4. `EpgChannelCatalog` 是「最后一次成功运行」的覆盖语义；某个源本次失败时它的频道会暂时从候选里消失（下次成功即恢复）。

**给 god 的裁决点**

1. **`docs/02 §5.1` 需要回写 v2**：新增 `channel.display_name`、`channel.user_group_title`（两列均 nullable、user-owned），并补一句「用户的显示名/分组移动以覆盖列表达，身份列 `name_key`/`group_key` 不随之改变」。这是本卡唯一越出既冻结 schema 的地方，请指派 DOC 卡。

3. **改名是否应参与排序**：现按源名排序（§5）。若要按显示名排序，是一次 `ChannelSorter` 口径变更，需 arch 回写并同步改 `ChannelSorterTest`/`ChannelListRowsTest`。
4. **guide 频道表的存放**：本轮选了**文件缓存**（`filesDir/epg-channels.tsv`，派生数据、单写者）而非新建第八张表。若 arch 认为它必须进 Room，请给一张卡，按 §13 一起做 v3 迁移。
