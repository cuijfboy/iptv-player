### 2.1 起播成功率（方式 B：先筛「本网确认可稳定播放的源」，再跑 20 次）

**口径变化（必须连着读）**：v1 是「在整张 `validated.m3u` 上按行抽样 20 条，成功率 ≥90%」。这张网段经 fake-IP 中转、存在按客户端指纹的概率性反盗链闸门（31 号报告），**整张清单里有相当比例的源在本网根本不可达**——按原口径判据在目标环境里不可达。人工 2026-09-22 裁决（卡 `P1G-ASK-1`）改为 **方式 B：判据落在「本网确认可稳定播放的源」上**，并要求报告写明筛选方法与口径变化。

**筛选方法（先定后测，两步）**：

1. **候选抽样**：从 `validated.m3u`（1,317 行 / 658 条流 / 571 个频道名）按**文件序每第 15 条取 1 条**（第 3、18、33…条）→ **44 条候选**，写成 `qa-p1b-scan.m3u`。这是「源清单」抽样，不预先看健康度。
2. **在电视上用 App 逐条起播**（每条都是 `am force-stop` 冷启动 → 定位到该行 → OK → 等 9 s → 读 `PLAY_FIRST_FRAME`）→ 得到 **43 个频道**（44 条流，其中 1 个频道名有 2 条流），**35 个频道起播成功 = 本网确认可稳定播放的源池**；8 条失败逐条归因（见下）。
3. **20 次起播**：在源池里按行序取**前 20 个**逐个冷启动起播，记录 `PLAY_FIRST_FRAME.costMs`。

### 2.3 导入=整体替换（BUG-STALE-STREAM / BUG-20260922-015）

设备落盘日志（`files/logs/iptv-*.log`，QA 拉回）：

```json
{"code":"DB_UPSERT","message":"catalog persisted","fields":{"channels":658,"streams":670,"removed":0,"streamsRemoved":0}}   ← 内置夹具首次播种
{"code":"DB_UPSERT","message":"catalog persisted","fields":{"channels":571,"streams":658,"removed":585,"streamsRemoved":82}} ← 导入 validated.m3u
{"code":"DB_UPSERT","message":"catalog persisted","fields":{"channels":43,"streams":44,"removed":528,"streamsRemoved":10}}    ← 再导 43 频道清单
{"code":"DB_UPSERT","message":"catalog persisted","fields":{"channels":3,"streams":4,"removed":42,"streamsRemoved":0}}        ← 再导故障转移夹具
```

- 每一次导入后，界面头行「频道 / 流」**等于该清单自身**（571/658、43/44）——v1 报告的「导入 10 流、列表显示 22 流」不再出现。
- **无 `p12.demo.invalid` 残留**：整场 12 次 `NET_REQ_FAIL{kind=logo, url=http://p12.demo.invalid/...}` **全部发生在导入之前的夹具会话**（ts 1790037550xxx），导入后再无一条。
- 同名频道（`CCTV1/CCTV2/CCTV3/CCTV5/CCTV13`）在夹具里有 2 条流，导入真清单后逐条等于新清单的流数（`streamsRemoved=82` 正是被清掉的旧流）。
- 顺带记录一条**清单侧事实（不是缺陷）**：解析管线对**同一个 URL 只保留一次**（`PlaylistNormalizer.dedupeByUrlHash`，docs/02 §6.1 的「同 URL 只留一条」口径），所以 QA 的故障转移夹具里若把 `CCTV1` 与 `A-主源故障` 的备胎写成同一个 URL，`CCTV1` 会被丢掉（本轮实测 5 条 → 4 条）。写夹具时要给不同频道用不同 URL。

- 少于 30 条的 `PLAY_SWITCH_CHANNEL` 是**按下一次键时上一次切换还在准备中**（切换事件按「被后一次取代时结算」发出），不是漏切：同一会话里 `PLAY_PREPARE_START` 与 `PLAY_FIRST_FRAME` 成对出现。
- **尾延迟是源侧**：合计 113 条里 3 条 >3 s（2.7%），最大 4,545 ms 的那次目标频道是 `CCTV-15音乐`（`genglei.8866.org`），它的首帧本身在本轮就波动在 0.76–4.21 s。App 侧的开销（决策 + 起播调度）在几十毫秒量级。
- 与 v1 的差别：v1 avg 1,220.5 / p95 2,197 / max 2,326（那是夹具里更快的源）。**判据「每次 ≤3 s」在本轮不是 100% 成立**，如实记为风险（§5）。

### 2.5 故障转移

夹具（3 频道/4 流，导入后头行 `频道 3 / 流 4`）：`A-主源故障` = 死主源 `http://10.255.255.1:81/…` + 真备胎；`A-无备胎` = 单条死流。

09:10:40.248 PLAY_PREPARE_FAIL  {failure=NET_UNREACHABLE, attempt=1}
09:10:40.281 PLAY_FAILOVER      {from=1329, to=1330, reason=NET_UNREACHABLE, action=switch}   ← 决策 33 ms
09:10:40.288 PLAY_PREPARE_START {channelId=1157, streamId=1330}
09:10:40.852 PLAY_FIRST_FRAME   {costMs=532, 720x576 avc mp2}                                 ← 失败→出画面 604 ms

- 画面确实出图（`phase5/01-failover-played.png` 是 CCTV1 节目画面上带「已切换备用源」状态）。
