## 2. 模板一 · 设计评审记录

**触发**：G1 或任何一次设计/接口评审。**责任人**：arch。**对齐既有**：`02-设计评审记录.md`（`R-*` 意见 / `W-*` 回写 / `Q-*` 开放问题三套编号）。

### 2.1 字段说明

| 字段 | 取值 / 格式 | 说明 |
|---|---|---|
| 评审对象 | 文档名 + **章节号** | 精确到 `§4.3`，不写整篇 |
| 严重级 | **阻断 / 重要 / 建议** | 阻断=不修不能开工；重要=不挡 P0 但须在对应阶段前闭环；建议=择期 |
| 意见 | 问题 / 风险 + 依据 | 依据要能落到实测数据或文档原文，不写"感觉" |
| 结论 | 该条意见的**处置结论** | 已有改动写"已修：<目标章节>"；未修的写"回写：<责任方>" |
| 回写清单 | 目标文档 · 章节 ｜ 回写内容 ｜ 责任方 ｜ 状态 | 状态用 `✅ 已改` / `⏳ 待执行` / `⏳ 待 god 答复` |
| 开放问题 | 问题 ｜ 推荐 ｜ 待谁拍板 | 需 god 拍板的写成 `Q*`，与摘要「放行判断」挂钩 |
| 签字 | 角色 ｜ 结论 ｜ 备注 | 评审人（arch）先签；god 集成后确认 |

**严重级三档的处置时限**：阻断=当轮修入或明确回写责任方，否则不签发；重要=登记进回写清单并指派；建议=可择期，须写入清单以免丢失。

## 4. 模板三 · 缺陷单

**触发**：任何测试/使用中发现的缺陷。**责任人**：QA 登记与关闭，**作者修**。
**对齐既有**：字段与 `03-测试计划与用例.md` §7.1–§7.4、`04-缺陷台账.md` §2/§3 完全一致；**台账正文写 `04`，本模板是填单格式**（一条缺陷 = 台账一行 + 下面这段详情）。

### 4.1 必填字段（缺任一项 QA 打回）

## 6. 通用规则

1. **单点归属**：每份记录一个责任人（§1 表）；结论变更走对应关卡（设计变更回 G1，排期变更回 G2），不在记录里私下改。
2. **脱敏**：`docs/05-过程记录/` 属公开仓库内容，设备地址一律占位符（`<TV-LAN-IP>`），**不写**内网 IP、MAC、序列号、口令；证据原始文件不入库，只留文件名与结论（`docs/03` §11、`docs/01` §4.3 R8）。
3. **判据要落数**：凡结论必须落到事件码或指标数字，禁止"很快/正常/大致没问题"。
4. **提交**：规范 `feat/fix/docs/refactor/test/chore(scope): subject`；每阶段至少一次提交；分支内提交，**不 push 远端**（god 为唯一集成者）。
5. **看板**：`hive/tasks.json` 由 god 维护；temp/agent 只**提案**卡状态，不直接改。
