## 0. 怎么用

本文件干两件事：**给 `docs/05-过程记录/` 建目录**（§1），以及**给四个必须留痕的关卡各发一张可直接照填的模板**（§2–§5）。字段不是新发明——每一张都和仓库里已写好的记录对齐（模板出处见各节「对齐既有」一行），照填即可，不必自造格式。

| 角色 | 用法 |
|---|---|
| PM | 维护 §1 索引；阶段末按 `01-WBS与排期.md` §13 更新估时/风险/里程碑 |

**编号口径**（沿用 `01-WBS与排期.md` §1）：`F1–F12` 需求、`S1–S6` Spike 判据、`L1–L8` 日志验收、`P0–P3`/`G0–G8` 阶段与关卡。角色代号 `god / PM / arch / dev-A / dev-B / QA`。

## 2. 模板一 · 设计评审记录

**触发**：G1 或任何一次设计/接口评审。**责任人**：arch。**对齐既有**：`02-设计评审记录.md`（`R-*` 意见 / `W-*` 回写 / `Q-*` 开放问题三套编号）。

### 2.1 字段说明

| 字段 | 取值 / 格式 | 说明 |
|---|---|---|
| 评审对象 | 文档名 + **章节号** | 精确到 `§4.3`，不写整篇 |
| 严重级 | **阻断 / 重要 / 建议** | 阻断=不修不能开工；重要=不挡 P0 但须在对应阶段前闭环；建议=择期 |
| 意见 | 问题 / 风险 + 依据 | 依据要能落到实测数据或文档原文，不写"感觉" |
| 结论 | 该条意见的**处置结论** | 已有改动写"已修：<目标章节>"；未修的写"回写：<责任方>" |
| 回写清单 | 目标文档 · 章节 ｜ 回写内容 ｜ 责任方 ｜ 状态 | 状态用 `✅ 已改` / `⏳ 待执行` / `⏳ 待 god 答复` |
| 开放问题 | 问题 ｜ 推荐 ｜ 待谁拍板 | 需 god 拍板的写成 `Q*`，与摘要「放行判断」挂钩 |
| 签字 | 角色 ｜ 结论 ｜ 备注 | 评审人（arch）先签；god 集成后确认 |

**严重级三档的处置时限**：阻断=当轮修入或明确回写责任方，否则不签发；重要=登记进回写清单并指派；建议=可择期，须写入清单以免丢失。

## 4. 模板三 · 缺陷单

**触发**：任何测试/使用中发现的缺陷。**责任人**：QA 登记与关闭，**作者修**。
**对齐既有**：字段与 `03-测试计划与用例.md` §7.1–§7.4、`04-缺陷台账.md` §2/§3 完全一致；**台账正文写 `04`，本模板是填单格式**（一条缺陷 = 台账一行 + 下面这段详情）。

### 4.1 必填字段（缺任一项 QA 打回）

| 字段 | 要求 |
|---|---|
| **版本号** | `versionName` / `versionCode` / `git rev-parse --short HEAD` / APK SHA256 前 8 位（证据 E1） |
| **事件码** | 关键路径的事件码，取值见 `docs/03` **§3.3**（如 `PLAY_PREPARE_FAIL`），附关键 `fields` |
| **logcat / 截图证据** | `logcat -v threadtime` 原文片段或 JSONL 会话（E2）；截图/录屏文件名与路径（E3） |
| **复现率** | 必现 / 高（≥7/10）/ 中（3–6/10）/ 低（≤2/10）/ 单次（需附现场日志） |
| **修复人** | 提交修复的作者（**不是发现人**） |
| **验证人** | QA（**只有 QA 能写「已关闭」**） |
| 其余 | 设备（机型/Android 版本/ABI/`mWakefulness`）、关联用例 `TC-xxx-xx` 与需求 `F*`、前置与最小复现步骤、实际/预期、严重级 S1–S5 |

**严重级判据**：S1 阻塞（装不上/起不来/崩溃循环/主流程不可用/数据损坏；**任何脱敏泄露一律 S1**）· S2 严重（有绕行的核心失效，如 ≥30% 频道起播失败）· S3 一般 · S4 轻微 · S5 建议。**自动升级**：崩溃/ANR → ≥S2；构建或安装失败 → S1；CI 红 → S2；同一用例重开 ≥2 次 → 升一级并回 G4 复盘。

### 4.2 模板（照填）

- **设备**：<机型> / Android <版本> / <ABI> / mWakefulness=<值>
- **用例**：<TC-xxx-xx>（关联需求 <F*>、验收指标 <S*/L*>）
- **前置与步骤**：1) … 2) … 3) …（可复跑的最小步骤）
- **实际结果**：
- **预期结果**：
- **复现率**：<必现/高/中/低/单次>（x/10）
- **证据（必填）**：
  - 事件码：`<EVENT_CODE>`（附关键 fields）

## 6. 通用规则

1. **单点归属**：每份记录一个责任人（§1 表）；结论变更走对应关卡（设计变更回 G1，排期变更回 G2），不在记录里私下改。
2. **脱敏**：`docs/05-过程记录/` 属公开仓库内容，设备地址一律占位符（`<TV-LAN-IP>`），**不写**内网 IP、MAC、序列号、口令；证据原始文件不入库，只留文件名与结论（`docs/03` §11、`docs/01` §4.3 R8）。
3. **判据要落数**：凡结论必须落到事件码或指标数字，禁止"很快/正常/大致没问题"。
4. **提交**：规范 `feat/fix/docs/refactor/test/chore(scope): subject`；每阶段至少一次提交；分支内提交，**不 push 远端**（god 为唯一集成者）。
5. **看板**：`hive/tasks.json` 由 god 维护；temp/agent 只**提案**卡状态，不直接改。
