## 0. 结论（先给答案）

**这套环境是一台跑 fake-IP 透明代理的网关**：网段内的 DNS 被透明劫持（换解析器也没用）→ 所有域名解析到 `198.18.0.0/15` → 网关 TUN 层按 SNI 把流量隧道转发到真实源，**不做 TLS 解密**。App 侧没有代理寄存器，只如实上报收到的状态码。

三个必须更正的既有说法（都是本轮新实测）：

1. **对 `198.18.0.0/15` 做端口探测没有信息量**。连**未分配**的 `198.18.99.99` 上，`1 / 9 / 22 / 80 / 443 / 12345 / 49152` 也全部「OPEN」（同端口 5 发 5 通）⇒ `connect()` 是本地隧道层答应下来的，**不代表远端有服务**。
2. **「网段挡 ICMP」不成立**。网关答 ICMP（1.2 ms）、`1.1.1.1` 答 ICMP（70 ms）；不答的是**电视自己**（设备行为）和 fake-IP 段（隧道行为）。
3. **god 记录的「按端口区别对待」实测的是电视自己的服务**。`5555/6466/7100/49152` 只在那台电视上通；**同一组端口在网关上全关** ⇒ 那是电视的服务集（ADB 等），不是网段的端口策略。

三方向建议的要点（细节在 §3）：源筛选要把「本网被闸门拦」与「源真死」分开；请求头指纹最便宜、可直接 A/B；分流或直连必须先做完 A/B 再动路由，否则出口 IP 一变可能更糟。

## 1. 事实记录（本机只读实测）

### 1.1 探测条件

| 项 | 值 |
|---|---|
| 时间 | 2026-09-22（与 god 当日实测同一天、同一条网段） |
| 执行机 | 开发 Mac `<MAC-LAN-IP>`，有线 `en0`，默认网关 `<LAN-GATEWAY>` |
| 手段 | `dig` / `nc` / `curl` / `ping` / `scutil` / `ifconfig` / `arp`，**全部只读**，不改任何配置 |
| 未使用 | 电视（`<TV-LAN-IP>` 只在 ARP 表里确认在线，未做任何设备侧操作） |

### 1.2 DNS 与 fake-IP 行为

| 域名（举例） | 解析结果 | 形态 |
|---|---|---|
| `play.kankanlive.com` | `198.18.7.43` | fake-IP |
| `hlsztemgsplive.miguvideo.com` | `198.18.5.101` | fake-IP |
| `lxfile.lxxcb.cn` | `198.18.7.44` | fake-IP |
| `live.jlntv.cn` | `198.18.7.45` | fake-IP |
| **`www.apple.com`（对照）** | `198.18.0.163` | fake-IP |
| **`github.com`（对照）** | `198.18.0.202` | fake-IP |

两个决定性对照：

| 实验 | 结果 | 含义 |
|---|---|---|
| `dig @<LAN-GATEWAY> <域名>` vs `dig @1.1.1.1 <域名>` | **同一域名两个解析器给同一个 fake-IP** | 53 端口被透明劫持；**换 DNS 不能绕开** |
| 非 IPTV 域名（apple / github） | 同样落 `198.18.0.0/15` | fake-IP 是**全网段**行为，不是只针对 IPTV |

fake-IP 分配是**粘性**的（31 号 E1 已证：扰动 500 个随机域名后四条 URL 映射不变）；本机系统代理为空（`scutil --proxy` 无 HTTP/HTTPS/SOCKS，仅 `*.local`/`169.254/16` 例外），也无 `*_proxy` 环境变量 ⇒ **本机不是靠手工代理配置走到这条路上的，是网络层劫持**。

### 1.3 ICMP 与可达性矩阵

**ICMP**（`ping -c 2`）：

| 目标 | 结果 | 说明 |
|---|---|---|
| `<LAN-GATEWAY>` | 0% 丢包，1.2 ms | 网段不封 ICMP |
| `1.1.1.1` | 0% 丢包，70 ms | 网段不封 ICMP |
| `<TV-LAN-IP>`（电视） | **100% 丢包** | 电视不答 ICMP（ARP 在线） |
| `198.18.7.43`（fake-IP） | **100% 丢包** | 隧道层不答 ICMP |

**TCP 端口**（`nc -z`，同一分钟）：

| 目标 | 5555 | 6466 | 7100 | 49152 | 9 | 12345 | 80/443 | 7890 | 9090 |
|---|---|---|---|---|---|---|---|---|---|
| `<LAN-GATEWAY>` | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✓ | ✓ | ✓ |
| `<TV-LAN-IP>`（电视） | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ | — | — | — |
| `198.18.x.y`（**任意** fake-IP，含未分配地址） | ✓ | ✓ | ✓ | ✓ | **✓** | **✓** | ✓ | — | — |

第三行是关键：**在任何 `198.18.x.y` 上，连 `:1` 都是「OPEN」**（`198.18.99.99:1`、`:9`、`:12345`、`198.18.0.5:22` 全部通过；`198.18.99.99:80` 打 HTTP 得到 `curl: (52) Empty reply from server`）。延迟量级也吻合：fake-IP `connect` **2.9 ms**（LAN 速度），而真实 WAN `1.1.1.1` 往返 **70 ms**。

⇒ 结论：**对 `198.18.0.0/15` 的端口探测既不可复现也无信息量**（偶发一次 `closed`，其余全通）。要把「电视是否在线」问清楚，只能用 ARP（同网段）或直接 `adb connect <TV-LAN-IP>:5555`。

### 1.4 代理与中间件痕迹

| 探针 | 响应 | 读法 |
|---|---|---|
| `curl http://<LAN-GATEWAY>:7890/` | `HTTP/1.1 407 Proxy Authentication Required` + `Proxy-Authenticate: Basic` | 网关上有一条**需认证的 HTTP 转发代理**（31 号 E1，本轮复现） |
| `curl http://<LAN-GATEWAY>:9090/`、`/version` | `401 Unauthorized`、`Content-Type: application/json`、`Vary: Origin`、body `{"message":"Unauthorized"}` | 一个**带鉴权的管理 API**；端口与响应形状符合常见 fake-IP 透明代理客户端（Clash/mihomo 家族）的外部控制器默认配置，`198.18.0.0/15` 也正是其默认 fake-ip-range ⇒ 环境形态判断的来源 |
| `curl -v https://www.apple.com/` | 证书是真证书：`issuer: Apple Public EV Server RSA CA 1 - G1` | **TLS 未被中间人解密**，是 SNI 隧道转发 |
| `curl -v https://play.kankanlive.com/` | 证书是真证书：`issuer: DigiCert ...`，`subject: ... O=甘肃云新媒体集团 ... CN=*.kankanlive.com` | 同上；IPTV 域名也没被替换证书 |
| `curl https://1.0.0.1/`、`https://8.8.8.8/`、`https://9.9.9.9/` | 全部 `code=000`，约 5 s 失败 | **纯 IP 目标的 HTTPS 不被承载** |
| `curl http://1.1.1.1/` | `301` | 同一 IP 的**明文 HTTP 可通** ⇒ 隧道只承载「有域名」的流 |

**非常规状态码在本轮再次出现**（同一台主机、隔几小时）：

| 目标 | 31 号当时 | 本轮 |
|---|---|---|
| `hlsztemgsplive.miguvideo.com:8080`（夹具其中一条） | `605`（`Server: CDN_6C381C27`） | **`403`** |
| `play.kankanlive.com`（经 fake-IP） | `200` | **`500`**，`Server: Server` |

⇒ 正是「**按指纹、概率性回非常规码**」的既有结论（31 号 H4/E3：同 URL `curl` 15 发 `200×9 / 418×6`、`Server: CloudWAF`；ExoPlayerLib 指纹 15/15 通过）。**「裸请求 200」不能当「源正常」的证据，「裸请求 403/605」也不能单独当「源坏了」的证据。**

## 2. 链路定位

### 2.1 一跳一跳

```
[电视 App]
  │ ① 系统 DNS 查询（电视与 Mac 同一条 LAN，同一台网关做解析器）
  ▼
[家庭网关 <LAN-GATEWAY>]  ──② 返回 fake-IP 198.18.x.y（对任意域名、任意解析器都这样）
  │ ③ TCP/TLS 目标是 198.18.x.y；connect 由本地 TUN 层接受（所以端口探测全通）
  │ ④ 按 SNI/域名选出口，隧道转发；TLS 端到端，不解密
  ▼
[上游出口 / 代理集群]  ──⑤ 可能带认证代理（7890 上 407 已证存在这样一条）
  ▼
[真实源站 + 源侧 CDN/WAF 反盗链闸门]  ──⑥ 按指纹/概率回 200 / 403 / 418 / 605 …
  │ ⑦ 状态码原路回传 → App 如实上报（App 侧无 605 字面量，rg 全仓 0 命中）
  ▼
[App 分类与 UI]
```

| 跳 | 谁在做 | 做什么 | 证据 |
|---|---|---|---|
| DNS | **网关**（不是 App、不是电视） | 透明劫持 53，返回 fake-IP；换解析器无效 | §1.2 两行对照 |
| fake-IP 与 connect | **网关 TUN 层** | 本地接受任意 `198.18.x.y:任意端口` 的 connect | §1.3 第三行（含未分配地址） |
| 出口与认证代理 | 网关/上游 | 存在一条 Basic 认证的 HTTP 转发代理 | §1.4 `407` |
| 源侧拦截/改写 | **源站/CDN/WAF** | 按客户端指纹与概率回非常规码 | §1.4 表格、31 号 E3 |
| 隧道内失败 | 网关自身 | 无法处理该流时给通用错（本轮见 `500`，`Server: Server`） | §1.4 |
| TLS | **无人改写** | 端到端真证书 | §1.4 两条证书 |
| App | 播放/刷新栈 | 只上报 `InvalidResponseCodeException.responseCode` | 31 号 E7 |

### 2.2 环境固有 vs 可能可调

| 现象 | 判定 | 理由 |
|---|---|---|
| DNS 劫持 + fake-IP + 隧道转发 | **环境固有**（App 与电视都改不了） | 网络层实现，本机无任何代理配置仍如此 |
| 对 fake-IP 的端口探测无信息量 | **固有**（且是探测方法的错） | 未分配地址也全通 |
| 纯 IP 目标的 HTTPS 不通 | **固有**（对含纯 IP 直链源的清单有直接影响） | §1.4 三 IP 全 `000`；31 号里 `92.50.128.180` 那类源 TTFB 470–720 ms，是**绕过隧道直连**的量级 |
| 源侧 403/418/605 概率性拦截 | **源侧固有，但指纹可试** | 31 号 E3：同 URL 不同 UA 通过率不同（curl 命中 418，ExoPlayerLib 指纹 15/15 通过） |
| `7890` 认证代理、`9090` 管理面 | **可能可调**（需管理权限） | 配置在网关上，不在 App |
| 分流规则（哪个域名直连/走代理） | **可能可调**（需管理权限） | 同上 |
| 电视不答 ICMP | **设备行为**，与网段无关 | 网关与 `1.1.1.1` 都答 ICMP |

### 2.3 无法从本机确认，需人工或换网验证

| 待定项 | 为什么本机钉不死 | 建议的确认方式 |
|---|---|---|
| 网关是谁在跑、`9090` 管理面归谁、分流规则内容 | 需要管理权限；本机只有 401 | 问人工：这台 `iLabRouter` 是谁维护的 |
| 电视上是否另有系统代理 / VPN / uid 级代理（把 App 的流量与 `adb shell` 的分开） | 需要电视；本轮禁用电视 | 电视恢复后 `adb shell settings get global http_proxy`、`dumpsys connectivity`、`ip rule`（只读，31 号 §5 已写好清单） |
| 「换一条没有 fake-IP 的网络」后同一批源是否恢复 | 需要电视 + 热点 | 手机热点对照复跑（31 号 §4 已写好判据） |
| 直连后出口 IP 变化是否反而被反盗链拦 | 需要改路由 | 先做 §3.2 的指纹 A/B，再决定是否改路由 |

## 3. 三方向建议

> 每条都标 **成本 / 收益 / 风险**，并注明「能否在 App 内做」。三方向彼此独立，可以只做其中一条。

### 3.1 方向一 · 源筛选策略（把「本网不可达」与「源质量差」分开）

**问题**：现在「本网被闸门拦」和「源真的死了」在数据里是同一个形状——一次浅探/深探失败。25 号 §2.1 的方式 B 是**人工口径补丁**，管线本身还没有这个区分。

**建议**：在刷新管线里加一个**独立的可达性维度**，而不是复用质量分：

1. 失败分类保持现状（`HTTP_CLIENT` / `HTTP_SERVER` / `NET_UNREACHABLE`）；
2. 新增一层**环境闸门判定**：`httpStatus ∈ {403, 418, 451, 511, 605}` 或「同类源在同一分钟内**同址**也失败」⇒ 打 `env_gated` 标记，**不参与永久降权**；
3. 该标记只影响**本网的排序/剔除**（例如本网起播率的分母），不写进源的长期 `score`；换网后自动失效；
4. 诊断/日志里要能一眼看出某条失败是 `env_gated` 还是 `dead`。

| 成本 | 收益 | 风险 |
|---|---|---|
| 小：一条判定 + 一个持久化字段（或一个内存标记） | 起播率分母干净；不会把好源永久降权（`PERMANENT` 目前对 418 是即刻生效的）；下一次专项不用再靠人工口径 | 误把「真死源」判成闸门源 → 需要判据保守（建议「同址同分钟 ≥2 条」才升级为环境判定）；**不要**和「源质量分」混在一个字段里 |

### 3.2 方向二 · 请求头指纹（最便宜、可立即 A/B）

**问题**：默认 UA 是 Chrome/Android 桌面串（`DEFAULT_USER_AGENT`，`core/network/.../Http.kt`），播放侧是 `ExoPlayerLib/…`；而闸门**确实按指纹区别对待**（31 号 E3）。`Referer` 只在源清单带 `#EXTVLCOPT:http-referrer` 时才发，绝大多数源是**裸请求**。

**A/B 方案（给 QA 或下一轮 dev 一轮跑完）**：取 5–8 条**已知在本网失败**的源 + 2 条已知成功的对照源，每个组合各打 15 发（对齐 31 号 E3 的口径）：

| 变量 | 取值 |
|---|---|
| UA | ① `ExoPlayerLib/…`（现状播放侧）② `Mozilla/5.0 (Linux; Android 12) … Chrome/120`（现状刷新侧）③ 无 UA |
| Referer | ① 不带 ② 源站首页 ③ 源清单里给的 referrer |
| 记录 | 状态码分布、TTFB、`Server` 头 |

判据：某组合 2xx 率显著高于现状且 TTFB 没有变差 ⇒ 把该组合写回源（`core:source` 已有 `userAgent`/`referrer` 字段，`M3uParser` 已解析 `#EXTVLCOPT:http-user-agent|http-referrer`，**不需要改播放器**）。

| 成本 | 收益 | 风险 |
|---|---|---|
| 小：一轮对照实验，成功则只改源清单或解析默认值 | 直接可能救回 605/418 那一批；结论可复用到所有源 | 指纹是**概率性**的（15 发里 6 个 418），单轮结论必须带样本量与分布，不能只看「一把通了」 |

### 3.3 方向三 · 网络分流或直连（要动路由，最小改动 + 可回退）

**问题**：现在 IPTV 源在隧道里走，出口 IP 与线路都由网关决定；而纯 IP 直链源本来就走另一条路（量级差 20 倍）。

**最小改动方案**（按从小到大排序，每步都可回退）：

1. **先验证「换网有没有用」**：电视接手机热点（无 fake-IP），同一批源复跑（31 号 §4 判据）。成本最低、信息量最大，且不改任何配置。
2. **在网关上给「电视 IP + IPTV 域名」加一条直连（DIRECT）规则**：一条规则，删除即回退；观察是否恢复。风险：出口 IP 变化可能**触发**反盗链。
3. **给电视单独一条不套 fake-IP 的策略/线路**：改动更大，回退要点同样是一条规则。
4. **（不建议现在做）给 App 配置走 `7890` 认证代理**：会引入凭据管理，且把环境依赖写进 App，优先级最低。

| 成本 | 收益 | 风险 |
|---|---|---|
| 中：需要网关管理权限 | 可能一次性解决整批源的不可达 | 直连后出口 IP/线路改变 ⇒ 可能反而被源侧拦；因此**必须先做 3.2 的指纹 A/B**，否则「改了路由还是不通用」无法归因；回退要真的可执行（保留原规则文本，一条命令恢复） |

## 4. 给 App 的可落地项（**建议，不实现**）

## B.4 对 App 的影响再评估：`env_gated` 是否仍必要

**结论：仍必要，判据不用改。**

- **闸门码仍出现**：`403`（多处 CDN/WAF）与 `418`（CloudWAF，按 UA）在新网络下都在。`403 < 500` 且非 `429/408` ⇒ 现有代码落 `HTTP_CLIENT` → **不可重试 + `StreamDemotion.PERMANENT` 立即永久降权**（沿用 §1.5 与 ⑨）。这正是 `env_gated` 要拦的误判。
- **触发条件**（新网络下实测）：① 源侧 **WAF/CDN 按客户端指纹**回非常规码（`lxfile` + `curl` UA → `418`，`Server: CloudWAF`）；② 源侧**按 token/路径有效性**回闸门码（miguvideo CDN 无有效 token → `403`）。
- **判据集合 `{403,418,451,511,605}` 无需修改**：`403`/`418` 已足以触发；`605` 本轮未再出现但它仍属该 CDN 家族，留着不增成本。
- **一个可调点**：新网络下 App 的两种 UA 在已测源上都是 `200`，说明「App 直接吃到 418」的概率可能比 `curl` 指纹低——但这是**逐源**行为，**不能据此撤销 `env_gated`**；保留它只是**标记**，不写长期 `score`，代价小、收益是分母干净。
- **`env_gated` 的实现位置与字段口径不变**（§3.1）：新增独立可达性判定，不并入源质量分，不永久降权。
