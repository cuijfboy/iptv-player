`tools/snapshot/probe.sh` 驱动**探针夹具** `ilab.iptv.player.spike/HoldProbeActivity`（本卡新加，

每 URL 一行写进设备上的 `snapN.jsonl`（随测随写，进程被打断也不丢已完成的部分）。

另有 **34 条**旧快照条目在上一轮电视实测里首帧就 >3000 ms（属于「慢源」），本轮按新判据直接出局。

### 2.3 中间事故：电视掉线 26 分钟，与「探针表面还在跑」

跑 `snap1` 到第 69 条时（00:42:18 起）**电视从局域网消失**：`adb connect` 超时、`arp` 显示 `(incomplete)`、电视 ping 不通；网关正常 ⇒ 是电视侧下线（god 侧 `WAKE-2` 已挂人工 ASK，WOL 无效；01:08:40 电视自行恢复）。

**教训（被写进夹具）**：掉线期间探针进程仍在电视上跑，
① 掉线窗口内的样本全部 `no_first_frame`（网络没了，结果无意义）；
② 电视待机把 Surface 撕掉后，恢复时**解码器不再出帧**——此后所有样本都是假阴性（`videoFormat` 能解析出 1280x720，却永远等不到首帧），这是「网络已好但结果全错」的陷阱。

处置：`snap1` 只保留 **1..63**；用重开进程的 `snap2` 重测 **61..189**；同时给夹具补了两条自愈/取证能力（本卡新增，属夹具不属产品）：

- `surfaceCreated` 检测到「Surface 曾经丢失」⇒ **重建 player 并重跑当前样本**（`HOLD_SURFACE_REBUILD`）；
- 独立看门狗线程：单样本超过 `首帧超时 + hold + 60 s` 直接判 `watchdog_stuck`（`Handler` 在设备待机时会停摆，实测第 80 条拖了 23 分钟才回收）。

### 2.4 探针成本

约 **35 s/条**（达标样本要跑满 30 s hold；失败样本只花到 3 s 首帧超时）。本轮 245 条 ≈ 2.5 h 电视机时，其中约 26 min 被掉线事故浪费。探针跑在电视上，**跑动时不要动电视**（页面/按键会打断）。

## 4. 流程工具化（`tools/snapshot/`）

```
tools/snapshot/
  README.md          判据、三个脚本怎么跑、成本、探针夹具是什么
  probe.sh           构建并安装探针夹具 → 推候选清单 → 电视逐条起播 + hold → 拉回结果
  build_snapshot.py  按候选顺序保留 pass 条目 → 写 channels.m3u + PROVENANCE.md（过滤私网/凭据键/去重）
  verify.sh          静态校验：≥150、一条频道一条流、每行元数据、tvg-chno 连续、分组覆盖、
                     无内网/`.invalid`/凭据键、`name_key` 唯一、PROVENANCE 计数与文件一致
```

一条命令：`probe.sh --candidates … --out /tmp/p` → `build_snapshot.py --probe /tmp/p/probe.jsonl …` → `verify.sh`（细节见 `README.md`）。`verify.sh` 在本卡跑出 **全部 ok**：

```
ok  one-stream-per-channel   extinf=154 url=154
ok  channels>=150            channels=154
ok  row-metadata / display-name-present / tvg-chno-1..N-contiguous
ok  group-covered:央视 / 卫视 / 地方/其他
ok  no-private-address / no-synthetic-invalid-host / no-credential-query-key / name-key-unique
ok  provenance-channel-count / provenance-group-counts
```

`build_snapshot.py` 也是**判据的单一事实源**：`PROVENANCE.md` 里写的阈值就是它跑的参数，脚本不可能生成一份「声称了没测过的判据」的快照。
