## 2. 根因机制与证据

### 2.1 机制（一句话）

`channel.epg_channel_id` 是**多对一**（多台频道可共用一个 guide 频道：标清/高清/同名异构台共用一份节目单是常态），而网格回映射写成了**一对一**：

```kotlin
// 修复前 — EpgGridViewModel.load()
val channelIdByEpgId = request.channels
    .filter { it.epgChannelId != null && it.id in wanted }
    .associate { it.epgChannelId!! to it.id }        // ← 同页后来者覆盖前者
…
programmes.groupBy { channelIdByEpgId[it.epgChannelId] }
    .mapNotNull { (channelId, rows) -> channelId?.let { it to rows } }
```

被覆盖掉的那些频道：`programmesByChannel` 里**没有它们的键**，但 `loadedChannelIds = wanted` 照旧包含它们 ⇒ `EpgGridView.submit` 取到 `emptyList()`（不是 `null`）⇒ `programmesToRowInput(..., LOADED, empty index)` ⇒ 整行画「无节目」占位。**面板读的是频道自己的 `epg_channel_id`，不做折叠，所以它照旧 > 0。**

### 2.2 页切分证据（为什么点名频道换了人）

采样打印了每个持有者所在的**行号 / 页号 / 页内位置**（行序 = 网格排序 `(group_key, sort_order, id)`）：

```
holder-pages: CCTV-1.hk = CCTV1#1@row571/page17[27], CCTV-1综合#19@row589/page18[13],
                            CCTV1 高清#60@row630/page19[22], CCTV1 标清#72@row642/page20[2]
              545944     = CCTV-12社会与法#31@row601/page18[25], 央视社会与法#55@row625/page19[17],
                            CCTV12 高清#68@row638/page19[30]
              561322     = CCTV13#14@row584/page18[8], CCTV-13新闻#32@row602/page18[26],
                            CCTV13 高清#69@row639/page19[31]
```

- `CCTV-1.hk` 的四个持有者**各占一页**（17/18/19/20）⇒ 本夹具上 `#1` 不会被折叠（`spotlight` 里 `hop=panel=9`）。
- `545944` 的 `#55` 与 `#68` **同在第 19 页** ⇒ 丢的是 `#55`（`collapseLostRows` 里可见）。
- `561322` 的 `#14` 与 `#32` **同在第 18 页** ⇒ 丢的是 `#14`。

QA 那台是 571 台的 `validated.m3u`（52 号 §2.3 已记录 `matched=141/571`），行序与页切分都不相同——`#1`、`#31` 在那边与各自的后来持有者落进同一页，于是空的是它们。**这解释了「同页对照组有块、点名行却空」而不需要假设任何渲染问题。**

### 3.1 落点

| 文件 | 改动 |
|---|---|
| `core/domain/src/main/kotlin/ilab/iptv/player/core/domain/epg/EpgChannelHop.kt` | **新增**（纯 Kotlin）：`programmesByChannel(pageChannelIds, channels, programmes)`，`groupBy { epgChannelId → [channelId] }` 的多对多 hop；不在页内的频道、没有绑定的频道、guide 未提及的频道都不出现 |

| `feature/epg/build.gradle.kts` | 仅加测试依赖 `testImplementation(libs.kotlinx.coroutines.test)`（与 `:feature:wizard` 同款） |

为什么把 hop 抽到 `:core:domain`：它是**两个标识之间的语义**（docs/02 §5.1），`RoomEpgRepository` 负责去的方向、调用方负责回来的方向，两侧都不该各写一份；抽出来后 `:core:data` 的采样、`:core:domain` 的单测和网格用的是**同一份**实现（§1.2 的 `hop*` 列就是它跑出来的）。

### 3.2 影响面与迁移

- **不做迁移**：没有任何 schema / 数据变化；既有的 `epg_channel_id` 绑定照旧。修复只影响**读**。
- **画面变化**：共用同一 guide id 的频道（夹具里 49 个 id / 120 台）现在**每一台都画出该 guide 的节目**。这是正确语义：它们本来就是同一份节目单；修复前只有最后一行有、其余行骗人。
- **性能**：同页共用 guide 的频道会把同一批 `Programme` 对象引用多挂几次（对象不复制），32 行页内最多 5 份引用；`ProgrammeIndex` 仍按行各建一次（与修复前对「有节目的行」做的事完全一样，只是行数变多）。S3 的虚拟化与 60 fps 口径未受影响（`GridPerfTest`/`GridPerf` 未改）。
- **不改匹配算法**：共用 guide id 不是匹配层的错（一个 guide 频道服务标清/高清/同名异构台是常态，46 号卡的 EPG-BIND 择优仍是逐台进行）；本轮**一行匹配层代码都没动**。

## 5. QA 两条观察项处置

### 5.1 观察项 ①：隐藏全部 658 后「页头 `频道 275/分组 2/流 276` 而列表空白、向导侧读到 0」

**与本次根因不同源**（没有任何 EPG 参与）。代码事实：

- 页头与列表**来自同一个状态对象**（`ChannelListUiState.channelCount = list.size`，行也由同一个 `list` 构建，`ChannelListViewModel.uiState`）⇒「275」与「空列表」**不可能**同时是最终状态，只可能是**渲染时刻的状态漂移**。向导读到 0 也与数据库一致（658 台全部 `hidden=1`），即**数据层是对的，分歧在浏览页的那一帧**。
- 漂移的来源有具体嫌疑：`ChannelListViewModel.batchSetHidden()` 是 `ids.forEach { repository.setHidden(it, hidden) }` —— **658 次独立写、658 次列表流重发**（Room 每次写都触发失效重查）。页头/帧统计在重发的中间态渲染（275 台还没隐藏完、组数已缩到 2）就会被读成「275」，而列表那一帧已是空。

**建议**：单开一张卡（`BUG-NEW` 或 QA 复跑项），真机复跑时**在批量隐藏结束后再读一次页头**（隔 1–2 s），并在 `batchSetHidden` 前后各打一条日志；若确认是中间态渲染，最小修法是给批量隐藏加一条仓储级批写（一次事务、一次重发）。**本卡不动它**（属于 `:feature:channels` + `ChannelRepository` 端口变更，超出本卡边界）。

### 5.2 观察项 ②：`已选 0 台` 时批量弹窗的「全选」按 OK/点击都无效

**与本次根因不同源**。代码事实（`BrowseActivity.showBatchActions()` + `ChannelListViewModel.selectAll()`）：

- 弹窗条目与动作**按下标一一对应**：`selected == 0` 时 `labels = [全选, 清空]`、`actions = [selectAll, clearSelection]`，第 0 项就是 `selectAll()`；`selectAll()` 的实现是 `manage.update { it.copy(selected = loaded.value.map { it.id }.toSet()) }`，**没有**任何 `manageActive` 之类的前置条件。
- 因此「点了没反应」只可能是两种：**(a)** 点的时候 `loaded.value` 还是空（列表流尚未发出/刚被批量操作清空）⇒ 选中的就是空集，看起来「无效」；**(b)** 选中成功了但界面读法不同（QA 读的是弹窗标题/页头的「已选 N 台」，而那一帧没刷新）。
- 需要真机区分：(a) 出错时 `loaded` 是否为空（日志：进入浏览页到打开的间隔、`BROWSE_*` 事件序）；(b) 点完「全选」后**再按一次 MENU** 看标题是「已选 658 台」还是「没有选中」。本卡拿不到电视，**不猜结论**。

**建议**：与 ① 合并成一张 `:feature:channels` 交互卡，由 QA 真机复跑取上述两条读数；若为 (a)，修法是把「全选」在 `loaded` 为空时**改成明确提示**（已有 `browse_batch_select_all_first` 文案可用），而不是静默无效。
