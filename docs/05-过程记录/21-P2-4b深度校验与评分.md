## 2. 评分表口径（docs/02 §6.1 的 100 分模型）

| 维度（rule id） | 权重 | 本包实现 | 字段来源 |
|---|---|---|---|
| 可用性 `availability` | 35 | 深探 `passed` 即得，否则 0 | `ValidationResult.passed`（Deep） |
| 稳定性 `stability` | 25 | `round(25 × stability)`；证据含 `stalled=true` 再 −10 | `StreamRepository.health()`（轮询失败率）+ 起播耗时中位数（W-S1-2） |
| 设备兼容 `device_compat` | 20 | H.264=20 / H.265=12 / AV1=4 / **未知=12**；AC3·EAC3 且 `DeviceProfile.audioPassthrough` 未列 −5；>1080p 或超设备上限 −3 | `CodecIds`（探针 vcodec/acodec）+ `DeviceProfile` |
| 画质/码率 `resolution` | 10 | ≥1080p=10 / ≥720p=8 / ≥480p=5 / 未知=0 | 探针 `w`/`h` |
| 防盗链 `anti_leech` | 5 | `stream.userAgent`/`referrer` 均为空=5；需要=3 | `stream` 行（`#EXTVLCOPT` 采集，§5.1） |
| 分片成功 `segment` | 2 | 证据 `segStatus` ∈ 2xx 得 2 | 探针分片腿 |

**三条口径决定（写清以便复核）**

1. **权重和是 97，不是 100**。§6.1 表逐项相加 = 35+25+20+10+5+2 = **97**。本包**不改权重**，而是按 §8.4 E6「总分归一化到 100」把原始和线性缩放到 0–100：`total = round(raw × 100 / 97)`，`ScoreBreakdown.byRule` 保留**原始分**（`SRC_SCORE` 逐维度上报的就是它）。→ 请 arch 要么把表改成加起来 100，要么在 §6.1 写明「归一化」这一步（§10.2 开放项 1）。
2. **未知编码给 12（中性）**：§6.1 只写了 H.264/H.265/AV1 三档，没说「探不出编码」怎么算。给 0 会因缺元数据误杀，给 20 会白送满分，故取中间值，并在 `SRC_SCORE.vcodec=null` 时看得出原因。
3. **阈值 55 用在备胎上**：§6.1 原文是「最高分为主、次高分（≥55）为备胎」，所以**主源不设 55 门槛**（弱但可播放的流仍当主源，对应 §8.3「仍可尝试播放」），备胎必须 ≥55；「最多 3 条」= 1 主 + 2 备（`SelectionRules.MAX_STREAMS_PER_CHANNEL`）。

**稳定性因子（`Stability.of(health, startCostMedianMs)`）**：`1 − 失败率 − 尾部扣分`，下限 0。起播耗时 >3 s 起线性扣、6 s 及以上扣满 **0.20**（W-S1-2 的「降权」上限，禁止硬编码源名/地区）。`attempts=0`（从未探测）取**中性 1.0**——新流不该因为「还没历史」被判低分。

> ⚠️ **该因子的起播耗时输入目前是空的**：`:core:domain` 的 `StreamRepository` 端口（§4.3）**没有**读 `play_history.start_cost_ms` 的方法，刷新期拿不到历史起播中位数，所以管线传 `null`（尾部扣分 0）。函数本身已实现并被单测覆盖（`StabilityTest`），**接线需要 arch 给一个端口**（§10.2 开放项 2）。

## 3. 深度校验（第二阶段）

`DeepProbeValidator`（`stage = DEEP`，`order = 20`，与浅校验同走 `Set<StreamValidator>` 的短路链）：

1. `GET` 流地址（上限 `deepFirstBytes`）→ 这本身就是直连 TS 流的「取到字节」证据；
2. 若响应体是 HLS 清单：**master → 第一个变体 → media 清单 → 直播边沿分片（末片，失败再试首片）**，取到分片 2xx + 有 body 即通过（「能拉到分片」）；
3. 读清单**声明**的编码/分辨率（`#EXT-X-STREAM-INF:CODECS`/`RESOLUTION`）；
4. 若绑定了 `TrackProbe`（Media3 真解码），用它的读数覆盖 2/3 并标 `codecSource="probe"`。

**事件证据键（`VAL_DEEP_OK` / `VAL_DEEP_FAIL` 的 fields，也是 `DeepEvidence` 的契约）**：`phase`（`playlist`/`variant`/`segment`/`edge`/`first`/`direct`/`unsupported`）、`status`、`segStatus`、`segBytes`、`segments`、`variant`、`vcodec`、`acodec`、`w`、`h`、`codecSource`（`declared`/`probe`/`unknown`）、`ms`、`timeoutMs`、`failure`（`FailureClass`）。

**诚实边界**

- **不做长时间播放**（派单要求）：只拉到分片字节就结束，不建渲染管线、不等首帧；
- **非 HTTP 协议**（`rtsp`/`rtmp`/`udp`）深探做不了 → 与浅校验一致地**如实失败**并标 `phase=unsupported`，不像「源已死」那样归类；
- **真解码（Media3 解出轨道）留设备轮**：本轮未绑 `TrackProbe`（`:core:source` 不能依赖 `:core:player`，§3.2 矩阵；且本轮禁用电视无法验证）。解码读数未接线时，评分用的是**清单声明值**——这一点在 `codecSource` 字段里对上游可见（§10.2 开放项 3）。

## 4. 甄选（每频道主源 + 备胎）

`DefaultStreamSelector` 只排序（不丢候选），`SelectionRules.select(ranked, verified)` 只决定「谁进、谁留」：

- `verified` = 本次深探通过，**或**该流健康度仍在 TTL 内（沿用上次结论）；浅校验失败、深探失败一律不可用；
- 主源 = 排序后第一个可用流；备胎 = 其后 `score ≥ 55` 的最多 2 条；合计最多 3 条；
- **不删除**：没被选中的流保留行并置 `disabled = true`（`SRC_SELECT.dropped` 报数）；
- **无可用流的频道保留可见**：频道行不动（不删），其全部流 `disabled = true`，`SRC_SELECT.unavailable=true` + `SRC_REFRESH_DONE.unavailable` 计数。

> ⚠️ **「标记不可用」落在流上，不在频道上**：§5.1 的 `channel` 表**没有**可用性列（§8.3 的「频道标记 ⚠️」是 UI 表达）。所以本轮的可用性信号是「该频道所有流 `disabled`」+ 事件字段；若要在列表上直接渲染 ⚠️，需要 arch 补一个频道级字段或让 UI 从流派生（§10.2 开放项 4）。

## 5. 增量 / 断点 / 预算 / 取消 / 播放避让

| 机制 | 本轮行为 |
|---|---|
| 增量 TTL | 健康 24 h / 失败 6 h（§6.1）。**新鲜流沿用已落库分数**，不重算——避免两次运行分数漂移；重算只在本次真正深探过时发生 |
| 断点续跑 | 浅校验结果即时 `recordOutcome`（P2-4a）；深探结论由**收尾 upsert 单点写入**（`score`/`disabled`/编码/分辨率/健康戳），因此「深探失败」会清掉浅校验留下的乐观 `lastOkAtMs`，让下一轮按 6 h 失败 TTL 复检 |
| 预算 | Deep 阶段逐条 `remaining ≥ StageProfiles.DEEP(2500 ms)` 才准入；超时优雅收尾 → `RefreshInterruption(BUDGET_EXCEEDED, DEEP)` |
| 未验证不覆盖 | 因预算没排上的流标 `PENDING`：`score`/`disabled`/健康戳**原样不动**（不拿「没探测」当作「不可用」） |
| 取消 | 所有挂起点 `ensureActive()`，`CancellationException` 原样重抛（§4.5 C5） |
| 播放避让 | `ConcurrencyGovernor.deepConcurrency()`：播放中减半（下限 1）。R7 触发点仍是 `SourceModule` 里返回常量 `false` 的 `PlaybackPrioritySignal`（P1-4 未接线，沿用 P2-4a 开放项） |

## 9. 真网抽样（本机有网，2026-09-22）

用**真实生产代码路径**（`OkHttpFetcher` + `RemotePlaylistSourceProvider` + `DeepProbeValidator`）跑 P2-4a 的聚合源，每个源取清单前 3 条频道流；结果落 `core/source/build/net-sample.txt`：

```
./gradlew --offline :core:source:testDebugUnitTest -Piptv.netSample=1 \
  --tests "ilab.iptv.player.core.source.deep.DeepProbeNetworkSampleTest"
```

**第一次（01:14，含正向对照）**

| 源 | 条目 | 结果 | 证据 |
|---|---|---|---|
| `control.bipbop`（公开 HLS 阶梯，**非**生产输入） | – | ✅ 通过 | `206`、分片 524,288 B、`video/avc`+`audio/mp4a-latm`、1280×720、`codecSource=declared`、`phase=edge`、5.3 s |
| `supprise.live`（TXT 聚合） | 303 | ✅ 3/3 通过 | `206`、各 524,288 B、`phase=edge`、0.1–0.6 s（无 `CODECS` → `codecSource=unknown`） |
| `fanmingming.itv` | 189 | ❌ `HTTP_CLIENT` | 播放列表腿 403 |
| `yang.gather` | 123 | ❌ `HTTP_CLIENT` | 播放列表腿 403 |
| `guovin.result` | 1619 | ❌ `HTTP_CLIENT` | 分片腿 404 |
| `fanmingming.index` | 94 | ❌ `HTTP_CLIENT` | 播放列表腿 404 |

**第二次（01:16，同一命令重跑）**：`control.bipbop` 仍 ✅（`206`、524,288 B、1280×720、4.2 s）；`fanmingming.itv`/`yang.gather` 仍是 403、`guovin.result` 分片 404、`fanmingming.index` 404；但 **`supprise.live` 三条这次全部 `TIMEOUT`（变体腿 ~20 s）** —— 同一批 URL 两次结果不同。

**结论**

1. 「**能拉到分片**」在真网上成立：对照流与 `supprise.live` 都拿到 2xx + 实际字节，且清单声明编码/分辨率被正确读出；
2. 失败分类有用：403/404 归 `HTTP_CLIENT`（源失效，不该重试），超时归 `TIMEOUT`（可重试），与 §4.6 的降权方向一致；
3. **公共聚合源里的频道 URL 大量不可从本机直达**（403 多为地域/防盗链），且**同一 URL 两次抽样结果会变**——这正是「按源隔离失败 + TTL 复检 + 不因一次失败删数据」在真数据上的必要性；
4. 抽样**未**把任何真实频道 URL 写进仓库（`BuiltInSources` 只含聚合地址；上文表格只留前缀）。
