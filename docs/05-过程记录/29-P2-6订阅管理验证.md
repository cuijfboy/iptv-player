## 3. 订阅 URL 管理（派单项 1）

**存储**：`source` 表（docs/02 §5.1，P2-1 建表）。字段映射：

| 表列 | 用途 |
|---|---|
| `id` | `sub:<16 位小写十六进制>`，由**规范化后的 URL** 推导（FNV-1a 64）⇒ 同一地址重复添加是幂等的，重启后 id 不变 |
| `provider_id` | 同 `id`（用户源没有独立 provider） |
| `label` / `url` / `kind` / `enabled` | 名称（留空回落域名）/ 规范化地址 / 格式提示映射的 `SourceKind` / 启用开关 |
| `last_fetch_at` / `last_result` / `entry_count` | 「最近结果（成功/失败 + 时间）」：成功写 `OK`，失败写 `FailureClass` 名，并在 UI 显示成「上次失败：TIMEOUT」 |

**URL 规范化与校验（纯函数，可单测）**：取小写 scheme/host、去默认端口、去 fragment、折叠重复 `/`；只接受 `http`/`https`（`rtsp://` 会在 OkHttp 里直接抛，见 §4.0 F2，所以在此先拦）；拒绝空、含空格、缺 host 的地址；**同一规范化 URL 出现在另一行即判重**（编辑自己那一行时用 `editingId` 放行）。

**编辑换 URL 会换 id**：id 就是 URL 的身份，所以 `update` 在 URL 变化时删旧行 + 写新行，并把三列状态继承过去（同名只改标签则 id 不变，状态也保留）。

## 4. 接入刷新管线（派单项 2）

**做法**：`SubscriptionSourceProvider` 实现 docs/02 §4.4 的 `SourceProvider`（扩展点 E1），在 `:core:data` 的 `SubscriptionModule` 里 `@IntoSet` 注册一次。`RefreshSourcesUseCase` 拿到的 `Set<SourceProvider>` 因此多一项——**管线代码一行未改**。

为什么是「一个复合 provider」而不是「一行一个 provider」：Hilt 的 set 是编译期固定的，用户运行时新增的行进不去；所以 fan-out 放在 `fetch(clock)` 里。

每行的取回交由 `RemotePlaylistSourceProvider`（P2-4a 的原件）执行 ⇒ 取回、字符集回退、解析与 `SRC_FETCH_OK/_FAIL`、`SRC_PARSE_OK/_FAIL`、`NET_CHARSET_FALLBACK` 都是同一条已上线路径，没有第二份实现。

规则（均有单测钉住）：

1. **只取 enabled 的行**（停用即不再消耗取回预算与时间）；
2. **一行坏不影响其他行**（404/超时/不可解析都只算这一行失败，其余照常返回条目）；
3. **每行写自己的最近结果**（`last_fetch_at` / `last_result` / `entry_count`）；
4. **全部订阅都失败**时整体返回 `Err`（否则刷新会把「一个源成功但 0 条」当成正常）；
5. `channel.source_id` = 该行 id（`sub:…`），可回溯到是哪条订阅贡献的流。

## 5. 本地文件导入升级：SAF + 投放目录（派单项 3）

两条路都在，且共用同一段「全有或全无」管线（`publish()`）：

- **SAF（新增）**：`ActivityResultContracts.OpenDocument`（`ACTION_OPEN_DOCUMENT`）→ `PlaylistImportPort.importUri(uri)`。导入前先 `takePersistableUriPermission(READ)`（review R-27），把 `content://…` 记进 `last-import.json` 的 `sourceUri`；读失败时释放该授权。**读取与授权都在 `:core:data` 的两个接缝后面**（`DocumentReader` / `UriPermissionStore`），所以「授权被拒」「文档被撤走」两条分支能单测。
- **投放目录（保留）**：`getExternalFilesDir(null)/playlists` + `adb push`，行为、文案、测试与 TESTABLE-1 完全不变。

SAF 传 `*/*`：`.m3u`/`.txt` 在电视上没有可靠 MIME（不少 provider 报 `application/octet-stream` 或干脆不报），窄过滤会把用户自己的文件藏起来；真正的合法性由内容解析判定。

**SAF 在 TV 上的可行性结论（本轮）**：

- **代码级结论**：SAF 需要系统里有 DocumentsUI（`ACTION_OPEN_DOCUMENT` 的响应方）。应用侧已做降级——`ActivityNotFoundException` 会被捕获并显示「这台设备没有可用的文件选择器，请改用投放目录」，**投放目录那条路不依赖任何系统组件**，所以即使没有 DocumentsUI，导入能力不丢。
- **实证级结论**：**本轮未能在电视上取证**（派单禁用设备，QA 正占设备做 P1 验收）。⇒ 留给 P2 验收：在电视上点一次「从文件选择」，结论记 `:feature:settings` 或浏览页弹窗的实际表现。
- 即便 SAF 可用，也应知道**启动时恢复的是应用自己的副本**（`imports/`），不重新读原文档——U 盘拔掉后频道表仍然在。

## 9. 订阅与导入的优先级规则（派单项 6，写清）

**一句话：本地导入拥有频道行；订阅刷新只拥有「已存在频道」的流行。**

| 层面 | 规则 | 代码位置 |
|---|---|---|
| 源清单 | 刷新取「内置 17 源 ∪ `source` 表里 enabled 的行」；`enabled=0` 完全不取回；同一规范化 URL 不允许两行（添加时判重） | `SubscriptionSourceProvider` / `SubscriptionRules.validate` |
| 频道行 | **只有本地导入可以新增/删除频道**（`CatalogSink` 的契约是*整体替换*）；导入因此「覆盖」此前刷新写下的任何内容 | `CatalogPriority`, `CatalogSink` |
| 流行 | 刷新只更新**已存在频道**下的 `stream` 行（健康/评分/`disabled`/甄选结果）；因此订阅刷新**不会**重排、复制或删掉导入进来的频道 | `RefreshSourcesUseCase` PERSIST 段 |

**已知缺口（本轮未修，报 god）**：因为刷新管线目前**没有写频道行的出口**（docs/02 §6.1 的 Persist 只落 `stream`），**只存在于订阅 URL 里的频道不会出现在列表**——订阅目前只能给已有频道提供/更新流。补法是给刷新加一个频道 upsert 出口（即 god `7a577d6` 记下的「统一 `CatalogSink`」后续任务），它要改 P2-4 管线，超出 P2-6 边界。
