## 7. 缺陷清单（按 S0–S3）

### 7-1（S2）手动刷新「成功」但一条都没落库：`DB_FAIL FOREIGN KEY constraint failed`

**证据**：本轮向导第 2 步自动起的那轮刷新，`SRC_REFRESH_DONE{phase:DONE, channels:207, selectedPrimary:131, selectedBackup:27, deepOk:159, deepFail:245}`，但会话里**没有 `selection persisted` 的 `DB_UPSERT`**，只有两条 `DB_FAIL{message:"stream upsert failed", streams:466, written:0, err:"FOREIGN KEY constraint failed (code 787 SQLITE_CONSTRAINT_FOREIGNKEY)"}`（一条在浅校验落库、一条在收尾落库）。浏览页仍是快照的 189 台（未被污染，也**没被更新**）。

**定位（代码链，非本轮改动引入）**：`RefreshSourcesUseCase` 只写 **stream**（`streamRepository.upsertAll`），**从不写 channel**；写入用的是 `ChannelMapper` 给的内存 id，而这些 id 在 Room 里并不存在（快照只播了 189 行）⇒ 外键约束拒绝整批。`git show f29c191` 不含该链路（只有资产 + DI + seeder + 测试 + 文档），本轮也未改它 ⇒ **属既有刷新管线缺陷**；`f29c191` 只是把症状从"可能静默挂错频道"（旧夹具 658 行时内存 id 恰好都存在）变成"整批写不进去"。**基线 c736682 未复跑验证**，此差异属代码推断，需 god 决定是否单开一块卡查刷新落库链路。

**用户可见影响**：点向导默认按钮（「使用内置源并继续」）的用户，刷新跑 12 分钟、报成功、界面数据不变——**开箱可看（189 快照）不受影响**，但"刷新能带回新源"这条产品承诺当前不成立。

### 7-2（S3）快照第 1 台（默认焦点）出帧后卡死

见 §3.3：id=1 `CCTV-10科教` 两次会话均「首帧 ~1.1 s → 8 s 卡死 → 无备胎 give_up」；Mac 侧同 URL 正常。**建议**：快照收录判据从「出画面且首帧 ≤5 s」加一条「**连续播放 ≥30 s 不 stall**」，并优先复查第 1 台（它是用户第一眼看到的那一台）。

### 7-3（S3）文案/文档与快照现状不符

- 导入弹窗、设置页「最近刷新」、诊断概览「最近刷新」都写 **「内置示例表（无法出画面）」**；整改后内置表已是**可播的 189 台快照** ⇒ 文案误导。
- `PROVENANCE.md` §1 分组写「体育/赛事 2 · 地方/其他 124」，而文件里那 2 条（广东体育、辽宁体育）的 `group-title` 就是 `地方/其他` ⇒ 实际 **126**（总数 189 无碍，UI 也只显示 4 个分组）。

### 7-4（S3，观察）离线文案不自洽

断网时向导第 2 步显示「更新完成：可播放 0 条 / **失败 0 条**」——18 个源其实全部失败，用户看到「失败 0」会以为"没坏只是没内容"。建议区分「0 条可用源（网络不可达）」。同理诊断概览的 `SRC_REFRESH_DONE` 字段（`channels=207`）描述的是**内存结果**而非落库结果（与 7-1 叠加时尤其误导）。
