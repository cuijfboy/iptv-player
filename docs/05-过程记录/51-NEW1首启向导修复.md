## 2. 布局方案：为什么选 ②（摘要行 + 二级页），而不是 ①（整屏套 ScrollView）

派单给了两个选项并推荐 ②。**采用 ②，理由是一条算式，不是口味**：

| 方案 | 720p（640×360 dp）下第 1 步需要的固定高度 | 结果 |
|---|---|---|
| ① 三步面板套 `ScrollView`（清单仍留在第 1 步） | 面板内容 ≈ 734 dp（QA 实测 17 行清单 ≈ 715 px = 357 dp，再加标题/提示/状态/4 个 48 dp 按钮），可用高度只有 360 dp | 按钮仍要**滚动才可见**，与派单项 2「不给必须先滚动才看到主按钮的体验」直接冲突 |
| ② 摘要行 + 二级页（本轮） | 固定部分 **232 dp**（2 行按钮页脚）⇒ 描述区 **128 dp** | 按钮在首屏；清单移一级，信息不丢 |

所以 ① 在 720p 上并没有解决问题，它只是把「被裁掉」换成「要滚」。② 同时理顺信息层级：第 1 步是**做决定**的地方，清单是**查看**的地方。

**「查看」不是「查看/调整」**：内置源目前**没有**逐个开关可写（[44](./44-P2-9首启向导.md) §3.2：内置 provider 是编译期 `@IntoSet`，`source` 表只存用户订阅），所以入口文案是「已启用 N 个内置源 · 查看清单」，二级页用一句话说明「更新时会一起刷新，目前不支持逐个关闭」——**不画一个按了不落库的复选框**。

**结构（`WizardPanels` 与 `WizardPanelLayoutTest` 共同钉住）**

```
root（padding 48/24 dp）
  ├── wizard_header（minHeight 36 dp）、wizard_hint（minHeight 24 dp）
  ├── wizard_body（0dp + weight 1）        ← 全屏唯一加权子项
  │     └── 4 个面板（match_parent，同一时刻只有一个 VISIBLE）
  │           每个面板**本身就是 ScrollView**（描述区；选源二级页的 17 个可聚焦行也在这里）
  └── wizard_footer（wrap_content）        ← 可见面板的按钮组，先于 weight 结算被测量
        └── 4 个按钮组（同一时刻只有一个 VISIBLE）
```

两个设计要点：

1. **面板就是 `ScrollView`**，不再套一层 `LinearLayout`——那层是 `UselessParent`（lint），也把「这里会滚」说了两遍；
2. **按钮放在 `wizard_body` 的兄弟节点里**，而不是放进面板再给面板加权重——后者是**嵌套权重**（`NestedWeights` lint：同一个子树测量两次）。当前结构只有一次权重结算，按钮永远先被量到。

## 3. 焦点可达性（派单项 2 的硬约束）

### 3.1 按钮页脚：主操作按钮永远在第 1 屏

每个面板的按钮固定成「**主操作独占一行 + 侧门一行**」（`WizardPanels.footerRows`）。高度预算（`WizardPanels.fixedChromeDp`，输入全部来自 `values/dimens.xml`，测试逐项对上）：

`固定高度(行数) = 2×24(边距) + 36(标题) + 24(提示) + 12(标题块间隙) + 8(页脚上间距) + 行数×48 + (行数−1)×8`

| 面板 | 页脚行数 | 固定高度 | 描述区 @720p | 描述区 @1080p |
|---|---|---|---|---|
| 选源（主按钮 1 行 + 侧门 3 个 1 行） | 2 | **232 dp** | **128 dp** | 308 dp |
| 更新（开始 / 中断+跳过） | 2 | 232 dp | 128 dp | 308 dp |
| 开看（进入 / 导入+跳过） | 2 | 232 dp | 128 dp | 308 dp |
| 选源二级页（返回 1 行） | 1 | 176 dp | 184 dp | 364 dp |

判据（`WizardPanelLayoutTest`）：`fixedChromeDp(panel) ≤ 屏高`（按钮在首屏）**且** `viewportDp ≥ MIN_VIEWPORT_DP(96 dp)`（描述区还读得到）。360 dp 与 540 dp 两个屏高都过；若有人给第 1 步再加第三行按钮（固定 288 dp），描述区只剩 72 dp，**测试会红**——这正是 NEW-1 那类改动的护栏。

### 3.2 「按钮不在滚动区里」是走 DOM 验的，不是靠肉眼

`WizardPanelLayoutTest` 解析 `activity_wizard.xml`，把每个 `ScrollView` 的后代 id 收成一个集合，然后断言：

- `WizardPanels.actionsOf(panel)` 里**每一个**按钮 id 都**不在**该集合里（⇒ 按钮不在任何滚动容器内）；
- 每个面板的后代里**有**滚动内容（⇒ 描述区确实在面板里滚动）；
- 每个按钮属于**它自己面板的按钮组**（`wizard_footer_*`），且该组按钮与模型**逐条相等**；
- `wizard_sources_list`（17 行清单）**在**滚动容器内。

### 3.3 焦点顺序与落点

| 关注点 | 做法 |
|---|---|
| 面板打开时落点 | `WizardPanels.primaryOf(panel)`：选源 →「使用内置源并继续」；更新 →「开始更新」（运行中 →「中断更新」）；开看 →「进入频道表（按 OK 播放）」（空表置灰 →「导入本地清单」）；二级页 → 第一行内置源（无行则「返回」按钮） |
| 首次聚焦可能被拒 | 面板刚 `VISIBLE` 时 `requestFocus()` 可能返回 false（还没布局），改为**失败就下一帧重试**（`target.post { requestFocus() }`），避免冷启动第一屏「无焦点」 |
| 描述区 ↔ 按钮 | 显式 `nextFocusUp/Down`：摘要行 ↓ 到「继续」，「继续」↑ 回摘要行，不依赖默认焦点搜索 |
| 二级页返回 | `BACK` 先关二级页（它是「选源」之上的一级），再走原来的步骤回退；另有「返回『选择源』」按钮做可见出口 |
| 清单内滚动 | 17 行是**可聚焦行**（`bg_wizard_row` 走 `:core:design` 焦点色板），D-pad 逐行走、`ScrollView.requestChildFocus` 自动把焦点行滚进视野 |
| 长文案宽度 | 宽度预算 `buttonWidthDp(k, 640) = (544 − (k−1)×8) / k`：独占一行 **544 dp**、2 个一行 **268 dp**、3 个一行 **176 dp**；测试用 14sp、全宽字 1 em 的保守字宽模型逐条核对（最长的「跳过，直接进入频道表」154 dp ≤ 236 dp 文字框，「进入频道表（按 OK 播放）」171 dp ≤ 512 dp 且独占一行） |

## 4. 标记写入与续跑（派单项 3）

**保留设计**：`wizard-completed` 仍**只在走完三步 / 升级路径**时写（`WizardViewModel.complete()` 是唯一作者），半途退出不写。

**新增：退出后再次进入续到上次步骤**（派单项 3 的首选做法）。实现落在既有端口 `FirstRunStore`（`:core:domain`），实现在既有 `SharedPrefsFirstRunStore`（同一个 `first-run` 文件），键 `wizard-step` / `wizard-skipped`：

| 时机 | 行为 |
|---|---|
| 进入向导 | `savedProgress()` 读出「步骤 + 跳过集」；没有记录 ⇒ 第 1 步 |
| 继续 / 跳过 / 返回 | 每步写一次 `saveProgress`（`apply()`：内存即时可见、磁盘异步） |
| 续到「更新」 | 自动开始一次更新（与「走到更新」同一条边）——用户离开时那次更新已被 BACK 取消，回来要能继续 |
| 续到「开看」/「选源」 | 不启动任何东西 |
| 走完三步 | `markCompleted()` 同时**清掉** `wizard-step`/`wizard-skipped`：完成态与续跑态互斥 |
| 未知 / 终止步骤值 | 读成「无进度」（回到第 1 步）——**安全的失败方向**：宁可重看第 1 步，也不落到渲染不出的面板 |

**为什么选「续跑」而不是「首步给出口」**：NEW-1 的「每次启动都回向导」本身不是缺陷（设计如此），缺陷是**回到向导后按键没有出路**。出路已由布局修复给足（按钮在首屏、BACK 是有文案的明确出口），续跑进一步把「回来重做一次选源、重看一次刷新」变成「回到刚才那一步」——`wizard-completed` 只在走完写，所以续跑没有改变「没走完就还会出现」的语义。向导退出提示同步改成「按返回键退出向导（**下次启动从这里继续**）」。
