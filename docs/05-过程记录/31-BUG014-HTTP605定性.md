## 0. 结论（先给答案）

**这是环境侧故障，不是 App 缺陷。** 605 由 QA 网段路径上的 HTTP 中间件/CDN 反盗链闸门返回，App 只是**如实上报收到的响应码**（`InvalidResponseCodeException.responseCode` → `PLAY_PREPARE_FAIL{failure=HTTP_SERVER, httpStatus=605}`）。UI 提示、失败分类与重试/降级行为都符合 `docs/02 §4.6`。

三条硬证据（全部在**本机、不占电视**复现，见 `$AGENT_DIR/evidence/BUG014/raw-probes.txt`）：

1. **605 在同一网段真实存在**：直接用 `curl` 请求**夹具里自己的** miguvideo URL（`qa-fixture-playlist.m3u` 第 115 行，对应抽样行 123）→ `HTTP/1.1 605`、`Content-Length: 0`、`Server: CDN_6C381C27`。同主机换个坏 token → `403`。即 605 是这条路径上 CDN 的自定义状态码，和我们 App 报的 605 同码同形。
2. **该网段会按客户端指纹概率性回非常规码**：同一 URL、同一台机器、几秒内连发，`lxfile.lxxcb.cn` 出现 `200×9 / 418×6`（另一轮 12 发里 6 个 418，`Server: CloudWAF`）。也就是说「裸请求 200」只是**抽样时恰好命中**，不是稳定事实；反盗链闸门本来就会挑请求回非常规码。
3. **本网段按「目的 fake-IP」路由，不按 Host 头**：`Host: play.kankanlive.com` 的请求发到 `198.18.0.238`（jlntv 的 fake-IP）时，**jlntv 的 openresty 回 403**；反向发到 `198.18.0.239` 时 kankanlive 回 400。连到「已分配给别的域名」的 fake-IP，就会落到别人的源、拿到**别人的**状态码（扫描 508 个 fake-IP 时实测到 418/511/513 这类非常规码）。

**为什么「同机同分钟 App 605、裸请求 200」**：App 的两个 HTTP 栈都走**平台路径**——播放是 Media3 `DefaultHttpDataSource`（= Android `HttpURLConnection`，`Media3Engine.kt:382`），刷新管线是 OkHttp（`NetworkModule.kt:29`，未设 `proxySelector` ⇒ 回落 `ProxySelector.getDefault()`）；两者都跟随系统 DNS 与系统代理。`adb shell` 里的 `nc`/`curl` 是**裸 socket**，既不用平台代理，也不带 App 的指纹。请求内容已排除（见 §2 E2），所以变量只能在这条**网络路径**上。

**代价（要给 god 知道）**：本报告没有钉死「是哪一台设备回的 605」（路由器代理/缓存，还是源站反盗链，还是电视上某条 uid 级代理路径）。要钉死需要 1 次真机取证（§5，约 2 分钟，只读命令）。这不影响 §0 的定性结论与 §4 的复跑方案。

## 2. 实验（方法 → 结果）

环境：本机 `<MAC-LAN-IP>`，网关 `<LAN-GATEWAY>`，与电视同一个 LAN；网段所有域名解析到 `198.18.0.0/15`（fake-IP），HTTP 经 `iLabRouter` 中转。

**E1 网段形态**：网关开放 `80/443/7890/9090`；对 `<LAN-GATEWAY>:7890` 发绝对形式请求 → `407 Proxy Authentication Required (Basic)` ⇒ 网段内既有一条要认证的转发代理，也有会应答 HTTP 的中间件。域名→fake-IP 分配是粘性的（重复查询 + 500 个随机域名扰动后四条 URL 仍是 `198.18.0.{238,239,240,241}`）。

**E2 请求内容矩阵**（4 条 URL × {origin-form 1.1 / 1.0 / absolute-form / UA=okhttp+gzip / `Proxy-Connection: Keep-Alive` / UA=ExoPlayerLib(Android BRAVIA)+`Accept-Encoding: identity` / `Range: bytes=0-` / HEAD}）→ **全部 200**（Range → 206；kankanlive 的 HEAD → 405）。⇒ 请求字节不是变量。

**E3 非标准码率**（每组 15 发）：jlntv / kankanlive / 92.50.128.180 四指纹全部 200×15；`lxfile.lxxcb.cn` 只有 `curl` 指纹被拦（`200×9 / 418×6`），ExoPlayerLib / gzip / 无 UA 指纹 15/15 通过。⇒ 反盗链闸门是**概率性 + 按指纹**的，「裸请求 200」不能作为「源站正常」的证据。

**E4 605 复现（不用电视）**：`curl "http://hlsztemgsplive.miguvideo.com:8080/wd_r2/cctv/cctv1hd/600/index.m3u8?<夹具原文>"` → `HTTP/1.1 605`、`Content-Length: 0`、`Server: CDN_6C381C27`、`X-Z-Via-Rsp: …BCS-CDN-0574-…`。⇒ 605 是本网段真实返回码。

**E5 路由按 fake-IP**：见 §0 第 3 条；另扫描 `198.18.0.1–254` + `198.18.1.1–254`（Host 固定 jlntv），命中 273 个 `200 openresty`、56 个空响应、33 个连接失败，其余回落到 **无关源**（GitHub / Akamai / Cloudflare / AppleHttpServer / volc-dcdn / Varnish「500 Domain Not Found」/ CDN_6C381C27 …）并携带 `418/511/513` 等非常规码。

**E6 时延**：本机 TTFB：jlntv 30 ms、kankanlive 29 ms、lxxcb 120–200 ms、92.50 470–720 ms；App 失败日志耗时：行 183 `170 ms / 89 ms`、行 273 `143/147 ms`、行 393 `145 ms`（`evidence/P1G/item1-row*.log`）。⇒ 与「LAN 内应答」同量级，不像真实 WAN 往返。

**E7 代码事实**：`rg 605` 全仓 0 命中；播放 = `DefaultHttpDataSource`（HttpURLConnection）；刷新 = OkHttp 无显式 `proxySelector`；`docs/02 §4.6` 把 5xx 归 `HTTP_SERVER` 并透传 `httpStatus`。⇒ App 侧无 605 生产点，只有上报点。

## 4. 「正常网络下复跑」方案（给 QA 的验证步骤）

目的：把「源站在此网段不可达/被闸门拦」与「App 侧失败」彻底切开。

1. 换一条**没有 fake-IP 中转**的网络（手机热点最省事），`adb connect` 电视后 `adb shell settings get global http_proxy` 必须为空；确认 `dig/nslookup` 里这四个域名**不再**解析到 `198.18.0.0/15`。
2. 装 as-shipped 包（`9ce62639…`，7,801,860 B）→ `pm clear ilab.iptv.player` → 用与第 6 轮**同一份夹具**（`qa-fixture-playlist.m3u`，573 行）重新播种，顺序不要改（行号映射依赖 `ChannelSorter`）。
3. 只跑这 4 行 + 1 条对照：`183 东丰`、`273 嘉峪关综合`、`393 泸县新闻综合`、`573 RBC(Opt-1)`、`3 CCTV-10科教`（对照）。判据：`PLAY_FIRST_FRAME` 出现 → 本网段的 605 是环境；仍旧 `HTTP 605` → 是**源站反盗链针对我们的指纹/出口 IP**，按第 4 步处理。
4. 若正常网络仍 605：把结论改成「源站反盗链（UA/Referer/出口 IP 白名单）」——这属于**源清单质量问题**，不是播放器缺陷；处理方式是给这几条源补 `#EXTVLCOPT:http-referrer` / `http-user-agent`，或在清单校验里降权/剔除（`core:source` 已有 referrer/UA 字段，无需改 `core:player`）。
5. 阶段口径提醒：即使这 4 条全部定性为环境/源侧，抽样起播率仍是 **12/16 = 75% < 90%**（剔除 4 条域名不可解析的源）→ `P1-G` 第 1 项判 ❌ 不因此变化。

## 5. 真机取证（需 god 批准设备空闲，约 2 分钟，只读取证）

只做四件事，用来钉死「谁回的 605」，不改任何状态：

1. `adb shell settings get global http_proxy`、`adb shell dumpsys connectivity | grep -iE "proxy|vpn|current"`、`adb shell ip rule` → 确认电视上是否有**系统代理 / VPN / uid 级代理**把 App 的流量与 adb shell 的分开（这是「同机不同路径」的最可能来源）。
2. 同一分钟内在电视 `adb shell` 里跑 `curl -v` 与 `nc` 打同一 URL，同时用本机 `curl` 打同一 URL，三方状态码并列记录。
3. 决定性一条：把某条夹具频道的 URL 指向本机（Mac）起的 HTTP 服务，用电视播放 → 本机日志里就能看到 **App 真实发出的请求头与来源**（UA / Host / 是否有代理风格请求行），这条与 E2 的假说直接对撞。
4. 若 god 允许并且设备侧有 root/抓包条件，抓一次失败流量的目的 IP（确认是否就是 `198.18.0.x` 且是否被劫到别的源）。

## 6. 建议（都不是本 bug 的修复，需另开卡）

1. **诊断能力**：`PLAY_PREPARE_FAIL` 目前只有 `streamId/attempt/httpStatus`，没有**请求 URL 与对端 IP**，所以这一轮只能靠外部实验反推。建议给该事件补 `host`/`peerIp`（脱敏后）——要动 `docs/03` 事件码，按边界留给 god 决定。
2. **源清单卫生**：把「反盗链/地域白名单」类源（miguvideo 这类 token 绑定 `client_ip` 的尤其明显）在 P2-4b 深度校验里单独归类，避免再以「起播失败」污染成功率分母。
