## 1. 根因与修法（一句话各一条）

**根因**：`ChannelCatalog` 写的是 `ChannelStore`（内存），`RoomCatalogWriter` 写的是 Room，两者**没有共同的抽象**。所以「生产用 Room」这件事无法只靠绑定完成——绑上以后列表读 Room、导入写内存，用户导入完看不到任何变化；而且内存与 Room 两套 `ChannelRepository`/`StreamRepository` 同时绑定会触发 Dagger `DuplicateBindings`。上一轮的集成修复只能**先把 Room 撤出生产**（`7a577d6` 的裁决注释），并留下一句「引入统一写入接缝（CatalogSink）后再切换」。

**修法**：把这个接缝做出来，让**任何来源的目录写入**都汇聚到同一个入口，再一次性切生产绑定。

## 2. 写入接缝：`CatalogSink`

新增 `core/data/src/main/kotlin/.../store/CatalogSink.kt`：

```kotlin
interface CatalogSink {
    suspend fun write(catalog: MappedCatalog, nowMs: Long): Int
}
```

设计要点（三条，都写进了代码 KDoc）：

1. **契约是「整体替换」，不是「合并」。** 这本来就是内存路径的行为（`ChannelStore.replaceAll`，`19-本地导入验证.md` §2 的「导入即替换」）。两个实现走**同一个契约**才是接缝的意义——合并会让导入后残留旧清单的台。
2. **`suspend`。** 生产实现是 Room，事务 API 是挂起式的；阻塞写会落到播放线程，违反 §4.5 C6。
3. **时间戳由接缝接收。** `MappedCatalog`（纯逻辑）+ `nowMs`（落库要盖的 `created_at`/`updated_at`）；内存实现忽略它。

| 实现 | 位置 | 角色 |
|---|---|---|
| `ChannelStore : CatalogSink` | `store/ChannelStore.kt` | 内存快照；`write` = `replaceAll`。**测试专用** |
| `RoomCatalogWriter : CatalogSink` | `store/RoomCatalogWriter.kt` | SQLite；`write` = 批量 upsert + **删除不在本次目录里的行**（级联删流）。**生产实现** |

`ChannelCatalog` 不再知道 `ChannelStore`：`commit(prepared, nowMs = clock.nowMs())` 只调 `sink.write(prepared.mapped, nowMs)`。`prepare()` 保持纯逻辑（不碰 sink），所以「先看结果再决定是否替换」的导入语义不变。

### 2.1 Room 侧的「替换」怎么落地（`RoomCatalogWriter`）

先按唯一键 upsert（保留 id，从而保留收藏/排序/`play_history`），拿到本次写入的库 id 集合；再把**不在集合里**的 `channel` 行删掉（`ChannelDao.allIds()` 求差集 → `deleteByIds` 分批，400/批，低于 SQLite 999 参数上限；外键 `stream.channel_id → channel.id ON DELETE CASCADE` 连带删流）。一次导入 = upsert 新表 + 删旧表，得到与内存 `replaceAll` 相同的终态。种子阶段库本来是空的，删集为空，行为不变。

## 4. 两条启动路径的取舍（要求 4）

两条路径的**语义**（这次逐条对齐）：

| 语义 | 内存路径（`ChannelCatalogLoader`） | Room 路径（`RoomCatalogSeeder`） |
|---|---|---|
| 首次启动没有导入 | 读内置夹具 | 库为空 → 读内置夹具落库 |
| 有导入 | 每次启动**重新解析**留存的副本再发布 | 库里已有行 → **不解析**，直接读 SQLite |
| 副本/记录损坏 | 退回夹具（不空列表） | 不涉及（副本坏不影响库） |
| 幂等 | 进程内 `loaded` 旗标 | `channel` 表非空即跳过 |

**取舍：生产只留 Room 路径**（要求 4 允许「另一条标注测试专用」）。理由：

1. **Room 本身即持久化**：导入已通过接缝写入 Room，冷启动读 SQLite 就是「上次导入恢复」，不需要第二条「重解析副本」的恢复逻辑——这正是两条路径重复的地方。
2. **少一次解析、少一个失败面**：冷启动不再读 asset/副本、不再解析 670 行（`RoomCatalogSeeder` 的 no-op 由 `RoomRepositoryTest` 的冷启动用例与本次 `PersistenceIntegrationTest` 共同钉住）。
3. **内存路径仍有测试价值**：它是无 Room 也可跑的「夹具优先/副本优先」参考实现与测试夹具（`ChannelCatalogLoaderTest` 仍全绿），只是不再接生产。

**如实写下的代价**：Room 路径下，若**只删掉数据库文件、却留着 `imports/` 副本**（例如用户清数据），启动会重新用夹具播种，而**不会**从副本恢复导入——内存路径会恢复。这是「以 Room 为真相」的必然结果，属可接受：清数据即「重置为出厂」，且导入副本仍在盘上可人工再导入。若产品要求「清库但保留导入」，那需要把 `RememberedPlaylistSource` 接进 `RoomCatalogSeeder`，属后续卡（见 §8）。
