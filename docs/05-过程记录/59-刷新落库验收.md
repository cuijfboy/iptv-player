## 9. 未做 / 观察 / 判断点

### 9-a【S3·观察，属既有口径】刷新只增不删 ⇒ 订阅里的新频道会进列表
本轮自持源里 3 台 QA 频道（源里 URL 404、浅校验判 `unavailable`）**频道行仍然落库并出现在列表**，流被标不可用。这正是 `docs/05/58` §0 报 god 的那处口径变化，**已由 god 批准**并按要求写入已知限制 ⇒ 不属于新缺陷，但使用者可见（源里不可用的频道会进表）。

### 9-b【作者遗留项复核】浅校验健康戳按「内存 stream id」
作者在 `58` §5.1 记的第二处根因（channel id 已修、stream 自身 id 未回读）本轮**未观察到错位证据、也未否证**：`dbB`/`dbC` 的 `play_history` 仅 **3 / 6** 行，`channel_id/stream_id` 指向库内真实存在且同频道的行（1/190、2/191、3/192），`stream` 表 `checked=192`、`failed=5`（= `unavailable:5`）自洽。与作者那轮（先清空 stream 表 + 1822 条流、出现 1600+ 行 `play_history`）形状不同，**本卡不据此签或否**，仍归作者/架构裁定（STREAM-ID-1）。

### 9-c【环境，非缺陷】内置源与 EPG
17 个内置源在本网段对 `raw.githubusercontent.com` **全部 TIMEOUT（≈30.3 s）**；同一台电视的 EPG 源正常（本轮日志有 `EPG_FETCH_OK`）。与 `docs/05/56`/`57` 一致，与刷新落库判定无关。

### 9-d【方法，已还原】输入法与向导
① 电视输入法会打乱 `adb shell input text`，本轮以「临时禁用索尼输入法 → 输入 → 收尾还原」解决（§3）。② **源刷新的唯一 UI 入口是向导第 2 步**（设置/诊断页没有「立即刷新源」按钮）；向导未写完成标记时冷启动必回向导，标记写入后可用 `am start -a ilab.iptv.player.action.WIZARD` 再进（本轮两轮刷新都走这条，落库路径 `WizardUpdatePort → RefreshScheduler.enqueueNow(MANUAL)` 未变）。

### 9-e 未做
定时刷新（`refresh-daily`/`SCHEDULED`）与长稳、`ON_DEMAND_SINGLE_CHANNEL` 单频道刷新未复跑（本卡只判「刷新落库」，与 `58` 范围一致）。
