## 2. 复现（修前）

### 2.1 现象来源

`docs/05-过程记录/55-G7-1打包与集成测试.md` §6 观察项②（同 §5.1 备注）：真机那一轮出现 **2 次 `SRC_REFRESH_DONE`，两次都是 ≈152 s**（`elapsedMs:151565`），并把第二次归因于「第 3 步按 BACK → 回到第 2 步」。

### 2.2 代码里的实际触发点

点击 BACK 本身**不调用**任何刷新入口：`WizardViewModel.onBack()` 只做「退一步 + 存进度」（在飞的一轮会顺带 `cancel()`）。全仓也只有 `WorkManagerWizardUpdate.start()` 会以 `RefreshTrigger.MANUAL` 入队（`rg` 核对，生产代码唯一调用方）。

真正会入队的是**进入第 2 步时的自动触发**：

```kotlin
// 修前
private fun maybeStartUpdate(state: WizardState) {
    if (state.step != WizardStep.UPDATE) return
    if (WizardStep.UPDATE in state.skipped) return
    if (updateState.value != WizardUpdateState.NotStarted) return   // ← 判据
    startUpdate()
}
```

`updateState` 是 `update.observe().map(...).stateIn(viewModelScope, Eagerly, NotStarted)`：它的**初始值**就是 `NotStarted`，而端口的真实读数（WorkManager 的数据库查询）要晚一拍才到。于是「初始值」和「读过之后确实是空的」在代码里是同一个值 —— 只要**判定发生在读数落地之前**，一个已经完成、已取消、已排队甚至正在跑的一轮，都会被当成「还没开始」再入队一次（`enqueueNow` 在被打断的那一轮上是 `REPLACE`，所以这不是空操作，而是实打实的第二轮）。

这正好覆盖真机那条路径的两种形态：向导**记住上次停在第几步**（NEW-1），于是"回到第 2 步"意味着**带着第 2 步重新进入这一屏**（重进 Activity / 新建 ViewModel / 冷启动续跑都是这个形状），判定就发生在读数之前。

### 2.3 负向对照（先复现，再修）

新增 `feature/wizard/src/test/.../WizardUpdateEntryTest.kt`，其中 `ReadingWizardUpdatePort.observe()` 用**虚拟时间延迟一拍**再给读数 —— 这不是 faker 的花活，而是真端口的样子（WorkManager 从数据库读，第一帧读数必然晚于屏幕）。

把 `maybeStartUpdate` **临时改回修前一行判据**后跑该文件：

```
8 tests completed, 5 failed
```

| 用例 | 修前 | 说明 |
|---|---|---|
| `coming back onto 更新 with a finished round on record starts nothing` | ❌ `startCount=1` | 已完成的一轮被整轮重跑（≈152 s 的来源） |
| `a round that is already queued or running is not started again by entering the step` | ❌ `startCount=1` | 已排队/运行中也照样再入队 |
| `a run the user cancelled stays cancelled until they ask for it again` | ❌ `startCount=1` | 被用户「中断更新」的一轮被自动重启 |
| `the button starts a run every time the user asks, finished or cancelled` | ❌ | 自动路径抢在按钮之前入队，把「用户显式点」的语义搞混 |

## 3. 改法

### 3.1 判据抽成纯函数（`:core:domain`）

`WizardUpdateReading.startsOnEntry(snapshot)` —— 只有三种"没有可展示的结果"才允许进入即触发：

| 读数 | 进入第 2 步是否触发 | 为什么 |
|---|---|---|
| `NONE`（队列里没有任何记录） | ✅ | 「新用户 3 步内看到画面」的自动起跑 |
| `QUEUED` + `RETRY_AFTER_INTERRUPTION`（进程死亡留下的一轮） | ✅ | NEW-004：要**重问**一次，`enqueueNow` 才会用 `REPLACE` 把它从退避里捞出来（队列非空，不会重复跑） |
| `QUEUED` + `AWAITING_CONSTRAINTS` | ❌ | 正常排队等约束，别去扰动它 |
| `RUNNING` | ❌ | 正在跑 |
| `SUCCEEDED` / `FAILED` / `CANCELLED` | ❌ | 有结果可展示；要再跑是**用户**按「重试更新」的事 |

### 3.2 视图模型：先读端口，再决定；每会话只问一次

```kotlin
private var updateEntryAsked = false

private fun maybeStartUpdate(state: WizardState) {
    if (state.step != WizardStep.UPDATE) return
    if (WizardStep.UPDATE in state.skipped) return
    if (updateEntryAsked) return
    updateEntryAsked = true                      // 先落旗，再挂起：两次进入不可能都通过
    viewModelScope.launch {
        val reading = runCatching { update.observe().first() }.getOrNull() ?: return@launch
        if (WizardUpdateReading.startsOnEntry(reading)) startUpdate()
    }
}
```

两层保险：**①新鲜读数**保证「已完成/已取消/已排队/运行中」都不会被当成"未开始"；**②会话内一次性记录**（对应派单里的「本轮已完成/已入队」幂等化）保证即使端口里那份记录后来消失了（WorkManager 会清理已完成 work），同一屏也不会再回到"每次进第 2 步都重跑"。读数失败按「没有读数」处理 —— **不猜**着起跑，面板上仍有按钮，代价是用户多点一下，而不是凭空 152 s。

### 3.3 边界（都没动）

- `RefreshScheduler` / `RefreshReclaim` / `RefreshRunLedger` / `RefreshWorker`：**未改**（NEW-004 的 30 条测试原样全绿）。
- `WizardUpdatePort` 接口：**未改**（用已有的 `observe()` 取一次读数，无需动冻结接口）。
- 快照资产、播放引擎、刷新写入链：未动。用户显式点击路径：未动。

## 6. 已知限制

1. **本轮未取证真机**：单测证明的是"进入第 2 步的判定不再依赖未落地的初始值"，真机 `SRC_REFRESH_DONE` 是否从 2 次回到 1 次需要电视复跑（建议复跑脚本：`pm clear` → 导入 → 第 2 步更新完成 → 进第 3 步 → BACK 回第 2 步 → 观察 `SRC_REFRESH_START/DONE` 计数与 `WORK_SCHEDULE{trigger:MANUAL}` 条数）。
2. **幂等记录是会话级**：`updateEntryAsked` 随 ViewModel 消失。极端情形（一轮完成后 work 记录被 WorkManager 清理干净 **且** 用户冷启动又落回第 2 步）仍会起跑一次 —— 那时端口里确实没有任何"已完成"的证据，面板文案也如实显示"还没有更新"。要彻底封住需要把"本轮已完成"持久化（`RefreshRunLedger` 目前是**全局单布尔、不按 unique 名分桶**，见 `67` §7 的已知限制），本卡不动它。
3. **`docs/05-过程记录/67-刷新重触发退避修复.md` 文件缺失**：`00-索引与模板.md` 有 67 行、提交 `359393c` 也写了"记录 docs/05/67"，但该文件不在树里（该提交只改了索引一行）。NEW-004 的内容我按提交信息与代码注释核对使用；**建议 god 补落该文件**（或把索引行改成指向提交信息）。
