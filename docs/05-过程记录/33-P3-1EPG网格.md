## 2. 关键设计决策（附理由）

### 2.1 绘制缝：`DrawSurface` 而不是 `Canvas`
渲染器只认 `DrawSurface`（4 个绘制动作 + 调色板 int），Android 侧才把 `Canvas`/`Paint`/`StaticLayout` 接上。**这是本卡「可离线自证」的前提**：同一条渲染代码既能被真机 `View` 调用，也能被 JVM 基准驱动（见 §3）。

### 2.2 时间轴线性于**真实时间**，DST 由 `Calendar.add(MINUTE, …)` 处理
水平轴按 epoch 毫秒线性映射，节目块宽度 = 真实时长。夏令时下：
- **春季跳变**（Europe/Berlin 2026-03-29 02:00→03:00）：刻度标签直接 01:30 → 03:00，**02:00/02:30 不存在**；一天 **46** 个刻度；
- **秋季回拨**（2026-10-25 03:00→02:00）：02:00/02:30 **各出现两次**；一天 **50** 个刻度；
- 平时 **48** 个刻度；相邻刻度的**瞬时差恒为 30 min**（标签跳跃/重复不代表时间跳跃）。

不用 `java.time`：`minSdk = 21` 且无 core-library desugaring（与 `docs/05-过程记录/19` 的导入对话框同一结论），项目既有代码（`XmltvTime`、`RefreshSchedule`）也走 `java.util.Calendar`。

### 2.3 行高 56 dp，而不是原型 S3 的 40 dp
`docs/02 §8.2` 冻结「焦点态最小 **48 dp** 命中区」，而网格里「一行」就是焦点目标；原型夹具不承担该条款。代价是每屏行数由 13 降到约 10，**每帧绘制块数 ~107（原型 119）**——两个数字同量级，结论不变（§3）。这是本次唯一有意偏离 S3 夹具的参数，记在此处备查。

### 2.4 窗口与分页：查询只走 `EpgRepository.observeWindow`
- 时间窗：初始 6 h（`now − 30 min` 起，对齐到刻度）；光标距边缘 < 1 h 时按 3 h 扩展，**跨度硬顶 24 h**（`docs/02 §8.3` 上限），扩展只会推动另一侧，**绝不丢光标**。
- 频道页：**按 32 台一页对齐**（可视行带 ± 8 行 → 归到页边界）。页内滚动**不产生新查询**；跨页才换页，一次最多两页（64 台，正好是 §8.3 的 `limit`）。
- 单页实现：`:core:data` 的 `RoomEpgRepository` 把 `channel.id → epg_channel_id → programme`，走 `idx_prog_lookup`，**不存在全表拉取路径**；UI 不碰 Room。

### 2.5 无数据的两种占位必须不同
`NO_EPG`（该频道没有 `epg_channel_id`，永远不会来数据）与 `LOADING`（有绑定、在预取边距内、查询还没回来）分开渲染：前者是事实，后者是过程。已加载但空表（`LOADED` + 无行）也归 `NO_EPG`。节目单中的空洞 ≥ 15 min 画 `GAP` 底色块。

### 2.6 文本缓存是**有界 LRU**，不是原型的「满了就不再写」
原型（`spike`）在缓存满后停止插入，命中率会单调恶化；本实现用 `accessOrder` 的 `LinkedHashMap` + `removeEldestEntry`，**上限仍是 §8.3 冻结的 512**，但节目块滚出屏再滚回来仍是命中。实测命中率见 §3。

### 2.7 焦点与选中是两件事
`docs/02 §8.2` 要求三重反馈：焦点行给抬升底色、选中节目块给亮色 + 3 px 描边。左右键**按 30 min 步进**（§8.2「网格页…左右键按时间步进」），上下键换行**保持同一时刻**，`ensureVisible` 只在光标将出安全区（两侧各 1/6 时窗）时滚**最小**距离，并交给 `OverScroller` 走 ~200 ms 动画。

## 3. 二维虚拟化与缓存的离线实测数据

### 3.1 基准：`EpgGridBenchmarkTest`（JVM，可重复跑）

场景 = S3 原型：**658 台**、30/60 min 混合块、**1920×1080 @ density 2.0** 视口、双轴惯性（横 700 px/s、纵 3500 px/s，逐帧采样、碰边反弹），**1800 帧（= 60 Hz 下 30 s）**，先跑 60 帧热身再由 JIT 统计。数据源为每行 6 h（与 S3 可比）与每行 24 h（深导引）两种。

```
EPG_BENCH hours=6  frames=1800 totalBlocks=5922  drawnBlocksAvg=106.87 drawnBlocksP95=112  drawnBlocksMax=113
          rowsPerFrameMax=14 textsPerFrameMax=149
          textCacheHits=226839 textCacheMisses=40059 textCacheHitRate=0.8499
          virtualizationSkipRatio=0.982  frameWorkMsP50=0.545 frameWorkMsP95=5.279
EPG_BENCH hours=24 frames=1800 totalBlocks=23688 drawnBlocksAvg=110.90 drawnBlocksP95=116 drawnBlocksMax=118
          rowsPerFrameMax=14 textsPerFrameMax=149
          textCacheHits=225233 textCacheMisses=40172 textCacheHitRate=0.8486
          virtualizationSkipRatio=0.9953 frameWorkMsP50=0.410 frameWorkMsP95=3.759
```

| 指标 | S3 原型（virtual） | 本卡 6 h 导引 | 本卡 24 h 导引 |
|---|---|---|---|
| 总块数（不虚拟化要遍历的量） | 5922 | **5922** | **23688** |
| 每帧绘制块数（平均 / p95 / max） | 119 | **106.9 / 112 / 113** | **110.9 / 116 / 118** |
| 虚拟化跳过率（1 − 绘制/总量） | 0.980 | **0.982** | **0.9953** |
| 每帧被物化的行数（含预取） | – | 14 | 14 |
| 文本布局缓存命中率 | 未埋点 | **0.850** | **0.849** |
| 每帧代码耗时 p50 / p95（JVM，非 fps） | – | **0.545 ms / 5.279 ms** | **0.410 ms / 3.759 ms** |

**结论（只覆盖绘制逻辑，不覆盖设备 fps）**
1. 每帧绘制块数稳定在 **~110**，与 S3 的 119 同量级；导引从 6 h 加深到 24 h，**总块数涨 4 倍而每帧块数不涨**（106.9 → 110.9），这正是二维虚拟化成立的判据；若退化为全量遍历，这个数字会逼近 5922 / 23688。
2. **单帧文档里的峰值**（113 / 118）远小于任何「虚拟化失效」阈值；`虚拟化跳过率` 用「整轮累计」口径算（见表），不是单帧比。
3. 文本布局缓存命中率 **0.85**：每帧 149 次取布局，其中大部分是上一帧已建过的键（同一块连续可见多帧）。缓存尺寸上限 512，实测 `TextLayoutStore` 单测守住上限与 LRU 行为。
4. `frameWorkMs*` 是**本机 JVM 上「建帧 + 画帧」的代码耗时**，**不是 fps、不能当帧率判据**：§8.5 的 fps 口径是 release 构建 + `Choreographer` 采样 + GPU，必须真机测（§7）。

### 3.2 视口与内容尺寸（可复核）
density 2.0 下：`行高 112 px`、`表头 80 px`、`频道列 320 px`、`3.2 dp/min → 6.4 px/min`。
6 h 内容 = `320 + 360×6.4 = 2624 px` 宽；658 行 = `80 + 658×112 = 73 776 px` 高。视口 1920×1080 → 横向最多滚 704 px、纵向 72 696 px，与基准脚本用的范围一致。

## 7. 未做项与给 god 的裁决点

**未做项（诚实清单）**

1. **真机 fps 待测**（派单明确留待后续轮）。§8.5 的达标线是 release 构建 + `Choreographer` 连续滚动 + p95 ≤ 17 ms，需要独占电视；本轮电视被 BUG-013 占用，**未连接设备、未安装、未取任何设备数据**。§3 的数字是**绘制代码的离线工作量**，与 fps 不是同一口径。
2. 真机上的滚动惯性/手感（`OverScroller` 的 200 ms 翻页、DPAD 长按连发）未调参；离线无法定。
3. 网格与播放页之间的返回/焦点恢复（`docs/02 §8.1` 播放返回契约）在网格这条链路上只用到 `PlayerContract` 的入口，**返回后回到网格**的行为未在设备上验证。
4. 真实 EPG 数据下的观感（覆盖率 20.5% 意味着多数频道会显示 `NO_EPG` 占位）未在设备上看过；占位样式可能还需一轮视觉调整。
5. 每帧的 `GridFrameInput` / `CanvasDrawSurface` / 块对象都是热路径分配（lint `DrawAllocation` ×2）。离线基准的 p95 5.3 ms 说明它没有把帧预算吃光，但**是否值得改成可复用缓冲**应由真机 `PERF_EPG_GRID` + `Choreographer` 数据决定，本轮不动。

**给 god 的裁决点**

1. **`docs/03 §3.3` 的 `PERF_EPG_GRID` 字段口径**：该行只登记了 `fps、drawnBlocks、scrollMs`，而 `docs/02 §8.3` 明确要求同时埋 `layoutCacheHit`。本实现按 §8.3 发**超集**：`screen, fps, drawnBlocks(p95), drawnBlocksAvg, drawnBlocksMax, layoutCacheHit, layoutCacheHits, layoutCacheMisses, virtualizationSkipRatio, frames, p95ms, scrollMs`。**`docs/01–04` 不在本卡可改范围**，请裁决是回写 `docs/03` 还是收窄字段。
2. **新增了一个跨模块入口**：`:core:ui` 的 `EpgContract` + `:feature:channels` 顶部「节目单」按钮（`BrowseActivity` / `activity_browse.xml` / `strings.xml` 各一处）。理由：P3 是「门面」，没有入口就没人能看到；沿用了 `PlayerContract`/`SettingsContract` 的 action 模式，**没有引入 feature→feature 依赖**。`:feature:channels` 与并行轮可能重叠，集成时请按「只吸收增量」处理。
3. **`:feature:epg` 的自身依赖**：新增 `androidx.lifecycle.viewmodel.ktx` 与 `kotlinx-coroutines-android`（写在模块自己的 `build.gradle.kts`，与 `:feature:channels` 同做法），不碰 `libs.versions.toml`。
4. **行高 56 dp**（§2.3）：为满足 §8.2 的 48 dp 焦点命中区而偏离 S3 夹具的 40 dp，若 QA 认为每屏行数更优先，可改回 40 dp（一处常量）。
