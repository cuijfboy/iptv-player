## 2. 根因（复核 dev-a-21 的定性，成立）

`RoomCatalogWriter.write()` 分三步：

1. **频道**按 `UNIQUE(name_key, group_key)` upsert —— 同名同分组的频道**保留原行**（这是有意的：频道的 row id 承载收藏/隐藏/排序/频道号/EPG 绑定，见 `ChannelDao.upsertAll` 的列拆分，docs/02 §5.1 + docs/01 F5）。
2. **流**按 `UNIQUE(channel_id, url_hash)` upsert —— **只增不删**。
3. 只有**本次目录里不存在的频道**被删除，它们的流靠外键 `ON DELETE CASCADE` 一起走。

于是「同名频道 + 换了一份清单」这条路上，旧清单留在该频道下的流**一条都没被删**：它们继续挂在那一行上，成为故障转移的备胎，界面「流」计数也比清单大。

设备上的数字对得上：内置夹具 `p1-2-baseline.m3u` 的 `CCTV1`/`CCTV2`/`CCTV3`/`CCTV5`/`CCTV13` 各有**两条同名流**（658 频道 / 670 流 的来源之一），导入 8 频道 / 10 流的 `real-excerpt.m3u` 后 → 10 + 旧流 = 界面 **「流 22」**、单行 `CCTV1 · 3 路流`（夹具 2 条 + 新 1 条）。

## 3. 语义（god 裁决：导入 = 整体替换）

`CatalogSink` 的契约本来就是 **replace, not merge**（`ChannelStore.replaceAll` 从 P1-2 起就是这个语义，见 `docs/05-过程记录/19`）。本次把 Room 实现补齐到这个契约上，**口径写死为**：

| 写入口 | 频道 | 流 | 用户字段 |
|---|---|---|---|
| **本地导入 / 内置夹具播种**（`CatalogSink.write`） | 新目录里没有的频道**删**（级联删流） | **整体替换**：新目录里没有的流**删**，包括同名频道下的旧流 | 收藏 / 隐藏 / 排序 / 频道号 / EPG 绑定**保留**（订单列拆分，不改） |
| **订阅刷新**（P2-4 管线，不走 `CatalogSink`） | 只处理已存在频道 | 只增改（健康/评分/`disabled`），是**甄选语义**，不变 | 同上（不改） |

两点刻意没动：

- **不按频道整体 `DELETE + INSERT`。** 那会换掉 channel 行 id，`play_history` / EPG 绑定 / 用户字段一起丢——正是 `upsertAll` 的列拆分要避免的事。
- **不改刷新管线。** 刷新走 `StreamRepository`（`RoomStreamRepository`），根本不经过 `CatalogSink`；「保候选」是刷新的语义，在这里把它改掉会破坏故障转移。
