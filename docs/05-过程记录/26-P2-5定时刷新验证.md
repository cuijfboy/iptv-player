## 3. 调度与避让策略（**阈值即契约**）

### 3.1 时间与周期

| 项 | 值 | 说明 |
|---|---|---|
| 触发时间 | 每日本地 **06:00** | `RefreshScheduleSettings.DEFAULT_MINUTE_OF_DAY = 360`；出界值（如 `-1`、`24*60`）回落到默认 |
| 首次延迟 | `下一次 06:00 − now` | 纯算法 `RefreshSchedule.nextDelayMs`；**正好压在 06:00 上算明天**（否则每次 06:00 启动都会立刻又跑一次） |
| 周期 / flex | 24 h / 5 min | WorkManager 在 `[目标, 目标+5min]` 内挑时刻；周期是真实 24 h，DST 当天墙钟会漂 1 h，**每次启动重算延迟**把它拉回 |
| 幂等 | `enqueueUniquePeriodicWork(name, UPDATE, …)` | 每次启动重算并覆盖；`UPDATE` 而非 `KEEP`，否则改了设置要等旧周期结束才生效 |

### 3.2 约束与重试

| 项 | 值 | 说明 |
|---|---|---|
| 约束 | 网络可用（`NetworkType.CONNECTED`）+ 电量不低（`requiresBatteryNotLow`） | ⚠️ `docs/02 §6.1` 该行写的是「**非计量网络** + 充电（可选）」；派单写的是「网络可用、电量不低」。**按派单实现**，差异报 god/arch 裁决（§7 第 1 条） |
| 退避 | **LINEAR，基准 30 min** | 第 n 次重试等 n×30 min |
| 最大尝试 | **3** | 累计最多 90 min；用尽后**返回 `success`（`gaveUp=true`）而**不是 `failure()`——周期任务报失败有把每日 06:00 整个取消掉的风险，为一次早上的断网丢掉以后所有刷新是更坏的失败 |
| 预算被截断 | 直接 `success` | 预算截断是**设计内**收尾（§6.1），立刻重试只会再烧一次预算；已写的行留在库里，靠 TTL 让下一轮接着跑 |

### 3.3 前台服务（**偏离 WBS 的写法，请 god/arch 过目**）

派单与 `docs/05` WBS 都写「`:app RefreshService`」。**没有自建 Service**，而是让 `RefreshWorker` 用 WorkManager 的长任务前台路径（`setForeground(ForegroundInfo)`）：

1. Android 12（API 31）起**禁止后台启动前台服务**，而 06:00 的任务天然在后台——自建 `Service.startForeground()` 走到真机上就是 `ForegroundServiceStartNotAllowedException`；WorkManager 的这条路径是官方为此提供的通道，也是唯一不需要向用户讨「忽略电池优化」的做法。
2. 一个代码路径而不是两条（自建服务还得再决定「谁来跑刷新」），且「结束即撤」由 WorkManager 保证（`doWork` 返回即撤前台态）。
3. 代价：通知由 `SystemForegroundService` 持有（`dataSync` 类型，API 34+ 需 `FOREGROUND_SERVICE_DATA_SYNC`，已在清单声明，合并清单实测见 §6.1）。**请 arch 把 `docs/05` WBS 的 `RefreshService` 改为 `RefreshWorker`**，或明确要求自建服务并说明 API 31+ 的处理方式。

> 另：`docs/02 §6.1` 把「充电/网络约束」排在 WorkManager 行里，与本卡一致；只有「非计量 vs 可用」一处措辞差异。

### 3.4 播放避让（R7）两半

**信号**：`:core:player` 的 `PlaybackUiStateMachine.publish()`（`PlaybackUiState` 的唯一写者）把相位镜像进 `:core:common` 的 `PlaybackActivity`；`:core:source`（并发减半）与 `:app`（是否推迟）读同一个标志。**相位带**与 P1-7 前台服务的「前台带」完全一致：`PREPARING / BUFFERING / PLAYING / FAILOVER` = 在播；`IDLE / STOPPED / ERROR / RELEASED` = 不在播（**暂停但已准备的会话不算在播**：它不抢带宽也不解码）。

为什么放在 `:core:common` 而不是 Hilt 端口：生产者（`:core:player`）与消费者（`:core:source`、`:app`）在依赖矩阵里互不可见（`:core:source` 无 `domain`/`player` 列，`:app` 无 `source`/`player` 列），任何 Hilt 绑定图都连不起来；`:core:common` 是三者唯一的公共模块。**报 arch 的开放项**：若希望它成为注入式端口，需要动 §3.2 矩阵。

**开跑前（`:app`）**：

| 条件 | 决策 |
|---|---|
| `respectPlayback=false`（用户关掉避让） | 照跑 |
| 不在播 | 照跑 |
| 在播 + `MANUAL` / `FIRST_RUN` / `ON_DEMAND_SINGLE_CHANNEL`（有人在等） | 照跑（由流水线并发减半兜底） |
| 在播 + `SCHEDULED` + 已推迟 < 3 次 | **推迟**（`Result.retry()`，LINEAR 30 min → 30/60/90 min，最多 3 h） |
| 在播 + `SCHEDULED` + 已推迟 ≥ 3 次 | 照跑（电视开着几天也必须刷到） |

**跑动中（`:core:source`，P2-4a 已有，本卡接真信号）**：`respectPlayback=true` 且信号为真时，Fetch 4→2 / Shallow 12→6 / Deep 6→3（每阶段建信号量时实时读，故中途开播也会生效）。

## 5. 断点续跑：本卡发现的真缺陷 + 修复

**发现方式**：写「第一轮被预算截断 → 第二轮（新进程）续跑」的成对单测时，第二轮把 4 条流**全部重探了一遍**，与 `docs/02 §6.1`「每条结果即时落库；进程被杀后重入自动跳过已完成项」矛盾。

**根因**（`RefreshSourcesUseCase` 尾段持久化）：候选行在 Shallow 之前先落库一次（`persistMergingHealth`，得到快照 `candidates`）；Shallow 的判定通过 `StreamRepository.recordOutcome` **即时写健康戳**；但 Deep 阶段之后的最终 upsert 把**未被 Deep 探测**的行（`VerificationKind.PENDING`）按**旧快照**原样写回——等于把本 run 刚写下的 `lastOkAtMs/lastCheckAtMs` 覆盖掉，于是下一轮认为这些流「从没验过」，重复探测。

**修复**：`PENDING` 行**不再回写**（`mapNotNull` 返回 `null`），连注释一起写清「回写旧快照会抹掉本轮的浅校验判定」。语义上这与 KDoc 原本的承诺「本次未探测的行保持库里的分数/健康/disabled」一致，只是原来没做到。

**影响面**：`RefreshBackHalfTest` 里那条断言 `lastCheckAtMs.isNull()` 的用例，断言的其实是被覆盖后的结果（作者意图是「Deep 没碰行」）。已把断言改为「Deep 列不动、**浅校验判定保留**」，测试名同步改写，并在用例上注明由 P2-5 驱动发现。**这是对 P2-4b 交付行为的一处修改，请 god 过目**（§7 第 2 条）。

**证据**（`:core:data`）：新增 `a resume after an interrupted run does not repeat the probes that already landed` —— 第一轮 `interrupted = BUDGET_EXCEEDED@DEEP`、浅校验 4 次、Deep 0 次；第二轮（新的 `RefreshSourcesUseCase` 实例 = 重启后的进程）`phase=DONE`、`total=4`、`okCount=0`、浅校验仍 4 次、Deep 仍 0 次。

4. `CoroutineWorker.setForeground` 是 `suspend`；回调若要更新通知，回调签名必须写成 `suspend (T) -> Unit`，否则编译报「Suspension functions can only be called within coroutine body」。
5. `:app` 的 `R` 是 `ilab.iptv.player.R`（namespace = `ilab.iptv.player`），在子包里用资源要显式 import。
6. WorkManager 的 `WorkManager.getInstance()` 依赖 `androidx.startup` 的 `WorkManagerInitializer`，它在 `Application.onCreate` **之前**跑完，所以在 `IptvApplication.onCreate` 里排期是安全的（合并清单已核）。
