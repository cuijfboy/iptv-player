## 3. 根因

1. **决策层**：`docs/02 §4.6` 的 `TIMEOUT` 行是 `RetrySame(≤1) → SwitchTo(next)`，`DefaultFailoverPolicy` 按 `FailoverInput.attempt` 逐级走，所以第一次起播超时**必然**换来一次同流重试——在一台**已经死掉**的主源上，这次重试等于再等一个完整窗口。
2. **窗口层**：`EngineTuning.prepareTimeoutMs = 12 s`（§7.5）是**所有** prepare 的唯一窗口，没有任何「有备胎时更早换手」的表达方式。
3. **可分辨性**：`FailureClass.TIMEOUT` 同时被**起播超时**和**播放中**的超时使用（`PlaybackErrorMapper` 把 `ERROR_CODE_TIMEOUT`、连接超时、`ERROR_CODE_BEHIND_LIVE_WINDOW` 都归到 `TIMEOUT`），而 `FailoverInput` 里**没有**任何字段能区分两者——这正是不能简单「把 `TIMEOUT` 行改成直接切换」的原因（那会把「直播边沿追赶」这类瞬时问题也误切成换源）。

## 4. 改法（要求 2）

### 4.1 决策：起播超时不再重试同一流

`DefaultFailoverPolicy.decideFailure` 增加一条前置规则（**只对起播阶段生效**）：

```
if (tuning.switchOnStartupTimeout && input.startupFailure &&
    failure.failure == FailureClass.TIMEOUT && hasFreshTarget(input)) {
    startupFailed += activeStreamId        // 本会话不再把这条流当目标
    return switchOrFallback(input, failure) // 有备胎就 SwitchTo(next)，没有则退回 ResolveFresh/GiveUp
}
```

- `FailoverInput.startupFailure`（**新增字段，默认 false**）：协调器**只在该次 prepare 未出首帧就失败**时置 true —— `runSession` 里 `port.watch` 返回 `Err`，或监督循环拿到 `WatchdogVerdict.PrepareTimeout`；`PlaybackPhase.ERROR`（已见过 `PLAYING`）一律为 false。
- `startupFailed` 集合进 `rankedCandidates` 的**排序首键**（排在最后，**不除名**，god 条件 3a）：起播失败的流不会再被"立即切换"选中，但备胎也失败后，后面几轮的有界重试**仍能回到它**——4 s 比实测慢源（0.7–10 s）短，不能因此把慢主源永久丢掉。回退给它的是**完整 12 s** 窗口，所以 6 s 级别的慢源最终仍能出画。
- 单流频道（含交付快照全部 154 台）不满足 `hasFreshTarget`，**逐字保持**原recipe：`RetrySame(≤1) → ResolveFresh → GiveUp + 「无可用源」`。
- `PLAY_FAILOVER` 增加 `stage` 字段（`startup` / `playing`，god 条件 3b）：**只加字段不加码**，切源与 `switch_done` 两条都带，便于 QA/日志一眼区分「起播失败切换」与「播放中失败切换」。

### 4.2 窗口：有备胎频道的**首次** prepare 用 4 s

| 参数 | 值 | 位置 | 说明 |
|---|---|---|---|
| `prepareTimeoutMs` | **12,000 ms（不变）** | `EngineTuning` §7.5 / 协调器 `DEFAULT_PREPARE_TIMEOUT_MS` | 单流频道、以及任何**非首次**尝试的窗口 |
| `fastFirstAttemptTimeoutMs` | **4,000 ms（新增）** | `PlaybackFailoverCoordinator.FAST_FIRST_ATTEMPT_TIMEOUT_MS` | 仅当**这是本会话的第一次 prepare**（`attempt == 1`，尚未发生任何切换/重试）**且**该频道候选 ≥2 时使用；设 `0` 即关闭（全部回到 12 s） |

> **为什么只给"第一跳"**（god 条件 3a 的延伸）：用户第一次点开/换到该频道时，短窗口是纯收益（4 s 就换到备胎）；一旦已经进到「切换/重试」回合，用户已经在等待，此时**耐心**才是让慢主源活下来的东西。若每个回合都用 4 s，一条需要 6 s 的**可用**主源会在 4 s 被判死、备胎又死时来回切，永远等不到出画——这正是要避免的。

**数据支撑（4 s 怎么来的）**

1. 判据侧：故障转移判据 ≤5 s；真机备胎自身起播 729–805 ms（上引）⇒ 主源窗口的预算是 `5,000 − ~800 ≈ 4,200 ms`，向下取 4,000 ms 留余量。
2. 正常路径侧（防止把「慢但活着」的主源扔掉）：交付快照 154 台**全单流**，4 s 窗口在快照上**永不生效**；对 571 台导入清单，G7-1/G7-2 实测首帧 642–2,004 ms（avg 907 / p50 709），4 s ≈ **2× 余量**。
3. 代价（明确写出）：**有备胎**且主源需要 >4 s 才出画时，用户拿到的是**备胎**而不是主源——实测备胎起播 ≤0.81 s，故这种情形下用户**更快**看到画面，但画面来自备胎（备胎按 §4.3 排序键 score ≥55 才被选为备胎）。这是本次「起播超时线 vs 换台等待体验」的取舍点，按 G7-1 §6 观察项①的授权做，**替代方案（保 12 s）会使死主源换台总等待停在 ≈12.8 s**。
