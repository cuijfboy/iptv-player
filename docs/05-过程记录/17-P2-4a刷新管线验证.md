## 3. 预算算术（§6.1 约束推导）

**冻结输入**：单次预算 `budgetMs = 45 min = 2700 s`；候选上限 `capCandidates = 3000`；`PipelineLimits` 并发/超时（Fetch 4/15 s、Shallow 12/6 s、Deep 6/12 s）。

**最坏情形（每一步都打满超时）**

| 阶段 | 并发 | 单项超时 | 波数 | 最坏耗时 |
|---|---|---|---|---|
| Fetch（17 源） | 4 | 15 s | ⌈17/4⌉=5 | **75 s** |
| Shallow（≤3000 候选） | 12 | 6 s | ⌈3000/12⌉=250 | **1500 s（25 min）** |

→ 前半程最坏 **1575 s < 2700 s**（余 1125 s）；即「取回 + 浅校验」在 45 min 内**算术可达**。

**为什么仍必须「截止时间驱动准入」**：Deep 段（P2-4b）最坏 ⌈3000/6⌉×12 s = **6000 s ≫ 2700 s**。原口径「20 min + 4000 候选 + 浅校验 12×6 s」就是被这条算术判死的（冷启动全量 ~33 min 即超预算）。故 45 min/3000 只是把预算放大，**可行性来自增量（健康流 TTL 24 h / 失败流 TTL 6 h 跳过复检）+ 每阶段开始前检查 `remaining < 阶段 p50` 即停止纳入**。

**阶段 p50 表（`StageProfiles`，用于准入判定）**：Fetch 3000 ms / Parse 800 / Normalize 300 / Dedupe 300 / Shallow 1000 / Deep 2500 / Score 500 / Select 300 / Persist 2000。Shallow 1000 ms 取自「HEAD 一次往返（数百 ms）+ 少数需 GET 回退」；Deep 2500 ms 取自 S1 实测 Media3 平均起播 2.14 s。

**准入语义（本包实现）**：Fetch 按「还剩 ≥3000 ms 才纳入下一个源」；Shallow 按**逐条**「还剩 ≥1000 ms 才纳入下一条」（比文档「每阶段前一次」更严，对应派单「超预算就停止纳入新候选」）。超预算 → 收尾并在终态 `RefreshProgress.interrupted = BUDGET_EXCEEDED`。

## 4. 浅校验判定（第一阶段，只判「能不能连上」）

1. `HEAD`（继承源 UA/Referer，超时 = `shallowTimeoutMs`）→ 状态 `2xx/3xx` 即通过；
2. `HEAD` 被拒（运维上很常见的 `403/405`）→ 回退 `GET` + `Range: bytes=0-(shallowFirstBytes-1)`（默认 4 KB），`2xx/3xx` 且读到体即通过；
3. 两腿都失败 → 失败，并把 `FailureClass`（TIMEOUT / NET_UNREACHABLE / HTTP_CLIENT…）带进 evidence，**不把超时误报成「源已死」**；
4. **非 HTTP 协议**（`rtsp/rtmp/udp/rtp`）HTTP 探测不可达 → 记为失败并在 evidence 标 `phase="unsupported"`（诚实标注；真正的处理在 P2-4b 的 Deep/引擎）。

**不做**：真实解码探测、分辨率/编码识别、边沿分片（m3u8 末片→首片）——全部属 P2-4b。

## 5. 预算 / 断点 / 可中断 / 播放避让

- **断点续跑**：每条浅校验结果**即时** `StreamRepository.recordOutcome` 落库（§6.1「每条结果即时落库」）。重入时 `isFresh()` 跳过**健康流（`lastOkAtMs` 24 h 内）**与**失败流（`failCount>0` 且 `lastCheckAtMs` 6 h 内）**；未探测过的流不算新鲜。
- **幂等**：入库走 `UNIQUE(channel_id, url_hash)` 的 upsert，并在写入前把**既有健康度合并进新流**（否则 upsert 会用 `lastOkAtMs=null` 覆盖检查点，续跑失效）。对同一目录跑第二遍：`checked=0`、`okCount=0`、校验器调用数不变。
- **取消语义（§4.5 C5）**：所有挂起点可取消，`CancellationException` 原样重抛；取消收集协程即中止整轮，不会到达 `DONE`。
- **R7 播放避让**：`ConcurrencyGovernor` 在 `respectPlayback=true` 且 `PlaybackPrioritySignal.isPlaybackActive()` 时把 Fetch/Shallow/Deep 并发**减半**（下限 1）。

## 6. 与文档的口径差异（需 arch 追认）

1. **`RefreshSourcesUseCase` 的模块归属**：§4.3 把它列在 `:core:domain`，但它必须同时看到 `:core:source`（`SourceProvider`/`StreamValidator`）与 `:core:domain`（`StreamRepository`），而 §3.2 矩阵**不允许 `source→domain` 与 `domain→source`**。本包落在 `:core:data`（矩阵允许 data→{domain,source,network}），契约类型仍在 `:core:model`（§4.2）。→ 建议 arch 把 §4.3 的该类显式归属 `:core:data`。
2. **Persist 与 Shallow 的顺序**：§6.1 示意图把 Persist 放在最后；本半程**先落候选再浅校验**，以便每条浅校验结果带稳定 id 即时落库（这正是「即时落库」断点要求）。评分/甄选后的最终 Persist 仍属 P2-4b。
3. **`PipelineLimits` 字段**：本包追加了 `shallowFirstBytes`（浅校验 GET 回退的首片字节数），§4.4 原表未列。属加法，建议回写。
4. **id 稳定性**：`:core:data` 的 `ChannelMapper` 仍按「本次装载序号」发 id（P1-2 既有行为），断点合并依赖同一目录的重跑次序一致；P2-1 的 Room upsert 落地后由 `UNIQUE(name_key, group_key)` 提供跨刷新稳定 id，此处的不稳定会消失。
