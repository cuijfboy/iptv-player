## 2. 首次运行判定（派单项 1）

**落点**：`SharedPreferences`（文件 `first-run`，键 `wizard-completed`），端口 `FirstRunStore`。

| 候选 | 为什么不选 |
|---|---|
| Room | 一个新表 + 一次 schema 迁移（`docs/02 §5.1`）为一个不属于任何实体的布尔值；`VERSION` 递增牵动迁移测试与 `2.json` |
| DataStore | 只有 `suspend` 读，会把「去哪个 Activity」变成一个需要 loading 帧的 await；而这个值的全部意义就是**立刻**能答 |
| `SharedPreferences` | 首次加载后是内存同步读，S6 冷启动路径上不加帧；与 P3-3 的 `SharedPrefsOverscanStore` 同一取舍。`FirstRunStore` 接口让换实现只动一个绑定点 |

**路由表（`FirstRunGate.decide`，纯函数）**

| 标记 | 已有证据 | 路由 | 是否写标记 |
|---|---|---|---|
| 已写 | – | `BROWSE` | 否（连读都不读） |
| 未写 | 有 | `BROWSE_UPGRADE` | **是**（升级场景：这次写过以后不再评估） |
| 未写 | 无 | `WIZARD` | 否 |

**升级场景的判定口径**：「已有证据」= 记得住的本地导入（`last-import.json`）**或** `source` 表有行。**频道数不参与判定**：全新安装启动时就已经带内置夹具的 658 台合成频道（`docs/02 §5.1`，`p1-2-fixture`），把它当"用过"会让向导永远不出现。纯夹具用户与全新用户不可区分，而向导不删任何东西——最坏后果是给老用户多看一次向导，比给所有新用户少看一次要好。

**为什么只有"未写标记"才读证据**：常见路径（标记已写）只做一次布尔读，冷启动不加任何仓储访问；`last-import.json` 与 `source` 各读一次只发生在首启判定上。两处读失败一律当作「无证据」（`runCatching`），最坏是多看一次向导，绝不因此崩在启动路径上。

## 3. 三步向导（派单项 2）

### 3.1 控制流

```
MainActivity（启动器；docs/02 §8.1 的 WizardActivity（仅首次）挂在这里）
   │  first-run 标记（同步一次布尔读）
   ├─ 已写 ─────────────────────────────────▶ BrowseActivity   [CLEAR_TASK|NEW_TASK]
   └─ 未写
        │  证据：last-import.json ? source 表行数 ?
        ├─ 有证据（升级）── 写标记 ──────────▶ BrowseActivity   [CLEAR_TASK|NEW_TASK]
        └─ 无证据（首启）──────────────────▶ WizardActivity（ACTION_WIZARD）
                                                │
         ┌──────────────────────────────────────┴───────────────────────────────────┐
         │ ① 选源            ② 更新                    ③ 开看                        │
         │ 内置 17 源全开     自动开始 MANUAL 任务        有频道：写标记 →              │
         │ 继续/跳过          进度/阶段/百分比             BrowseActivity(hint=first-play)
         │ 导入本地清单       中断/重试                   无频道：导入入口（见 §4）      │
         │ 添加订阅           跳过                       跳过：写标记 → BrowseActivity  │
         └──────────────────────────────────────────────────────────────────────────┘

步进：SOURCE ──next/skip──▶ UPDATE ──next/skip──▶ WATCH ──next/skip──▶ FINISHED（交接）
      SOURCE ◀────back───── UPDATE ◀────back───── WATCH
      SOURCE ──back──▶ 退出向导（不写标记 ⇒ 下次启动还会出现）
      UPDATE ──back（在跑）──▶ 先中断，再回 SOURCE
```

### 3.2 各步的内容与动作

| 步 | 界面给什么 | 遥控动作 |
|---|---|---|
| ① 选源 | 内置聚合源清单（逐条列名，全部启用）、已添加订阅数、当前播放列表名、上一次导入结果 | `使用内置源并继续`（默认焦点）/ `导入本地清单` / `添加订阅` / `跳过选源` |
| ② 更新 | 状态行（未开始/排队/阶段+百分比/完成/失败/已中断）+ 不确定进度条 | `开始更新`（未开始时；之后变 `重试更新`）/ `中断更新`（仅运行中显示）/ `跳过更新` |
| ③ 开看 | 频道总数与可播放数，或空表文案 | `进入频道表（按 OK 播放）` / `导入本地清单` / `跳过，直接进入频道表` |

**内置源「全开」是事实陈述，不是开关。** `docs/02 §12` 写「仅内置源清单地址，且可在设置中关闭」，而逐个内置源的开关**至今没有落库位置**（内置 provider 是编译期 `@IntoSet`，`source` 表只存用户订阅）。因此 ① 如实列出「这 17 个会被刷新」，而不是画一组写不进任何地方的复选圈（见 §11 裁决点 2）。

### 3.3 更新步骤怎么做到"同一管线"

| 环节 | 复用什么 |
|---|---|
| 入队 | `RefreshScheduler.enqueueNow(MANUAL)` → 唯一任务名 **`refresh-manual`**（`ExistingWorkPolicy.KEEP`） |
| 执行 | `RefreshWorker` → `RefreshRunCoordinator` → **`RefreshSourcesUseCase`**（P2-4 那条管线，零改动） |
| 前台服务 | WorkManager 的 `SystemForegroundService` + `RefreshNotifications`（P2-5 的 `IMPORTANCE_LOW` 静默通知；"前台服务 + 进度"由此而来） |
| 进度 | `WorkInfo.progress`（本轮给 `RefreshWorker` 加 `setProgress`，把**已经发给通知的同一帧**再发布一次） |
| 中断 | `WorkManager.cancelUniqueWork("refresh-manual")`；管线边算边写、按 TTL 断点续跑（P2-5），所以中断丢的是剩余工作量，不是已写入的行 |
| 失败 | `RefreshWorkOutcome` 的 `result` 载荷（`completed`/`deferred`/`gaveUp`）+ 新增 `error`/`okCount`/`failCount` |

**失败文案**（`WizardUpdateReading` 判 `result` 而不是判 `WorkState`，因为 P2-5 故意让 `gaveUp`/`deferred` 也回 `success`，否则失败的周期任务会带走每日 06:00 的调度）：

| 快照 | 屏幕文案 |
|---|---|
| `FAILED` | 更新失败：源不可用或网络中断（`＜异常类名＞`）。可以重试。 |
| `SUCCEEDED` + `gaveUp` | 更新失败：多次重试后仍未成功（`＜异常类名＞`）。可以重试，或先跳过。 |
| `SUCCEEDED` + `deferred` | 更新已推迟：正在播放，稍后自动重试。 |
| `SUCCEEDED` + 未知载荷 | 更新结束，但结果无法识别（…）。可以重试。 |
| `CANCELLED` | 已中断更新：已经写入的数据保留，可以再点更新继续。 |

## 4. 跳过分支与"跳过后的状态"（派单项 3）

`skip` 与 `next` 走同一条前进边，差别是**跳过被记进状态**（`WizardState.skipped`），并由界面如实说出来；`WizardFlow.back` 回到某步时会把该步的跳过标记清掉，避免"用户其实做了这一步，界面还说跳过了"。

| 步骤 | 跳过动作 | 记录 | 界面后果 |
|---|---|---|---|
| ① 选源 | `跳过选源` | `sourceSkipped=true` | ② 照常自动开始（内置源本来就全开，所以①的继续与跳过效果相同，只有记录与文案不同——这是本轮的诚实取舍）；① 的状态行加「已跳过选源：将直接使用内置聚合源」；`UI_SCREEN_OPEN.wizard` 带 `sourceSkipped=true` |
| ② 更新 | `跳过更新` | `updateSkipped=true` | ③ 顶部加「已跳过更新：频道表可能还是空的，稍后可在设置里手动刷新」；若频道为 0，③ 走**无源分支** |
| ③ 开看 | `跳过，直接进入频道表` | 终态 | 照写完成标记并进频道表，但**不带** `first-play` 提示（不弹「按 OK 播放」、不主动把焦点移到第一个可播放频道） |
| 任意步 | `返回键` | —— | 回上一步；② 在跑时先中断再回①；① 的返回键 = 退出向导（**不写标记** ⇒ 下次启动仍会出现） |

**无源分支（跳过的必然落点）**

1. ③ 开看：`catalogLoaded && channelCount == 0` → 文案「还没有可播放的频道：可以导入本地清单，或回到第 2 步更新内置源。」，`进入频道表（按 OK 播放）` **置灰**、焦点落到 `导入本地清单`（D-pad 不会停在禁用按钮上，第一步仍可达）。
2. 频道表本身：`channelCount == 0` 时头部从「频道 0 / 分组 0 / 流 0」改成「频道表是空的：请用上面的『导入播放列表』导入本地清单，或到设置 → 源管理里加订阅后刷新」。
3. 单测钉住：`WizardViewModelTest.开看 says there is nothing to watch…` 与 `开看 follows a refresh that lands while the screen is open`（刷新在用户停在③时落地，计数必须跟着目录走，而不是③打开时的快照）。
