## 3. 取舍与契约（请 god/arch 过目）

### 3.1 Media3 还是 compat：**选 media3（`media3-session` 1.6.1）**
与引擎同族（`media3-exoplayer` 已是主引擎）、版本在 `libs.versions.toml` 单一来源；`MediaSessionService` 一个组件同时给到「媒体键路由 + 前台服务 + 通知」三件事，而 `MediaSessionCompat` 的媒体键要自己配 `MediaButtonReceiver` + MediaBrowserService 才通。证据：`Last MediaButtonReceiver: ComponentInfo{ilab.iptv.player/androidx.media3.session.MediaButtonReceiver}`。

### 3.2 前台服务落位 `:feature:player`（**偏离 `docs/02 §7.2 P1`**，同 P1-5 的控制器偏离）
§7.2 写「由 `:app` 的 `PlaybackService` 持有」，但 §3.2 规则 3 禁止 `:app` 直接声明 `:core:player`，而这个服务的全部工作就是驱动 `PlaybackSession`。`:feature:player` 是矩阵里唯一同时可见 `:core:player`（规则 4）的模块。**请 arch 回写 §7.2 P1 的落位。**

用 `@EntryPoint` 而不是 `@AndroidEntryPoint`：Hilt 只接受**直接**继承 `Service` 的类，`MediaSessionService` 会被拒（实测报错 `base class must extend ComponentActivity, ..., Service, or BroadcastReceiver`）。图与作用域不变。

### 3.3 失焦取舍（工作项 3 要求写进本文件）

| 焦点事件 | 动作 | 理由 |
|---|---|---|
| `LOSS_TRANSIENT_CAN_DUCK` | **降音**（`ExoPlayer.volume = 0.2`），不暂停 | 直播是「边沿」：暂停意味着回来时缓冲已过期，恢复要重新起播（S5：好源 ~0.9 s，差源数秒）。降音保住用户正在看的频道；代价是别的应用说话时我们仍占带宽——所以只在这一行降音 |
| `LOSS_TRANSIENT` | 暂停，`GAIN` 时恢复 | 对方要独占输出（如通话），静音缓存没有意义 |
| `LOSS`（永久） | 暂停 + **归还焦点**，不自动恢复 | 谁拿走焦点谁做主；下次 `GAIN` 就抢回来会和新的持有者打架 |
| 会话结束 | 归还焦点 | 否则电视上下一个应用被一个不发声的持有者卡住 |

引擎侧 `setAudioAttributes(..., handleAudioFocus = false)`（P1-3 既有）→ 焦点请求/释放由本包独占持有，策略可单测。

### 3.4 通知自己做，不用 `DefaultMediaNotificationProvider`
工作项 1/2 要求通知带频道名，P1-5 的「正在切换备用源…」和失败文案也要出现在同一处，所以覆写 `onUpdateNotification` 自绘通知（`PlaybackServiceLifecycle` 决定前台/移除，`PlaybackNotificationContent` 决定文案与按钮）。代价：Media3 内部的「是否在前台」记账不再使用（其 `shouldRunInForeground` 只看控制器 `playWhenReady`，与本实现无冲突，已核对 1.6.1 源码）。

### 3.5 新增依赖与事件码
- `media3-session 1.6.1`：与引擎同版本，进 `libs.versions.toml` 单一来源。
- **未新增事件码**：`docs/03 §3.3` 的 46 码表与 `EventCodesTest`（断言 46）本轮不可改（边界：不改 `docs/01–04`）。因此前台服务/焦点/网络三组日志**没有专属码可用**，本轮不写这些日志（证据用 dumpsys + 单测）。**建议 arch/god 增补**：`SERVICE_PLAYBACK_START/STOP`、`PLAY_FOCUS_CHANGE`、`PLAY_NET_RETRY`（见 §7.3）。

## 6. 本轮发现的真实缺陷

### 6.1 失焦后被自己"抢回"（真机发现，已修）
第一版在**每次前台/通知刷新**时再请求一次焦点。后果链条：别的应用抢焦 → 策略暂停并归还 → 暂停让相位离开 `PLAYING` → 通知刷新 → **又请求焦点** → 这次授权是 `GAIN` → 策略恢复播放。真机实测（`11-audio-focus-loss.txt`）：VLC 01:39:03 请求焦点，本应用 01:39:05.703 归还、**13 ms 后**又请求，VLC 01:39:07 主动放弃焦点——两个应用在抢音频输出。
修法：焦点请求**只跟随实际播放**（相位 `PLAYING` 且未持有才请求），见 `PlaybackService.syncFocus` 的注释；修复后同一实验里栈顶归 VLC、本应用保持暂停（`21-focus-loss-fixed.txt`）。

### 6.2 服务生命周期初值会把刚起的服务拆掉（写下时发现，已修）
`PlaybackSession.state` 是 `StateFlow`，观察者订阅时立刻收到初值；若上一会话是 `STOPPED`，`onPlaybackState` 会判定"播放已停止"→ `stopSelf`，而此时 `onStartCommand` 还没到。修法：`IDLE/STOPPED/RELEASED` 只在**已经进过前台或后台**时才收尾，并加 1 条单测锁住。

### 6.3 Hilt 不接受 `MediaSessionService` 基类（构建错误，已绕开）
`@AndroidEntryPoint` 要求直接父类是 `Service`。改用 `@EntryPoint` + `EntryPointAccessors`（§3.2）。

### 6.4 看门狗会把 MediaSession 暂停当卡顿（设计评审时发现，已修）
遥控/通知/系统媒体控制都经 MediaSession 暂停引擎，绕过了控制器自己的 `paused` 标志；看门狗若只看位置不动就会在 8 s 后"救"成换源。修法：`EngineSample` 增 `playWhenReady`，`isPausedByUser` 参与暂停判定（用 `playWhenReady` 而非 `isPlaying` 才不会掩盖真实冻结），加 1 条单测。

## 7. 未做项与开放项

### 7.1 网络恢复重试：真机端到端未做（**重要**）
