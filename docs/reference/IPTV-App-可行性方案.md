# 从「更新器」到「IPTV 观看 App」——可行性分析与设计方案

> 结论先行：**技术上完全可行**，而且我们已经完成了大约一半的「非播放」工作。
> 但真正决定成败的不是「能不能播出一个流」，而是 **播放引擎选型** 与 **构建方式（是否迁 Gradle）** 这两个岔路口。
> 本文档只做分析与方案，不含任何实现代码。

---

## 0. 结论速览

| 问题 | 回答 |
|---|---|
| 现在加了播放 + UI 就是 IPTV App 了吗？ | 能力上**差三块**：①播放引擎 ②TV 交互 UI ③频道/EPG 持久化 |
| 可行性 | **高**。风险集中在引擎选型、AC3/EAC3 音频、以及 AAR 依赖带来的构建改造 |
| 最大岔路口 | **A. 零依赖 + framework MediaPlayer** ｜ **B. 迁 Gradle + Media3/ExoPlayer** ｜ **C. 迁 Gradle + libVLC** |
| 建议路径 | 先做 2 个各 1 天的 Spike 用数据定调，再分 P1→P4 四期建设 |
| 与 TiviMate 的关系 | 现状**已经能看**（TiviMate/Kodi + 我们产出的 658 台 + guide.xml）。自研价值在「完全自主 + 开源 + 自带验证与自动故障转移」，代价是要追上成熟度需大量打磨 |

## 2. 逐项可行性深入分析

### 2.1 播放引擎（最关键）

#### A. framework MediaPlayer（零依赖）
- 优点：零依赖、零体积增量、零构建改造；我们已经在用它做探测
- 缺点：HLS 支持基础（无自适应码率、错误恢复弱、部分非标 m3u8/TS 会失败）；没有细粒度缓冲控制；音轨/字幕选择能力有限
- 定位：**「能看」级别**，适合先跑通闭环（P1）

#### B. ExoPlayer / AndroidX Media3（业界标准）
- 优点：Android TV IPTV 的事实标准（TiviMate、Jellyfin 均用）；HLS 直播优化好、重试容错强、支持音轨与字幕选择、AC3/EAC3 支持、缓冲可控
- 缺点：分发形态是 **AAR**（含资源与清单），**手工链无法直接吃**，必须迁 Gradle 或手工合并资源；带 Kotlin stdlib，体积 **+1.5～3 MB**
- 定位：**「好用」级别的必选项**，对应 P3

#### C. libVLC（兼容性最强）
- 优点：几乎什么都能放（非标 TS、老 RTSP、奇异封装）；我们电视上已装 VLC 3.7.1 可作对照
- 缺点：**native .so**，armeabi-v7a 约 **25～30 MB**；同样需要 AAR + jni；体积与内存代价大
- 定位：**终极兜底**，可作为「引擎二」按流自动降级

> 补充第四种 mpv/libmpv：能力强但 Android TV 生态与文档不如前两者，不建议首选。

**推荐策略：引擎抽象 + 双引擎** —— P1 用 MediaPlayer 跑通；P3 迁 Media3 为主；对 Media3 失败的流自动降级到 libVLC（按需，不默认打包）。

### 2.2 构建与依赖（第二岔路口）

我们现在的链路是：aapt2 compile → aapt2 link → javac → d8 → zipalign → apksigner，**纯 JAR 友好、AAR 不友好**。

| 方案 | 说明 | 代价 |
|---|---|---|
| 保持手工链 | 只用 framework API（MediaPlayer / ListView / SQLiteOpenHelper / MediaSession）与纯 JAR 三方库 | 用不了 AndroidX / ExoPlayer / VLC |
| 手工吃 AAR | 解出 classes.jar 给 d8；AAR 的 res 用 aapt2 合并；手写 manifest 合并 | 资源 ID 冲突、易碎、不可持续 |
| **迁 Gradle + AGP** | 依赖解析、AAR/资源/清单合并、R 类全自动 | 需准备 platforms;android-36（当前只有 android-36.1，需装 cmdline-tools） |

> 诚实结论：**一旦要做播放器，迁 Gradle 基本绕不过去**。手工链是「快速验证 MVP」的利器，不是「做产品」的长久之计。

### 2.3 交互控制 UI（工作量最大的一块）

Android TV 的核心是**焦点导航（D-pad）+ 大屏可读性**。需要这些屏幕：

| 屏幕 | 内容 | 要点 |
|---|---|---|
| 首页 / 分组 | 分组卡片（央视/卫视/港澳台/地方）+ 收藏 | 焦点态要明显 |
| 频道列表 | 左侧频道列表（含分组过滤），右侧实时预览或台标 | 658 台必须虚拟化，否则卡 |
| 全屏播放 + 信息条 | 上/下换台、OK 呼出信息条：频道名、now/next 节目、进度 | 信息条几秒后自动隐藏 |
| **EPG 时间网格** | 横轴时间、纵轴频道、当前时间竖线、节目块可点 | **最难**：自定义 View + Canvas 绘制才够流畅 |
| 频道管理 | 收藏、隐藏、排序、频道号编辑 | 需落库 |
| 设置 | 源管理、EPG 源、自动更新、缓冲/解码、宽高比 | 复用现有能力 |
| 首次向导 | 一键更新 → 生成列表 → 开始观看 | 把现有能力串成流程 |

技术选择：
- **零依赖路线**：framework 的 ListView / 自定义 View + Canvas 画 EPG 网格（可行且高效，样式要自己搭）
- **AndroidX 路线**：Leanback + RecyclerView，组件现成，但要 Gradle

### 2.4 持久化

| 方案 | 说明 |
|---|---|
| framework SQLiteOpenHelper | 零依赖，可直接用；需手写 SQL 与迁移 |
| Room（AndroidX） | 类型安全 + 迁移管理，但需注解处理器与 Gradle |

建议表：channel（频道号/分组/收藏/隐藏/logo）、stream（一频道多 URL、优先级、上次可用）、programme（start/stop/channel）、source、settings。
数据量很小（658 频道 / 数千节目），SQLite 绰绰有余。

### 2.5 播放行为要求（决定「像不像一个 IPTV App」）

| 行为 | 要求 | 说明 |
|---|---|---|
| 换台速度 | 目标 **1.5–3 秒** | HLS 起播物理下限；靠播放器复用、失败快速跳过 |
| **自动故障转移** | 主源失败→自动切备胎 | **我们已经每台存 2 条流，天生有优势** |
| 卡顿重连 | 缓冲停滞 N 秒自动重建 | 引擎能力 + 看门狗 |
| 网络变化 | 断网恢复后自动重试 | 监听网络状态 |
| 音频 | AC3/EAC3 **透传** | 国内源常见 AC3，Sony 电视通常支持透传，**必须实测** |
| 显示 | 宽高比（原始/16:9/4:3/拉伸）、过扫描微调 | 老源常见 4:3 |
| 音轨/字幕 | 多音轨可选、字幕开关 | 部分源有 |
| 后台/回桌面 | 前台媒体服务，保证不被屏保杀掉 | 我们已踩过屏保冻结的坑 |

### 2.6 设备与系统约束

| 约束 | 影响 | 对策 |
|---|---|---|
| **仅 32 位 armeabi-v7a** | 排除只提供 arm64 的库 | Media3/MediaPlayer 无原生码，安全；libVLC 需 v7a .so |
| 3 GB 内存 / MT5895 | UI + 播放 + 后台刷新并存 | EPG 网格 Canvas 绘制、列表虚拟化、限制并发 |
| **Sony 环境屏（DreamActivity）** | 切后台会冻结进程 | 媒体前台服务 + 保持屏幕常亮 |
| 无 root | 不能改他人 App 配置 | 本应用自包含，无影响 |
| 遥控器 | 无触摸；Sony 遥控有数字键 | D-pad 全导航 + 数字键快速跳台 |
| 明文 HTTP | 已解决 | 保持 usesCleartextTraffic |
| 音频透传能力 | 不确定 | **必须 spike 实测** |

## 3. 架构设计（模块划分）

~~~
┌─────────────────────────── App ───────────────────────────┐
│ ui/        TV 界面：频道列表 · EPG 网格 · 播放覆盖层 · 设置   │
│ player/    引擎抽象 PlayerEngine + 状态机 + 故障转移看门狗    │
│ data/      SQLite：channel / stream / programme / settings  │
│ epg/       节目表导入、now-next 查询、刷新调度               │
│ source/    采集 · 解析 · 去重 · 两阶段校验（已有）            │
│ service/   更新服务 · EPG 刷新 · 播放前台服务(MediaSession)  │
│ core/      Http(OkHttp) · 日志 · 设置 · 工具                 │
└────────────────────────────────────────────────────────────┘
~~~

关键接口（先定契约，便于双引擎替换）：
- PlayerEngine：prepare(url, headers) / start / stop / release / 状态回调 / 选音轨字幕 / 设宽高比
- ChannelRepository：按分组与收藏查询、取主源与备胎、记录上次可用
- EpgRepository：now/next、按时间窗查询节目
- FailoverController：错误或超时 → 切备胎 → 重试 → 给该源降权

## 4. UI 交互设计要点

- **换台**：全屏下 D-pad 上/下 = 上一台/下一台；数字键 = 直接跳台；OK = 呼出信息条
- **信息条**：频道名 + 台标 + now/next 节目 + 时间进度，5 秒无操作淡出
- **EPG 网格**：纵轴频道（虚拟化）、横轴时间（滚动）、当前时间红线、节目块点击弹详情；658 台 × 数小时节目必须 Canvas 绘制
- **焦点**：所有可点元素要有清晰焦点态；返回键层级一致（播放 → 列表 → 分组 → 退出）
- **首启向导**：更新 → 生成列表/EPG → 选分组 → 直接进第一台

## 6. 动工前必须先做的 Spike（用数据定调）

| # | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
| S1 | framework MediaPlayer 播放能力 | 取 20 个已验证频道循环播放 | 成功率、起播耗时、失败样本特征 |
| S2 | Media3/ExoPlayer 对比 | 同批流，Gradle + Media3 | 成功率提升多少？值不值得迁 Gradle |
| S3 | **AC3/EAC3 透传** | 挑 AC3 音轨频道实测 | 有声音；无声则需软解或换源 |
| S4 | Gradle/AGP 兼容 | 本机装 platforms;android-36，跑通空工程 | 能产出 APK |
| S5 | EPG 网格性能 | 658 频道 Canvas 原型 | 滚动 ≥50 fps，内存增量可控 |
| S6 | 换台体验 | 连续换台 30 次 | 平均 ≤3 秒，无内存泄漏 |

**只有 S1/S2 出结论后再定引擎；S4 出结论后再定构建方式。**

## 7. 风险清单与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 引擎选错 | 大面积返工 | P0 双引擎 Spike，先抽象接口再实现 |
| AAR 无法手工处理 | 构建链推倒重来 | 尽早迁 Gradle（S4） |
| AC3/EAC3 无声 | 高码率频道「有画面没声音」 | S3 实测；不行就引擎降级到 libVLC 或过滤该音轨 |
| **EPG 覆盖仅 9%** | 节目单大面积空白 | 增加 EPG 源、按频道别名多源匹配、允许用户自填 |
| 流随时失效 | 今天能看明天不能 | 自动故障转移 + 周期复检（已有能力）+ 降权淘汰 |
| 换台慢 | 体验硬伤 | 播放器复用、缓冲调优、失败快速跳过、数字键跳台 |
| 内存/性能 | 卡顿、被杀 | 虚拟化列表、Canvas 绘图、限制并发、及时 release |
| 合规 | 法律风险 | 不内置源、源由用户配置、保留声明 |

## 8. 与 TiviMate / Kodi 的关系（要不要自研）

**现状**：电视上已有 TiviMate（658 台 + guide.xml）与 Kodi（658 台 + 61 频道 EPG）可用。

| 选择 | 适合 |
|---|---|
| 继续用 TiviMate / Kodi | 目标是「看节目」→ **这是性价比最高的答案** |
| 自研 App | 目标是「完全自主、开源、可改」，并看重「自己验证过的源 + 备胎自动切换 + 本机定期复检」的组合 |

自研真正能差异化的三点：
1. **验证与播放一体**：只有它知道哪些源「在这台电视上刚刚验证过」
2. **备胎自动切换**：每台 2 条流，失败即切
3. **开源可控**：无广告、无订阅、可定制

但必须承认：**TiviMate 的成熟度（EPG 网格、录制、多播放列表、稳定性）不是短期能追上的。**

## 9. 合规提醒

完整的 IPTV 观看 App 若**内置**抓取来的源，性质就从「技术工具」变成「分发未授权内容」。
建议：**App 不带源**，源由用户自行配置或导入；保留声明；不集成任何付费内容或绕过 DRM 的能力。

## 10. 建议的下一步（等你确认）

1. **先做 P0 的 S1+S2+S3**（约 2–3 天有效工作量）——这是唯一能用数据回答「该用哪个引擎、值不值得迁 Gradle」的方式
2. 拿到结论后再决定是否进入 P1
