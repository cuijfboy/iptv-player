## 1. 设计目标与原则

| 原则 | 落地手段 |
|---|---|
| **单向依赖** | 依赖只允许由外向内：`feature → domain ← data → platform`；domain/model 不依赖 Android |
| **依赖倒置** | domain 定义**端口（interface）**，data/platform 提供**适配器（implementation）** |
| **纯策略可测** | 选台、评分、故障转移、匹配等**决策逻辑为纯 Kotlin**，零 Android 依赖，可直接单测 |
| **平台能力隔离** | 播放器、数据库、网络、XML 解析被封装在平台模块，替换实现不影响上层 |
| **可插拔扩展** | 源、校验器、评分规则、播放引擎、EPG 源、日志 Sink 全部以"集合 + 接口"方式注册 |
| **异常不跨边界** | 模块间用 `AppResult<T>` 传递失败，禁止异常穿透模块边界 |
| **可观测内建** | 每个关键路径都有**事件码**；日志是架构的一等公民，而非事后补丁 |
| **可中断/可恢复** | 长任务（源刷新、EPG 导入）持久化进度，随时可被杀掉并续跑 |
| **性能预算前置** | UI/刷新/播放都有量化指标与埋点，回归可度量 |

## 2. 分层模型

```
┌──────────────────────────────────────────────────────────────────────────┐
│ L4 表现层 Presentation                                                    │
│   :app  ·  :feature:channels  :feature:player  :feature:epg               │
│   :feature:settings  :feature:wizard  ·  :core:ui  ·  :core:design        │
│   职责：View / Fragment / Activity / ViewModel / UiState（单向数据流）      │
│   规则：只调用 domain 的 UseCase；不直接触碰 Room / OkHttp / ExoPlayer      │
└───────────────────────────┬──────────────────────────────────────────────┘
                            │ 依赖 UseCase + 领域模型
┌───────────────────────────▼──────────────────────────────────────────────┐
│ L3 领域层 Domain                                                          │
│   :core:domain（纯 Kotlin）  ·  :core:model（纯 Kotlin）                   │
│   职责：UseCase / 领域模型 / 仓储端口(Port) / 纯策略(选源·评分·故障转移)     │
│   规则：零 Android 依赖；不出现 okhttp / room / media3 类型                 │
└───────────────────────────┬──────────────────────────────────────────────┘
                            │ 依赖倒置：domain 定义接口
┌───────────────────────────▼──────────────────────────────────────────────┐
│ L2 数据层 Data                                                            │
│   :core:data（仓储实现）  :core:database（Room）  :core:network（OkHttp）   │
│   职责：Repository 实现、DTO↔Entity↔Domain 映射、缓存与事务                 │
└───────────────────────────┬──────────────────────────────────────────────┘
                            │ 使用平台能力
┌───────────────────────────▼──────────────────────────────────────────────┐
│ L1 平台层 Platform                                                        │
│   :core:source（采集/解析/校验）  :core:epg（XMLTV）  :core:player（播放）   │
│   职责：将 Android/第三方能力适配为可替换的引擎实现                          │
└───────────────────────────┬──────────────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────────────────┐
│ L0 基础设施 Common（被所有层依赖，自身不依赖任何业务）                       │
│   :core:common（AppResult/Logger 接口/Dispatcher/Clock/事件码）             │
│   :core:log（日志实现：内存环 + 文件 + logcat + 崩溃）                       │
└──────────────────────────────────────────────────────────────────────────┘
```

**关键解耦点**：*`FailoverPolicy` / `StreamSelector` / `ScoringRule` 是**纯 Kotlin 策略**（L3），`PlayerEngine` 是**平台适配器**（L1）*。因此"何时切源"可以脱离 Android 单测，"怎么播"可以整体替换（Media3 ⇄ libVLC ⇄ 未来引擎）。

> **`:core:design`（token）与 `:core:ui`（组件）的分界（卡 `DOC-12`，P3-7 裁决）**：**颜色/尺寸/字体这类「值」放 `:core:design`**（`values/colors.xml` + `values/dimens.xml` + `TvFocus.kt`），**可聚焦控件这类「行为」放 `:core:ui`**（`ChannelCardView` `FocusExt` `TvDialog`）。理由：EPG 网格的渲染器是**纯 Kotlin**（刻意不依赖 `android.graphics`、不读资源），只能吃 int 常量，所以焦点色必须有**一份非资源形态**——`TvFocus` 与 `colors.xml` 是**同一契约的两半**，`TvFocusTokenTest` 读回 XML 逐值比对，漂移即失败。**不要**在 `:core:ui` 里再定义一套焦点色，也不要把组件搬进 `:core:design`。

**守护规则（CI 强制；只约束「直接声明」）**：

1. `:core:domain` / `:core:model` / `:core:common` 为 **`java-library`（Kotlin JVM）**，**源码**（`src/`）中出现 `android.` / `androidx.` 引用即失败（`verifyPureKotlin`，含无 `import` 的全限定写法）；
2. `:feature:*` **不得直接声明** `:core:database` / `:core:network` / `:core:source` / `:core:epg`（只能经 domain 端口）；
3. `:app` **不得直接声明** `:core:database` / `:core:network` / `:core:source` / `:core:epg` / `:core:player`；Hilt 绑定由 `:core:data` 提供，`:app` 只做组装；
4. 唯一例外：只有 `:feature:player` 可直接声明 `:core:player`（`PlayerEngine` 是 UI 直连的平台适配器，见 §4.5 规则 C2）；其余 `feature:*` 一律经 domain 端口；
5. **传递依赖不违规，但中间模块必须用 `implementation` 暴露**（不得用 `api` 把内部依赖转出去）；禁止循环依赖。

> **口径与实现（god 裁决 2026-09-21，BUG-002 / CR-03 收口）**：守护以**本矩阵为唯一数据源**，由约定插件 `iptv.module.dependencies`（任务 `verifyModuleDependencies`，挂到 `check`）在构建期校验各模块的 `project(":…")` **直接声明**；传递依赖不算违规，但中间模块必须用 `implementation` 暴露（用 `api` 转出内部依赖会判失败——反证 B：`:core:data` 把 `:core:database` 由 `implementation` 改 `api` → `rule 5 … FAILED`）。本版矩阵按实测修正了两处与规则文字矛盾的地方：`:app` 行原先错标 `database`/`player` 为 ✅（实测 `:app` 的 `releaseRuntimeClasspath` 顶层**不含** database/network/source/epg/player），并补上 `:core:testing` 列/行。规则 1 的守护只扫源码（不扫构建脚本），构建脚本里的依赖声明由本条矩阵守护覆盖（CR-02 同源）。

> **职责三分：引擎=机制 / 策略=domain / 协调=feature（god 裁决 2026-09-22，卡 `DOC-6`；与 `05-过程记录/20-P1-5换台与故障转移验证.md` §8.1 同源，本矩阵仍是唯一判据）**：
> - **机制 = `:core:player`** —— 引擎适配与引擎侧状态机（`PlayerEngine` / `Media3Engine` / `PlaybackSession`），只对上暴露窄钩子（`sample()` 采样、呈现回调、`onRenderedFirstFrame` 等）。矩阵中 `:core:player` 行**没有** `domain` 列 ⇒ 它**不得**直接声明 `:core:domain`。
> - **策略 = `:core:domain`** —— `FailoverPolicy` / `DefaultFailoverPolicy` / `PlaybackWatchdog` 与 `FailoverAction` 等纯策略（§4.3）：零 Android、100% 可 JVM 单测。
> - **协调 = `:feature:player`** —— `PlaybackFailoverCoordinator` 把机制与策略接起来（会话循环：prepare → 看门狗监督 → 决策 → 再 prepare），是 `PLAY_PREPARE_START` / `PLAY_FIRST_FRAME` / `PLAY_FAILOVER` / `PLAY_STALL` / `PLAY_SWITCH_CHANNEL` 的**唯一发出者**。`feature:*` 行允许同时声明 `domain` 与 `player`（规则 4），因此只有这一层能同时看见机制与策略。
>
> **因此不要把故障转移协调器放进 `:core:player`**：那需要 `:core:player → :core:domain`，会直接违反本矩阵（`verifyModuleDependencies` 判失败）。

> **`SourceKind` 与「本地文件」来源口径（卡 `DOC-5`，对齐 P2-6 本地导入实现，`f9574ba`）**：
> - `SourceKind` 描述**源怎么送达**：`M3U` / `TXT` 是当前解析器**唯一产出**的两种（按正文自动识别，不看扩展名）；`XTREAM` / `JSON` 是预留的订阅/接口源；**`LOCAL_FILE` = 来自设备本地文件的源**（用户在应用内选中的清单），是冻结枚举里的**预留值**。
> - **来源标识用 `channel.source_id`**：内置夹具 = **`p1-2-fixture`**（`AssetBundledPlaylist.DEFAULT_SOURCE_ID`）；本地导入的清单 = **`local:<文件名>`**（`LocalPlaylistImport.sourceIdFor`，如 `local:mylist.m3u`）。导入是**整体替换**当前频道表，因此任一时刻 `source_id` 要么是夹具、要么是一个 `local:` 导入，二者不会同时在表里。
> - **实现现状**：P2-6 最小可用尚未把 `SourceKind` 写进任何表/配置（频道表只有 `source_id` 文本列），`LOCAL_FILE` 目前只用于**语义表达与未来的 `SourceConfig.kind`**，解析器不产 `LOCAL_FILE`；订阅 URL 管理、SAF/持久化 URI 属 P2-6 正篇。

> **`deepFirstBytes` 语义（卡 `DOC-7`，对齐 P2-4b，`f7a8bbe`）**：深探（`DEEP`）**只取每腿的首片字节**——`GET` 清单 → 首个变体 → **直播边沿分片（末片，失败再试首片）**，读到分片 `2xx` + 有 body 即通过，**不做长播放、不建渲染管线、不等首帧**（P2-4b 界内要求）。因此 `deepFirstBytes = 256 KiB` 是「一份清单或一段分片前缀」的上限，远小于真实播放缓冲；拿到的是**清单声明的** `vcodec/acodec/分辨率`（除非绑定了 Media3 `TrackProbe` 真解码，`:core:source` 侧接缝，未接线时标 `codecSource=declared`）。同一语义对直连 TS/裸流：`GET` 到字节即「能拉到」，同样不播。

### 4.5 并发与线程契约（冻结）

| # | 规则 |
|---|---|
| C1 | **状态单一写者**：`PlaybackController` 是 `PlaybackUiState` 的唯一写者；`PlayerEngine` 只暴露 `EngineState` 与 `PlaybackEvent`，UI **不得**订阅引擎。`EngineState → PlaybackPhase` 映射：IDLE→IDLE、PREPARING→PREPARING、READY/BUFFERING→BUFFERING、PLAYING→PLAYING、ENDED/RELEASED→STOPPED、ERROR→ERROR；发生切换决策时置 `FAILOVER`（覆盖映射） |
| C2 | **引擎线程**：一个进程内 **1 个** `PlayerEngine` 实例；`attach/prepare/play/pause/stop/release/setAspectRatio` 全部在 `DispatcherProvider.engine`（单并行度）上串行执行；`prepare` 由 `Mutex` 互斥——新请求到达时**取消旧请求并等待其清理完成**，再执行新请求 |
| C3 | **流水线并发**：并发上限与超时只在 `PipelineLimits` 定义，各阶段用 `Semaphore` 背压；播放会话进行中且 `respectPlayback=true` 时，Fetch/Shallow/Deep 并发减半 |
| C4 | **数据库**：只在 `:core:data` 调用；批量写按 `PipelineLimits.batchSize=500` 行/事务；`Metric` 写入与节目表修剪不得与播放路径共享线程 |
| C5 | **取消语义**：所有长任务响应 `CancellationException` 并重抛；播放会话取消 = `stop()` + 释放引擎 + 结束前台服务 |
| C6 | **作用域**：只用注入的 `AppScopeProvider.appScope` / 会话级 `CoroutineScope`；禁止 `GlobalScope`、禁止 `runBlocking`（测试除外） |

### 4.6 错误模型（冻结：现象 → 分类 → 策略动作）

| 现象 | `FailureClass` | `retryable` | `FailoverPolicy` 动作（§6.2 生效） |
|---|---|---|---|
| HTTP 403 / 404 / 410 | `HTTP_CLIENT` | false | `SwitchTo(next)` + 该流永久降权 |
| HTTP 429 / 5xx | `HTTP_SERVER` | true | `Backoff(1s)` → `RetrySame(≤1)` → `SwitchTo(next)` |
| 连接/读取超时 | `TIMEOUT` | true | **起播阶段（未出首帧）且仍有备胎 → 立即 `SwitchTo(next)`**（首跳耐心窗 4 s，见 §6.2）；**播放中** → `RetrySame(≤1)` → `SwitchTo(next)` |
| DNS 失败 / 网络不可达 | `NET_UNREACHABLE` | true | `SwitchTo(next)` 优先换源 |
| TLS 握手失败 | `TLS` | false | `SwitchTo(next)` |
| 清单/EPG 解析失败 | `PARSE` | false | 播放：`SwitchTo`；刷新：该源标记失败（不阻塞其他源） |
| 解码器不支持该编码 | `DECODE_UNSUPPORTED` | false | `SwitchTo(next)` + 该 codec 组合记负权 |
| 解码中断/花屏（流损坏） | `DECODE_CORRUPT` | true | `RetrySame(≤1)` → `SwitchTo(next)` |
| **环境闸门**（网关/WAF/CDN 返回 418 / 451 / 511 / 605） | `HTTP_CLIENT` / `HTTP_SERVER`，但 `AppError.origin = ENV_GATED` | true | 当轮仍按上表动作，但**不写长期 score、不进永久降权、不记为源失效**（`ENV-1`，god 批准 2026-09-23）；短文案「网关未放行」 |
| 清单为空 / 无分片 | `EMPTY_MEDIA` | false | `SwitchTo(next)` |
| 频道所有候选均失效 | `PLAYLIST_GONE` | false | `ResolveFresh`（单频道按需复检）→ 仍失败则 `GiveUp` + UI「该频道暂时不可用」 |
| 设备不支持（无解码器/无音轨） | `NO_CAPABILITY` | false | 先关透传重试一次 → `SwitchTo(next)` |
| 数据库/存储写入失败 | `STORAGE` | true | **不切换**：内存态继续可用，报错降级，下次启动重试 |
| SAF/存储权限缺失 | `PERMISSION` | false | 引导用户授权，不重试播放 |
| 协程取消 | `CANCELLED` | false | 不视为失败，不发 `PLAY_FAILOVER` |
| 其他 | `UNKNOWN` | false | 记 `ERROR` 事件 + `SwitchTo(next)` |

**看门狗（停滞）不是 `AppError`**：`StallSignal` 由 §6.2 看门狗直接产出 → `Backoff(1s)` → `SwitchTo(next)`。

> **索引与幂等（W4，冻结）**：`stream` 唯一键为 `UNIQUE(channel_id, url_hash)`；`channel` 唯一键为 `UNIQUE(name_key, group_key)`；`programme` 唯一键为 `UNIQUE(epg_channel_id, start_ms)` 且写入用 `INSERT OR REPLACE`，窗口修剪按 `epg_channel_id` 批量删除。原始唯一索引会挡住"同一 URL 服务多频道"（同源多台）与"跨分组同名台"两类真实数据。落库实现由 dev-A 在 P0-3 执行。

> **`group_key` 推导（god 决策 2026-09-22，卡 `DOC-3`）**：`group_key` = **分组标题的归一化键**——取 M3U 的 `group-title`（缺省时用 `#EXTGRP`，TXT 取第三列，仍缺则视为无分组），做归一键（全角→半角、去空白、小写，算法同 `name_key`）；**缺失时回落 `other`**。`group_title` 另存**原始标题**用于显示，两者不同职责。
> **理由**：`group_key` 参与 `UNIQUE(name_key, group_key)`，必须是"这份播放列表里的分组身份"。若用固定的 5 个枚举值（如 `新闻/体育/…`）当键，**跨分组同名台会被错误合并成一条**（正是 W4 要避免的那类真实数据）。键用归一化标题后，同一列表内分组名相同即同组、不同即不同组，行为可预测。

> **schema v1 → v2：两列 user-owned 覆盖位（卡 `DOC-10`，P3-4 `b533c3e`）**：`channel` 表新增 **`display_name TEXT NULL`**（用户改的显示名；NULL = 用源名）与 **`user_group_title TEXT NULL`**（用户移动到的分组标题；NULL = 用源分组），两列都 **user-owned**——刷新/导入合并时**保留**，不被源数据覆盖。迁移 **`MIGRATION_1_2`** = 两条 `ALTER TABLE channel ADD COLUMN`（**无默认值、无回填**：老行两列皆 NULL，升级前后行为逐字相同）；`IptvDatabase.VERSION = 2`，导出 schema `schemas/…/2.json` 已入库（`MigrationBaselineTest` 改为「v2 为当前版本、`ALL` 恰为 `(1→2)`」，新增 `Migration_1_2Test`）。
> **口径与理由**：① **改名只写 `display_name`，绝不写 `name`/`name_key`** —— 去重身份 `UNIQUE(name_key, group_key)`、刷新合并、EPG 匹配全按 `name_key`，改名若动它就会"改个名变成另一台"（去重失效、自动合并产生重复行）；显示名单独存，列表/信息条用 `Channel.shownName`（= `display_name ?: name`）。② **移动分组只写 `user_group_title`，身份列 `group_key` 不动** —— 有效分组由 `ChannelGrouping.effectiveGroupKey/Title/Group()` 从 `user_group_title ?: group_title` 派生；若改 `group_key`，下次刷新会按原 `(name_key, group_key)` 重新插入一条，出现两台同名。两条都是"**身份列稳定、用户覆盖列叠加**"的同一条原则，实现见 `docs/05-过程记录/41-P3-4频道管理器.md` §3。

> **频道级「不可用」的口径（卡 `DOC-7`，P2-4b 结论 `f7a8bbe`）——本期不加数据列**：`channel` 表**不**加可用性列。当前口径 = **「该频道全部流 `disabled`」即该频道不可用**，并配 `SRC_SELECT.unavailable` / `SRC_REFRESH_DONE.unavailable` 事件字段（§11「频道标记 ⚠️，仍可尝试播放」是 UI 表达）。
> **理由**：① 可用性是**派生态**，权威数据在 `stream.disabled`，另存一列就有了两个写者，刷新/导入/播放各写一处必然漂移（正是 §4.5 C1 要避免的）；② 频道保留可见（不删行）与「无可用流」是两件事，后者用一次 `EXISTS(stream WHERE channel_id=? AND disabled=0)` 即可判定，UI 派生成本可忽略；③ `stream` 行的 `disabled` 已是甄选（§6.1 Select 阶段）的落地点，不新增第二处状态。
> **若将来列表渲染 ⚠️ 有性能问题**（千级频道逐行 `EXISTS` 太慢），再加**只读的 `channel.available` 生成列或视图**，由该 `EXISTS` 派生，仍不允许独立写入——**改动须走「arch 提案 → god 批准 → 版本递增」**。当前 P2-4b 实现与本口径一致，无需改码。

```

  (N源)   (M3U/TXT)  (URL/名称)  (url_hash) (4000) (可达性)  (可解码) (100分) (主+备)  (Room)
```

| 阶段 | 并发 | 超时 | 说明 | 事件码 |
|---|---|---|---|---|
| Fetch | 4 | 15 s/源，8 MB | 并行拉取；UTF-8 → GB18030 回退；失败不阻塞其他源 | `SRC_FETCH_OK/FAIL` |
| Parse | 串行 | – | M3U（`#EXTINF`/`#EXTVLCOPT`）与 TXT（`#genre#`、`名,url`）双格式；**解析器绝不因未知行/未知属性中断整份清单** | `SRC_PARSE_OK/FAIL` |
| Normalize | 并行 | – | URL 规范化（scheme/host 小写、去默认端口、去 fragment）；名称全角→半角/去空白 | – |
| Dedupe | 串行 | – | 按 `url_hash` 去重；**按源交错**保留多样性 | `SRC_DEDUPE` |
| Shallow | 12 | 6 s | 清单可达 + master 变体（前 4）+ **直播边沿分片**（末片→首片） | `VAL_SHALLOW_*` |
| Deep | 6 | 12 s | Media3 `Probe` 解出真实 vcodec/acodec/分辨率 | `VAL_DEEP_*` |
| Score | 串行 | – | 六维加权（和 97）→ 归一化 0–100（下表） | `SRC_SCORE` |
| Select | 串行 | – | 每频道：最高分为主、次高分（≥55）为备胎，最多 3 条 | `SRC_SELECT` |
| Persist | 串行 | – | Room 事务批量 upsert；保留历史健康度 | `DB_UPSERT` |

> 上表的并发/超时数值即 §4.4 `PipelineLimits` 的默认值（唯一定义处），改动只改 `PipelineLimits`。

> **解析容错与 `#EXTVLCOPT` 采集口径（god 批准 2026-09-22，卡 `DOC-3`）**：解析器**容忍 `#EXTVLCOPT` 的任意键**——不认识的键直接忽略，既不报错也不中断整份清单（`#EXTVLCOPT` 是 VLC 的私有扩展，键集合没有标准，未知键必须是无害的）；其中 **`http-user-agent` / `http-referrer` 采集进 `RawEntry`**，落库对应 `stream.user_agent` / `stream.referrer`，供防盗链源在起播时带上正确请求头（评分模型的「防盗链」维度也依赖这两列）。除此之外不做任何头部改写。

**评分模型（六维加权和 = 97 → 归一化到 0–100，可插拔 `ScoringRule`）**

| 维度 | 权重 | 规则 |
|---|---|---|
| 可用性 | 35 | 判定可播放即得 |
| 稳定性 | 25 | 按轮询失败率线性扣；媒体序号不前进再扣 10 |
| 设备兼容 | 20 | H.264=20；H.265=12；AV1=4；**未知=12（中性）**；AC3/EAC3 −5；>1080p −3 |
| 画质/码率 | 10 | 1080p=10；720p=8；480p=5 |
| 防盗链 | 5 | 无需特殊头=5；需要则 3（并记录 UA/Referer） |
| 分片成功 | 2 | 边沿分片 2xx 加分 |

> **权重和 97 与归一化（卡 `DOC-7`，P2-4b 口径，`f7a8bbe`；依据 §8.4 E6「总分归一化到 100」）**：上表六维逐项相加 = 35+25+20+10+5+2 = **97，不是 100**。**权重不改**，按 §8.4 E6 把加权原始和**线性缩放到 0–100**：`total = round(raw × 100 / 97)`；`ScoreBreakdown.byRule` **保留各维原始分**（`SRC_SCORE` 逐维度上报的就是原始分，不是归一化后）。因此 §6.1「Select」行与本节所有阈值（如备胎 `≥55`）**是在归一化后的 0–100 尺度上**判定的。
> **未知编码取中性 12（脚注，P2-4b 决定）**：「设备兼容」维度上表只列了 H.264/H.265/AV1 三档，**探不出编码**（`SRC_SCORE.vcodec=null`）时取**中性 12**——给 0 会因缺元数据误杀、给 20 会白送满分，取中间值且可从事件字段看出原因。该默认值随 S1/S2 复测结论调整（同「设备兼容分」条）。

> **设备兼容分（W6，冻结）**：该维度分数由 `DeviceProfile` + S1/S2 实测结论计算，扣分阈值（H.265/AC3/>1080p 等）随实测调整，**禁止硬编码机型字符串**（如 `MT5895`）；S1/S2 出结论前用上表默认值。

> **源端起播耗时（W-S1-2，S1 实测 2026-09-21）**：S1 的起播耗时呈**双峰**——p50 ≈1.2 s，但 5 条境外/远端源落在 3.7–6.2 s，**尾部完全由源端/网络决定**（同一条源在 S5 复现同样慢，与设备/引擎无关）。评分须把**实测起播耗时**作为一个扣分因子：对历史 `PLAY_FIRST_FRAME.costMs` 中位数 >3 s 的源降权（先并入「稳定性」维度扣分，P1 全量复测后再定是否单列权重与分值），**禁止硬编码源名/地区**。
> **该因子的输入端口（卡 `DOC-7`，留待 dev 接线）**：起播中位数从 `play_history.start_cost_ms` 读，端口为 `StreamRepository.startCostMedianMs(streamId, windowMs)`（§4.3）。P2-4b 已实现扣分**纯函数**（`:core:domain` `Stability`，`>3 s` 起线性扣、`≥6 s` 扣满 0.20），但端口未接线，管线暂传 `null`（尾部扣分 0）；接线属实现任务（dev），不影响 0–1 因子的其余项。

### 6.2 播放与故障转移状态机（F3/F4）

```
        ┌──────────┐  prepare()   ┌───────────┐  first frame  ┌──────────┐
        │  IDLE    │─────────────▶│ PREPARING │──────────────▶│ PLAYING  │
        └──────────┘              └─────┬─────┘               └────┬─────┘
             ▲                          │ error/timeout            │ stall(N s)
             │ release()                ▼                          ▼
        ┌────┴─────┐   give up     ┌───────────┐  switch stream  ┌──────────┐
        │ RELEASED │◀──────────────│ FAILOVER  │────────────────▶│ BUFFERING│
        └──────────┘               └───────────┘                 └──────────┘
```

`FailoverPolicy`（纯 Kotlin）决策输入 → 输出：

| 错误类别 | 判定 | 动作 |
|---|---|---|
| 4xx（403/404/410） | 源失效 | 立即 `SwitchTo(next)`，永久降权 |
| 超时 / 连接重置 | 瞬时 | **起播阶段（未出首帧、仍有备胎）→ 立即 `SwitchTo(next)`**（首跳耐心窗 4 s）；否则 `RetrySame`（≤1 次）→ 失败则 `SwitchTo(next)` |
| 解码失败 / 不支持编码 | 设备不兼容 | `SwitchTo(next)`，并标记该 codec 组合负面 |
| 缓冲停滞 ≥ N 秒 | 卡顿 | `Backoff(1s)` → `SwitchTo(next)` |
| 候选耗尽 | – | `GiveUp` + 提示"该频道暂时不可用" |

> **SWITCH-P95-1（god 批准 2026-09-23）**：有备胎频道的**首次** prepare 耐心窗 = **4 s**（判据 5 s − 实测备胎起播 0.73–0.81 s）；`EngineTuning.prepareTimeoutMs = 12 s` 与**无备胎/单流**频道的完整路径（`RetrySame(≤1)` → `ResolveFresh` → `GiveUp`）**逐字不变**。起播失败过的流只降权不除名、排序最后，仍可在后续尝试中作为回退目标（并给它完整 12 s 窗口）；播放中（已出首帧）的超时保持 `RetrySame(≤1) → SwitchTo(next)`，避免活源抖动被误切。回退开关：`FailoverTuning.switchOnStartupTimeout = false`（配合 `fastFirstAttemptTimeoutMs = 0`）逐字回到 0.1.1 行为。

> 上表与 §4.6 的分类映射等值；`FailoverLimits` 阈值默认值见 §4.3。**无备胎频道（`streams.size == 1`）**：`RetrySame(≤maxRetrySame)` → `ResolveFresh`（该频道按需复检一次）→ `GiveUp`。实测基线 417/579 频道只有一个流，此路径是常态而非例外。

**看门狗**：独立协程，采样 `playbackPosition / bufferedPosition / isLoading`，静止超过阈值即触发上层决策；**换台时复用同一个 `PlayerEngine` 实例**（`stop() + prepare()`），降低起播耗时。

> **状态机归属（冻结，优先于上图）**：上图是**引擎侧**状态；业务态（含故障转移过程）由 **`PlaybackController` 唯一维护**（§4.5 C1）。引擎不自行切源——它只上报 `PlaybackEvent.Error/Stalled`，由控制器调 `FailoverPolicy` 决策，再下发新 `PlaybackRequest`。图中的 `RELEASED` 是引擎状态；UI 侧 `PlaybackPhase.RELEASED` 仅在播放会话结束时出现。

### 6.3 EPG 流程（F6）

```
EpgProvider.fetch() ─▶ 流式 Pull 解析（XmlPullParser） ─▶ 时间窗过滤 ─▶ ChannelMatcher 链 ─▶ Room 事务写入 ─▶ now/next 查询
     (可 gzip)            (不整文件入内存)        保留/修剪窗[now−6h,+48h]   id→name→fuzzy→alias→manual
```

- **EPG 只有两个时间窗，各有用途，别再混用（卡 `DOC-12`，BUG-018 修复 `6c0a3c2`）**：
  - **网格窗 = 唯一的口径窗**：`:core:model` 的 `EpgGridWindow` 定义 `SPAN_MS = 6 h`、`HISTORY_MS = 30 min`、`RULER_STEP_MINUTES = 30`，`of(now, zone)` 给出 **`[floor(now − 30 min), +6 h)`**，起点**按本地时区**对齐到标尺步（Kathmandu UTC+05:45 与 UTC 差 15 min，用 UTC 对齐会错——单测钉住）。**覆盖率与「有节目」的判定、`EPG_MATCH_HIT.programmesInWindow`、择优深度、闸门里的 `programmed` 全部由它派生**（§4.2 `withProgrammes`、§4.3 `EpgStoredGuide`）。这正是「**数出来的 == 看得见的**」的机制保证：BUG-018 的病根就是两处各用了一个窗。
  - **保留窗 = `[now−6h, +48h]`（`ProgrammeWindows`）**：**只回答"数据库留多少 guide"**——parse 阶段的过滤与入库后的 prune（§5.1 节目表滚动窗口）。**它不再是「有节目」的判据**；`now/next` 也仍是"问到哪一刻答哪一刻"，不走网格窗。
- **匹配链可插拔**（E5）：① `tvg-id` 精确 → ② 归一化名称精确 → ③ 前缀/包含模糊 → ④ 人工别名表 → ⑤ 用户手动绑定（存 `epg_match='MANUAL'`，永不被覆盖）。
- **候选化匹配语义（卡 `DOC-11`，EPG-BIND `d56dc88`）**：上面那条链**不再是"先命中先赢"**——**每层（tier 1–4）的全部命中都进候选集**（按 guide id 去重、保留最早层级作 `type`），跑完所有源的所有层再交给下面「绑定择优」一次性定夺；**唯一候选即使 0 节目也绑定**，0 节目候选靠"窗内节目数"规则**自然落败**（**不剪索引**——剪了会测不出 `emptyBinding`，也挡掉"guide 补齐后自动接上"）。**机制保证"既有绑定只增不降"**：每层返回从"一个 id"变成"id 列表"，候选集是旧集的超集 ⇒ 旧胜者仍在 ⇒ 深度不下降。**后果**：`EPG_MATCH_HIT` 由"每频道一行"变为**每候选一行**（同一事件码、同一字段，只是行数，见 `docs/03 §3.3`）。
- **脚本折叠（繁 → 简）属第三级规则（`NAME_FUZZY`，卡 `DOC-10`，`3d3f2a3`）**：内置一张 **繁体→简体单字表（130 字）**，对匹配键两侧做逐字符替换，作为 tier 3 里**最优先**的一条子规则（顺序：**①繁简 ②`+`→plus ③去标点 ④去 feed 标记**，`EpgNameVariants.variants()` 是这四条的 16 个子集枚举）。**为何不进 tier 2**：tier 2（`EpgNameKey`）的键是入库字段 `channel.name_key`（带 `UNIQUE` 约束），折叠语义变化会牵动身份与去重；tier 3 是"可解释、可回退"的折叠层，`EPG_MATCH_HIT` 的 `matchedOn`/`guideKey` 两条并排就能看出折叠。**表来源**：四个 guide 的 `<display-name>` ＋ 出厂夹具，**用 OpenCC（Apache-2.0）`TSCharacters.txt` 求差集**得到差异字（126 语料字 + 4 余量字＝130）；**重生成方法**（三步）：抽 display-name → 用 `TSCharacters.txt` 求差 → 保留差异字，某天新 guide 出现新字按同样三步重生成并过一遍单测（表规模刻意**不**扩到全量繁体）。只做繁→简（简→繁不做），`name_key` 与 `channel.name_key` 一律不动；**无运行时依赖**（表是纯 Kotlin 常量，约 800 B）。详见 `docs/05-过程记录/39-EPG繁简折叠.md`。
- **第 5 条归一化规则「编号手柄」（卡 `DOC-11`，EPG-BIND `d56dc88`）**：把"台号手柄 + 中文栏目名/地区名"约化成**台号手柄**——`cctv-2财经` → `cctv2`、`cctv-16奥林匹克` → `cctv16`、`cctv-5+体育赛事` → `cctv5+`。**从原始键（及繁简折叠后）计算**，**不参与**前 4 条的 16 子集枚举——否则 `cctv-4(亚洲)` 会先被"去标点"变成 `cctv4` 再被判成同台，**拒绝原则失效**。**拒绝异台形状**：`CCTV4K`/`CCTV8K` 的**拉丁尾巴**、`CCTV-4 (亚洲)` 这类**括号尾巴**都不并入 `cctv4`。**残留暴露面 = 无括号中文地区后缀**（`CCTV4美洲` → `cctv4`）——实测无害（未见误并）。手柄**只在 tier 3 末尾追加**，且自己即手柄时为 no-op ⇒ 碰不到的键其变体集合与顺序与上一轮**逐字相同**（既有回归测试不动）。这正是别名表"一条未改就达标"的原因（40 号建议的第二步「补 `CCTVn → CCTV-n 栏目名`」**不需要**）。
- **绑定择优（卡 `DOC-10`，EPG-BIND-1 `4f552eb`）**：同一频道可能被**多个源**同时命中（内地 guide 与港澳 guide 都收 `深圳卫视`），而 `channel.epg_channel_id` 只能存一个。旧实现是"**逐源覆盖、后命中者赢**"——**靠运气**（后一个源若表格更薄，也会悄悄盖掉更好的绑定）。现改为**先跑完所有源、再一次性定夺**：`LoadEpgUseCase` 收集每个源的提议 → **一次** `countByChannelInWindow` 取"窗内节目数" → `EpgBindingPreference.choose` 选唯一赢家 → **一次** `setEpgBindings` 写库。**择优规则（`EpgBindingPreference.choose`，纯函数、全序、可复现）**，按序比较：
  1. **窗内节目数最多者胜**——此处的**窗 = 网格窗**（`EpgGridWindow`，卡 `DOC-12`）：节目条数是"观众真看得见"的度量，god 裁决**择优深度沿用网格窗**（保持「数出来的 == 看得见的」；若某天 guide 普遍很薄、出现绑定反弹，把"择优窗"拆成独立常量即可——**一行改动，不改口径**）；
  2. **并列 → 源顺序**（后命中的源赢，沿用旧覆盖循环的裁决，`sourceOrder` 降序）；
  3. 再并列 → **匹配层级**（`TVG_ID` < `NAME_EXACT` < `NAME_FUZZY` < `ALIAS`，强层级优先）；
  4. 再并列 → **guide id 升序**。
  后两条只为构成**全序**：任何输入下赢家唯一，重跑同一批 guide 绑定不变（幂等）。**唯一候选即使 0 节目也绑定**——"暂无节目"不是解绑的理由，而是覆盖率报告要**说出来**的事（由 `emptyBinding` 口径表达）。详见 `docs/05-过程记录/40-EPG绑定择优与覆盖率口径.md`。
- **覆盖率三口径（卡 `DOC-10`，EPG-BIND-1）**：`EpgCoverage` 同时上报三个数，全量与**主流切片**（**`D14`**：`央视 + 卫视 + 港澳台`，见下条）各一套——
  - **`matched`**：**有 id**（旧口径，`ratio = matched/total`，字段原义保留供老读者）；
  - **`withProgrammes`**：该 id 在**网格窗内 ≥1 条节目**（"观众真的看得到"；窗口在 v1.3 由保留窗追平为网格窗，见 §4.2 注）；
  - **`emptyBinding`**：**有 id 但网格窗内 0 条**（＝ `matched − withProgrammes`）；
  - **`programmedRatio` = `withProgrammes / total`** —— 这是**"说真话"的那个口径**：绑定到一个**背后没有任何节目**的 guide id（界面全空）**不算覆盖**。诊断面板「主流覆盖」与告警门槛都用它（见下条与 §8.1）。
- **「主流频道」定义（`D14`，god 2026-09-22）**：**主流 = 央视 + 卫视 + 港澳台**三类分组之和（对应代码常量 `MAINSTREAM_GROUPS = [CCTV, SATELLITE, HK_MO_TW]`）。本口径此前**无上游定义**（`docs/01–04` 从未写过），`D14` 为首次落定；`docs/03 §3.3` 的 `mainstream*` 字段、`docs/04` §5 的 P3-5/P3 出口判据都按此口径。
- **告警门槛**：`mainstreamProgrammedRatio < 0.60` 时打 **`EPG_COVERAGE` 的 WARN 变体**（**不新增事件码**：`docs/03 §3.3` 冻结 50 条，告警以同一码 + `alert=coverage_below_target` 表达，§6.3 "不打扰用户"——告警是日志事件、不是通知）。P3-5 目标由"id 覆盖率"改按**可看率**判定：**候选化后**实测主流 **`withProgrammes` 153/156 = 98.1% ≥ 60%（达标）**、主流空绑 **0**；全量 `withProgrammes` **200/658**、空绑 9 条（全为本地台、源无数据）。候选化前基线（卡 `DOC-10`，`4f552eb`）：主流 `withProgrammes` 126/156 = 80.8%、空绑 27（口径定义与判据见 `docs/04` §5）。**卡 `DOC-12` 起计数按网格窗**（BUG-018 修复）：真网 4 源采样 `withProgrammes` **203/658**、`emptyBinding` **6**、主流 **153/156 = 98.1%**（与候选化后同一天不同窗的采样，数字小幅变动属窗口口径变化，非回归）。
- **刷新闸门口径（卡 `DOC-12`，BUG-016 修复 `6c0a3c2`）**：`EpgRefreshPolicy.gate` 在"上次成功时间 + 最小间隔"之外多读一个输入 **`EpgStoredGuide`**（`:core:model`，由 `:core:data` 的 `EpgStoredGuideReader` 用 **3 个 COUNT** 取：`channels` 频道表行数、`matched` 有 id 数、`programmed` **网格窗内**有节目数），派生 `catalogReady = channels > 0`、`empty = channels > 0 && (matched ≤ 0 || programmed ≤ 0)`。据此：
  - **目录为空 → `DEFER(catalog_empty)`**：冷启动早于频道表播种时**不再白跑**（旧行为：空表读表、白跑 26 s、还把 `last_fetch_at` 盖掉、冻住后续 6 h）。等待**零网络**：调度器照常入队，作业 `Deferred` → `Result.retry()`（30/60/90 min），播种/导入落在等待期内即成功 ⇒ **新装不必再等一次冷启动**。
  - **空 guide → `RUN(empty_guide)` / `SKIP(empty_backoff)`**：有 id 但窗内没节目的 guide **不算新鲜**。距上次成功在 **`emptyRetryMs`**（新设置项，默认 **30 min**，`coerceIn(0, minIntervalMs)` 夹住）**以内 → `SKIP(empty_backoff)`**，**超过 → `RUN(empty_guide)`**。**空白电视因此会重跑**且节奏有界：**地板 30 min**（不快于 `emptyRetryMs`）、**天花板 6 h**（不慢于 `minIntervalMs`）。
  - **三个 reason token**（`catalog_empty`/`empty_guide`/`empty_backoff`）随 `WORK_SCHEDULE` / `WORK_RUN` 落盘为字段（`docs/03 §3.3`），**不新增事件码**（仍 50）。**未做**：按次数升级的阶梯退避（需持久化计数器）——当前是「地板 + 天花板」的有界常数退避，建议单开卡（见 `docs/05-过程记录/46-BUG016与018修复.md` §8.3）。
- **网格 ⟷ 面板的判读（卡 `DOC-15`；依据 `05-过程记录/52-BUG018取证与NEW2.md` §3.3、`54-BUG018对账修复.md` §2.3）**：诊断面板「EPG 绑定与窗口」按**整表逐台**读、**不做折叠**；EPG 网格按**当前页 32 行**读（§8.3 分页）。同窗同刻对比二者，按**四种情形**判读：① `id=(未绑定)` + 网格空 ⇒ **没绑上**（匹配层/清单）；② `id=X 窗口内 0` + 网格空 ⇒ 该 id 这 6 h **确实无节目**；③ `id=X 窗口内 N>0` + 网格空 ⇒ **该页还没载入**（分页/加载中）；④ **同一页里多个频道共用同一 `epg_channel_id`（guide id 多对一）** ⇒ **回映射必须多对多**。`channel.epg_channel_id` 天生多对一（标清/高清/同名异构台共用一份节目单是常态；出厂夹具 **49 个 guide id 被 120 台共用**），而把节目从 guide id 映射回频道 id 若写成一对一 `associate`，**同页后来者会覆盖前者**，更靠前的持有者拿到空表却仍记「已载入」⇒ 整行画「无节目」、面板照旧 `N>0`（这正是 BUG-018 的病根）。修复（`:core:domain` `EpgChannelHop` 多对多 hop，卡 `BUG-018`）后，同页共用同一 guide id 的**每一台都出块**，情形 ④ **不再产生空行**。
- **失败降级**：EPG 拉取失败保留旧数据，UI 只显示频道名，不阻塞播放。

## 7. 播放引擎设计（`:core:player`）

### 7.1 引擎与选型（冻结规则）

| 项 | 设计 |
|---|---|
| 主引擎 | **Media3 ExoPlayer 1.11.1**（`media3-exoplayer` + `-hls` + `-ui` + `-session` + 可选 `-exoplayer-rtsp`） |
| 抽象 | `PlayerEngine` 接口 + `PlayerEngineFactory` + `EngineSelector`；引擎实现互不感知 |
| 选型 | `EngineSelector.select(required, device)` 按 `capabilities ⊇ required` 选第一个可用工厂；默认仅注册 Media3 |
| 兜底引擎 | `:core:player-vlc`（libVLC 3.7.6，仅 `armeabi-v7a`，LGPL）→ **引入判定（冻结）**：S2 显示 AC3/EAC3 占比 ≥5% 且无法透传时才引入；否则不打包（当前基线 AC3 仅 2/741 ≈ 0.3%） |
| 不可用处理 | `EngineSelector` 找不到满足能力的引擎 → `AppError.capability(...)`（`NO_CAPABILITY`），按 §4.6 降级顺序处理，不静默降级画质 |

> **依据（S1 实测，2026-09-21，`05-过程记录/07-Spike报告` §2）**：Media3 在本机 **20/20 起播**（成功率 100% ≥ 判据 90%）、平均 **2.14 s**（≤ 判据 3 s）；对照集是同一批 MediaPlayer 深探阳性样本，故 `Media3 − MediaPlayer = 0` 个百分点（小样本，只能说明无大规模回归）。据此**维持 Media3 为主引擎**；全量复测作为 P1 入口（见 §7.8）。

### 7.2 生命周期与归属（冻结）

| # | 规则 |
|---|---|
| P1 | 进程内 **1 个** 引擎实例，由 `:app` 的 `PlaybackService`（前台服务）持有；会话范围 = `Watch` 到 `Stop`/退出应用 |
| P2 | 引擎引用由 `:core:player` 的 `PlaybackSession`（机制层：持有唯一实例 + `engine` 调度器 + 窄钩子）与 `:feature:player` 的 `PlaybackFailoverCoordinator`（协调层：**唯一**调用引擎所有方法的角色）共同承担，且只在 `DispatcherProvider.engine` 上调用（§4.5 C2；落位口径见本表后 note） |
| P3 | 进入/离开播放页 **不创建/释放引擎**：`PlayerActivity` 只 `attachSurface(surface, owner)` / `attachSurface(null, owner)`；`null` = 停渲染不停音频 |
| P4 | 前台服务在会话期间常驻（防冻结）；会话结束才 `stop()` + `release()` + 停服务 |
| P5 | `release()` 之后引擎不可复用；控制器必须重新 `create()`（保证状态机干净） |

> **落位口径（god 裁决 2026-09-22，卡 `DOC-6`；替代本表 P2 原先「实现位于 `:core:player`」的写法）**：`PlaybackController` 是 §4.3 的 domain 端口，仍是业务态的唯一入口；其**实现职责拆成两层** ——
> - **机制层** `:core:player`：`PlaybackSession`（唯一引擎实例 + `engine` 调度器 + 窄钩子 `sample()` / 呈现回调）。
> - **协调层** `:feature:player`：`PlaybackFailoverCoordinator`（会话循环，以及 §7.3 播放事件码的唯一发出者）。
>
> 协调器放 `:feature:player` 的原因：`:core:player` 被 §3.2 矩阵禁止直接声明 `:core:domain`，而协调器必须同时看见引擎钩子与 `FailoverPolicy`；`:feature:player` 是唯一同时满足矩阵与 JVM 单测的层。**下一位开发者不要照旧文档把协调器写进 `:core:player`。**

### 7.3 起播契约（冻结：S1/S5/S6 的指标口径来源）

| 项 | 规则 |
|---|---|
| 入口 | `suspend fun prepare(request: PlaybackRequest): AppResult<PreparedMedia>`；`request.timeoutMs` 默认 12 s，超时返回 `AppError.timeout(...)` |
| 互斥 | 同一时刻只允许一个进行中的 `prepare`（`Mutex`）；新请求 = 取消旧请求 → 等旧请求清理完成 → 起新请求 |
| 可取消 | `prepare` 必须响应取消；被取消的请求返回 `CancellationException`（不记 `PLAY_PREPARE_FAIL`） |
| **起播开始** | `playbackPrepareStartUptimeMs` = 控制器下发 `prepare` 的系统 uptime |
| **首帧** | 引擎 `onRenderedFirstFrame` → 发 `PlaybackEvent.FirstFrame(costMs)`；`costMs = firstFrameUptimeMs − prepareStartUptimeMs` |
| **埋点归属** | `PLAY_PREPARE_START` / `PLAY_FIRST_FRAME` 由 `PlaybackController` **唯一发射**（引擎只发事件，不写日志），`sessionId` 取自 `SessionIdFactory.newId("play")` |
| 失败 | 失败必须带 `AppError.failure`（§4.6 映射表），并附 `attempt`（从 1 起） |

### 7.4 Surface 与显示（冻结）

| 项 | 设计 |

### 7.5 复用与调优默认值（冻结；S1/S5 出结论后按 §4.7 回写）

| 项 | 默认值 | 说明 |
|---|---|---|
| 实例复用 | 单实例 `stop()+prepare()` | S5 验证复用是否真的更快 |
| 起播缓冲 | `minBufferMs=1500`、`maxBufferMs=5000`、`bufferForPlaybackMs=800` | 追起播速度优先 |
| 直播边沿 | `targetOffsetMs=3000`、`minPlaybackSpeed=0.97`、`maxPlaybackSpeed=1.03` | 追边沿、避免超追 |
| 卡顿阈值 | `stallThresholdMs=8000`（§4.3 `FailoverLimits`） | 看门狗采样 1 s 一次 |
| 重试 | `LoadErrorHandlingPolicy` 仅在 `retryable=true` 时重试；重试次数由 `FailoverLimits.maxRetrySame` 统一控制 | 与 §4.6 一致，避免双重重试 |
| 缓存 | `SimpleCache` **默认关闭**（P1 前不引入） | 直播收益低 |
| 系统集成 | `MediaSession`（media3-session）+ 音频焦点 + `setWakeMode` + 屏幕常亮 | 遥控播放键走 MediaSession |

> **依据（S5 实测，2026-09-21）**：复用单实例 30 次：平均 **946 ms**、PSS **+3.9 MB**；重建实例 10 次：平均 765 ms、PSS **+12.5 MB**（**~1.25 MB/次**），建实例仅 ~4 ms。**重建的代价是内存而非速度**——所以「单实例复用」的价值是内存与状态可控，**不是更快**。本节默认值维持不变。

### 7.6 音频能力与降级顺序（冻结；S2 判定）

```
探测设备能力（AudioCapabilities + 已连接设备）
  → 优先直通（AC3/EAC3/MP2 若设备声明支持）
  → 失败/无声：关闭直通重试同一流（preferPassthrough=false）
  → 仍失败：SwitchTo(备胎)（按 §4.6 的 NO_CAPABILITY）
  → 无备胎：ResolveFresh → GiveUp + 明确提示"该频道音频不兼容"
```

- **术语（S2 实测修订）**：原「软解」措辞改为「**引擎/设备解码为 PCM**」。本机实测（S2）显示 AC3/EAC3 走的是**压缩码流直通 HAL**（设备侧解码），AAC/MP2 才解成 PCM 走混音线程——两种配置下音频路径一致，故不应笼统叫「软解」。
- **新增观测项「码流直通 HAL」**：真机上「引擎解码 vs 直通」必须可区分，判据是 `dumpsys media.audio_flinger` 中本进程的 `AUDIO_FORMAT_AC3` / `AUDIO_FORMAT_E_AC3` DIRECT 线程活动与 `underruns`（写入 `PLAY_FIRST_FRAME` / 诊断日志），否则日志无法判定实际走了哪条路径。
- **MP2 的 mime**：Media3 1.6 上 MP2 的 mime 是 **`audio/mpeg-L2`**（不是 `audio/mpeg`）；能力探测须以 `MediaCodecList` 的实际类型为准，禁止按 `audio/mpeg` 误判「不支持」。

> 依据：基线 741 条流中 AAC 695、**MP2 30**、AC3 2、缺元数据 14。MP2 与"无元数据"两类必须在 S2 全覆盖，不能只测 AC3。
> **S2 结论（2026-09-21）**：AAC / MP2 / AC3 / EAC3 四类在本机**全部可解码播出**（AC3/EAC3 走设备直通，AAC/MP2 走 PCM 路径），本节降级顺序维持不变，**无需引入 libVLC**（见 §7.8）。
> **限制（如实记录）**：S2 的「出声」是**路径级证据**（音轨选中 + 播放位置前进 + HAL 活动输出 + `underruns` 0），**不是听感证据**（本轮无人耳/无麦克风）；**未做 HDMI ARC/AVR 透传实测**（本机只挂 `builtin_speaker`）；AC3/EAC3 用的是**裸 ES** 公开测试向量（经本机 HTTP 分发），**非 HLS/TS 直播封装**，即「直播边沿 + AC3 直通」这条路径**未验证**。

### 7.8 P0 Spike 结论（2026-09-21 定稿，依据 `05-过程记录/07-Spike报告`）

P0 的 S1/S2/S5/S6 全部通过，本节原「待定项」逐条落为结论：

| 原待定项 | 由谁定 | 结论（2026-09-21） | 依据 |
|---|---|---|---|
| Media3 是否作主引擎（成功率/起播） | S1 | **维持 Media3 为主引擎** | 20/20 起播（100% ≥90%）、平均 2.14 s；对照集 MediaPlayer 亦 100%，差值 0（小样本）|
| 是否需要 libVLC 兜底模块 | S2 | **不打包 libVLC**（维持） | AC3/EAC3 占比 **0.27%**（2/741，且这 2 条已源失效）≪ 5% 阈值，且本机**可解码、可透传**——两个引入条件都不满足；S2 音频矩阵全绿（AAC/MP2/AC3/EAC3 均出声路径 OK）|
| 引擎复用是否优于重建实例 | S5 | **维持单实例 `stop()+prepare()`** | 复用 30 次平均 946 ms、PSS +3.9 MB；重建平均 765 ms、PSS +12.5 MB（~1.25 MB/次）——代价在内存而非速度（§7.5）|
| 启动期预加载范围 | S6 | **维持「只预加载频道表 + 上次频道元数据」** | 夹具级冷启动到可看 1.39–1.55 s（≤5 s）；夹具不含频道表/Room，属**下限**（§8.6）|
| `DeviceProfile` 的 codec/分辨率上限 | S1/S2 | 维持 H.264 ≤1080p 为默认最优档 | 实测可播含 HEVC 1080p/2160p、MPEG-2、MP2；上限随 P1 全量复测校准 |
| **「20 条样本」升级为全量复测** | 新增（W-S1-3） | **P1 入口条件 = 用 Media3 全量复测 658 条** | 20 条样本无法暴露细小差异（对照集本身是 MediaPlayer 阳性集）；全量复测用于补齐 `Media3 − MediaPlayer` 差值 |

## 8. UI 架构（Views + Leanback）

### 8.1 导航结构

```
WizardActivity（仅首次）
      │
      ├─▶ BrowseActivity ──┬─▶ ChannelListFragment（分组 Tab + 列表）
      │                    ├─▶ EpgGridFragment（时间网格）
      │                    └─▶ SettingsActivity ─▶ DiagnosticsFragment / LogViewFragment
      └─▶ PlayerActivity（全屏）
```

- **Activity 边界**：播放独立 Activity（生命周期清晰、避免与浏览页互相拖累）。
- **单向数据流**：`ViewModel` 暴露 `StateFlow<UiState>`，View 只渲染 + 发事件；`UiState` 为不可变 data class。
- **本地导入入口（卡 `DOC-5`，P2-6 最小可用，`f9574ba`）**：频道表页（`BrowseActivity`）顶部工具区新增「**导入播放列表**」按钮（`@id/import_playlist`，位于 `browse_header` 与频道列表之间；列表首行按 `DPAD_UP` 可达）。层级 = **浏览页 → 文件选择对话框（`AlertDialog`，列出投放目录里的候选清单）→ 选中某项即原地导入并刷新列表**；**不新增 Activity、不改返回栈**。返回键 = **关对话框、留在浏览页**（导入成功后同样不新开页面）；投放目录为空时对话框只显示目录路径与「关闭」按钮。

**导航契约（冻结）**

| 项 | 约定 |
|---|---|
| 播放入参 | `PlayerActivity` 只认 `PlayerContract` 三个 extra：`EXTRA_CHANNEL_ID: Long`（必填）、`EXTRA_STREAM_ID: Long?`（可选，指定起始流）、`EXTRA_AUTOPLAY: Boolean`（默认 true） |
| 播放返回 | `setResult(RESULT_OK, Intent().putExtra(EXTRA_RESULT_CHANNEL_ID, channelId))`；浏览页收到后**按 channelId 恢复焦点**（找不到则回到分组首项） |
| 浏览页状态 | 分组 Tab 索引、滚动位置、焦点位置在 `onSaveInstanceState` 内保存；进程重建后必须恢复 |
| 向导退栈 | 向导完成 → 启动 `BrowseActivity` 并 `FLAG_ACTIVITY_CLEAR_TASK or FLAG_ACTIVITY_NEW_TASK`（返回键不再回到向导） |
| 返回键层级 | 播放页 → 浏览页；浏览页 → 系统（App 不从浏览页直接退出播放会话，播放由控制器停止）；设置/诊断 → 浏览页；对话框 → 关对话框 |
| 事件通道 | ViewModel 暴露 `StateFlow<UiState>`（状态）+ `Channel<UiEvent>`（一次性事件，buffer = 8，`DROP_OLDEST`）；View 不得直接调 Repository/引擎 |
| 导入播放列表入口 | 频道表页（`BrowseActivity`）的「导入播放列表」按钮 → `AlertDialog` 选择设备投放目录里的本地清单；选中后**整体替换**当前频道表并原地刷新（不新增 Activity/层级，返回键只关对话框）。详见上方「本地导入入口」，实现见 `docs/05-过程记录/19-本地导入验证.md` |

> **诊断面板「主流覆盖」文案（卡 `DOC-10`，EPG-BIND-1 `4f552eb`）——冻结面（§8 UI）内的展示变更，本批回写**：设置 → 诊断 → 运行概览的 EPG 区块里，「**主流覆盖**」与「覆盖」两行由**旧口径 `matched/total`** 改为**可看率口径** `withProgrammes / total`（见 §6.3「覆盖率三口径」），并在**空绑非零时**追加后缀「**（空绑 N）**」，例如 `149 / 156 = 95.5%（空绑 4）`；`emptyBinding = 0` 时**逐字同旧字符串**（健康列表行为不变）。同一行同时修掉一个既有缺陷——此前面板「主流覆盖」的分母 `byGroupTotal` 未填，显示为 `153 / 0 = 0.0%`，本轮补齐。实现 `DiagOverview.coverageText/coverageOf/mainstreamOf`（`:feature:settings`），口径与事件字段一致（§6.3）。诊断面板内容见 [`03` §7.1](./03-日志与诊断设计.md)。

### 8.2 焦点与遥控（TV 核心）

| 关注点 | 做法 |
|---|---|
| 焦点可见性 | 焦点态用**缩放 + 描边 + 高亮**三重反馈；禁用系统默认高亮（`defaultFocusHighlightEnabled=false`）后自绘 |
| 焦点路由 | 显式 `nextFocusUp/Down/Left/Right`；列表用 `LinearLayoutManager` + `focusSearch` 兜底 |
| 按键映射 | **播放页（冻结；卡 `DOC-6` 对齐 P1-5 现状）**：`KEYCODE_DPAD_UP/DOWN`（含 `KEYCODE_CHANNEL_UP/DOWN`）=**换台**（同分组、按浏览列表顺序；**不做焦点移动**）；`KEYCODE_0..9`=**跳台**（冻结的 **2 s 输入窗口**，支持多位频道号，输入中在信息条回显）；`KEYCODE_DPAD_LEFT/RIGHT`=进入信息条的「画幅」与失败卡片的「重试」（上下键已让给换台）；`KEYCODE_MEDIA_PLAY/PAUSE`=播放控制；`KEYCODE_BACK`=**两级**（信息条可见 → 先收起信息条；再按 → 回浏览页）。浏览页/网格页键位见下方焦点路由表 |
| 过扫描安全区 | 5% 边距（`dimens` 统一），所有可点元素落在安全区内 |
| 10-foot 规范 | 正文 ≥ 18sp、标题 ≥ 28sp、焦点态最小 48dp 命中区 |
| Leanback 使用 | `BrowseSupportFragment`/`ListRow` 用于分组与卡片；列表虚拟化依赖 `RecyclerView`（658+ 台必须虚拟化） |

- **默认高亮不叠加的规则（冻结，卡 `DOC-12`，P3-7 裁决）**：框架的 `defaultFocusHighlight` **只在背景不含 `state_focused` 时**才绘制。本 App 的行/键/按钮背景**都是含 `state_focused` 的 selector**，所以它们**本来就不叠加**框架默认高亮——`defaultFocusHighlightEnabled=false` **不需要逐屏去关**。唯一例外是 **EPG 网格**：它是 `Canvas` 自绘、没有 selector，必须在 `API 26+` 显式关掉默认高亮（`EpgGridLayout` 已关）。**新增自绘控件照此办理**。
- **焦点视觉 token 归 `:core:design`（卡 `DOC-12`）**：焦点色/描边宽度是 **token**（`values/colors.xml` + `TvFocus.kt`），不是 `:core:ui` 里的组件常量——理由与分界见 §3.1 注；强调色 `#FF7AC7FF`／2 dp、行高亮 `#FF2B2B3C` 全局统一（搜索键盘由琥珀改蓝即为本条的一次应用）。
- **数字键跳台**：缓冲窗口冻结为 **2 s**；频道号优先级冻结为「用户编辑 > 源 `tvg-chno` > 自动编号」（`01` F5 附注）。
- **焦点路由表**：播放页的上下键**不**做焦点移动（直接换台，见上表按键映射），「画幅」与「重试」改由**左右键**到达（`PlayerActivity.renderOverlay` 按相位重设左右目标，避免失败卡片出现后的焦点死区）——**P1-4 的上下焦点布线已被 P1-5 按本条冻结条款替换**；浏览页左右键切分组 Tab、上下键在列表内移动；网格页上下键跨行取同列节目，左右键按时间步进。

### 8.3 EPG 时间网格（自绘，性能关键）

- **自定义 `View` + `Canvas`**：二维虚拟化，**只绘制可视矩形内的节目块**；
- 横向 = 时间轴（`OverScroller` 惯性滚动），纵向 = 频道（与左侧频道栏联动）；
- 当前时间红线；节目块点击 → 详情/切台；`StaticLayout` 缓存文本布局；避免滚动中触发布局；
- 调试期用 `FrameMetricsAggregator` 采集帧耗时，写入 `metric` 表并在诊断页展示。

> **二维虚拟化是硬性要求（S3 实测，2026-09-21）**：自绘 + 二维虚拟化 **60 fps**（p95 16.72 ms，30 s 内 0 掉帧）；**不做虚拟化**（每帧遍历全部 658 行）只有 **4.3 fps**（p95 266 ms，帧耗时是前者的 ~14 倍）。因此「只绘可视矩形」是冻结契约的**硬性项**，任何实现都不得退化为全量遍历。

**数据与性能契约（冻结）**

| 项 | 约定 |
|---|---|
| 数据来源 | 网格**只能**经 `EpgRepository.observeWindow(EpgWindowQuery)`（§4.3）；禁止 UI 直接查 Room |
| 窗口上限 | 单次 ≤64 频道、窗口 ≤24 h（`EpgWindowQuery.limit`）；翻页用游标，不一次性加载 658 台 × 多日 |
| 绘制 | 二维虚拟化，只绘可视矩形；`StaticLayout` 结果按 (text,width,style) 缓存，缓存上限 512 条 |
| 埋点 | `PERF_EPG_GRID` 事件（fps、**drawnBlocks＝每帧绘制块数**、**layoutCacheHit＝文本布局缓存命中率**、scrollMs）在 debug 全量、release 采样（默认 10% 会话）；`drawnBlocks` 应稳定在可视块数量级（实测 ≈119 块/帧），若逼近总块数（≈5922）即为虚拟化失效 |

### 8.4 性能预算

| 指标 | 目标 |
|---|---|
| 频道列表滚动 | ≥ 50 fps |
| EPG 网格滚动 | ≥ 50 fps |
| 冷启动到可看 | ≤ 5 s |
| 换台（同引擎复用） | 平均 ≤ 3 s |
| 播放内存增量 | ≤ 150 MB |

### 8.5 测量口径（冻结；S3/S6 按此复现）

| 指标 | 口径 |
|---|---|
| 帧率 | **release 构建**，连续滚动 30 s，`Choreographer` 采样帧间隔，报 p50/p95；**达标线 = 无掉帧（60 Hz 输出下 p95 ≤ 17 ms，即 ≥50 fps 的等效均值）**——原「p95 ≤ 16.7 ms」是与 60 Hz vsync 死磕，实测正常值就落在 16.72 ms（S3），故给 0.3 ms 容差 |
| 冷启动 | release 构建，杀进程后冷启动 **5 次取最大值**；起点 = `Process.getStartUptimeMillis()`，终点 = 首帧渲染完成（`PLAY_FIRST_FRAME`） |
| 换台 | release 构建，连续换台 30 次，报平均与 p95；按「有备胎 / 无备胎」分组 |
| 内存 | 播放 10 min 后 `Debug.MemoryInfo` 采样，对比进入播放页前基线 |
| 记录 | 每次测量写 `PERF_*` 事件 + `metric` 表，结论回写本文档 §7/§8 与 `04` 的 Spike 判据 |

### 8.6 P0 Spike 结论（2026-09-21 定稿，依据 `05-过程记录/07-Spike报告`）

| 原待定项 | 由谁定 | 结论（2026-09-21） | 依据 |
|---|---|---|---|
| 自绘网格方案是否成立 | S3 | **成立（自绘 + 二维虚拟化）**，虚拟化为硬性要求（§8.3） | 60 fps vs 4.3 fps |
| 列表/网格达标档位（是否降级为「列表 + 精简网格」） | S3 + 真机 | **不降级** | 原型 60 fps，对达标线（§8.5）有余量 |
| 启动期预加载到哪一步（频道表 / 台标 / EPG now-next） | S6 | **维持「频道表 + 上次频道元数据」** | 冷启动到可看 1.39–1.55 s |
| 过扫描微调是否需要进设置首屏 | S3 真机观察 | 放设置「显示」二级页（不变） | S3 未纳入该观测，维持原判 |

> **限制（如实记录）**：S6 是**夹具级下限**——夹具首页不解析 658 条频道表、不初始化 Room、不取台标，因此 1.39–1.55 s 只是绘制路径的下限，**真实产品冷启动须在 P1 带频道表/Room 后复测**；S3 只覆盖绘制与滚动，**不覆盖数据加载**（真实 EPG 分页、`StaticLayout` 命中分布未测）。

## 10. 并发与线程模型

| 场景 | 调度器 | 并发上限 | 说明 |
|---|---|---|---|
| UI | `Dispatchers.Main.immediate` | – | 只做渲染与事件分发 |
| 网络（源/EPG） | `Dispatchers.IO` | Fetch 4 / Shallow 12 | `Semaphore` 背压 |
| 深度探测（Media3） | `Dispatchers.IO` + 专用单线程池 | 6 | Media3 实例较重，限制总量 |
| 解析（M3U/XMLTV） | `Dispatchers.Default` | CPU 核数 | 大文件流式，避免整文件入内存 |
| 数据库 | Room 自带执行器 | – | 批量事务写入 |
| 播放 | **单线程 confined dispatcher** | 1 | 引擎状态机串行化，避免竞态 |
| 看门狗 | `Dispatchers.Default` | 1 | 定时采样，超阈值发事件 |

**规则**：所有 `Dispatcher` 通过 `DispatcherProvider` 注入（可测）；长任务必须响应 `CancellationException`；不允许在 `GlobalScope` 起协程。
本表的并发上限与超时数值由 §4.4 `PipelineLimits` 唯一定义；播放线程、状态写者、取消语义以 §4.5 的冻结契约 C1–C6 为准（本节不重复定义）。

> **指标写入（W5，冻结）**：`metric` 表的**唯一写者**是 `MetricsRepository`（`:core:data`）；`MetricBridge`（`:core:log`）只把白名单事件转成 `Metric` 交给端口，**不直接依赖 Room**（Room 绑定留在 `:core:data`，与 §3.2 矩阵一致）。

## 11. 错误处理与降级

| 层 | 责任 |
|---|---|
| platform | 把技术异常转成 `AppError`（带事件码 + `FailureClass`，§4.1），不抛给上层 |
| domain | 决策（重试/切换/放弃），不关心具体实现 |
| data | 事务一致性；写失败不破坏已有数据 |
| presentation | 把 `AppError.code` 映射为用户可读文案（映射表随 `values/strings.xml`）；**绝不**直接显示堆栈 |

> 分类与策略动作的唯一出处是 §4.6 的映射表；本节只描述各层职责，不另立规则。

**降级矩阵**

| 故障 | 降级行为 |
|---|---|
| EPG 不可用 | 隐藏节目信息，只显示频道名；播放不受影响 |
| 源刷新失败 | 保留上次数据，提示"使用缓存数据" |
| 某源全部候选不可用 | 频道标记 ⚠️，仍可尝试播放（可能临时恢复） |
| 播放引擎不支持该流 | 切备胎；若配置了 libVLC 则切换引擎 |
| 存储写入失败 | 内存态继续可用，下次启动重试 |
